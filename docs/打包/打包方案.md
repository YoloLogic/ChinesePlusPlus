## 一、先破一个直觉：编译器不是一个自给自足的程序

可以把它想成一个厨师：**会用中文点菜、认得中文菜谱，但锅碗瓢盆和食材是别人的。**

你编译一个 `你好.cpp` 的那一刻，机器上同时有三拨东西参与：

| 参与的东西 | 谁提供 | 实测大小 |
|---|---|---|
| 编译器本体（词法/语法/语义/优化/生成） | **我们** | 78 MB（全在一个 exe 里） |
| clang 自己的内建头（`stddef.h`、`stdarg.h`…） | **我们**（构建时生成） | 8 MB |
| clangd（给 IDE 用的语言服务） | **我们** | 45 MB |
| C++ 标准库 + 系统头（`<cstdio>`、`<vector>`、`<windows.h>`） | **微软**（随 Visual Studio） | 15 + 345 = **360 MB** |
| 链接器 + 导入库（把 `.obj` 拼成 `.exe`） | **微软**（`link.exe` + `.lib`） | 501 + 86 + 105 = **692 MB** |

**实测证据**（`chinese++.exe -### 随便.cpp`，注意当时 `INCLUDE` / `LIB` 都是空的，
也就是**没有 source 过 vcvars**）：

```
-internal-isystem ...\VC\Tools\MSVC\14.44.35207\include          ← 微软 STL
-internal-isystem ...\Windows Kits\10\Include\10.0.26100.0\...   ← Windows SDK
" ...\VC\Tools\MSVC\14.44.35207\bin\Hostx64\x64\link.exe"        ← 微软链接器
```

**好消息**：clang 会**自己探测** Visual Studio 的安装位置（走注册表 / vswhere），
所以用户**不需要** source `vcvarsall.bat`。这让打包比想象中简单。

## 二、关键事实：Windows 上**没有**"系统自带 C++ 标准库"

- **Linux / macOS**：系统自带（glibc + libstdc++ 或 libc++），编译器直接拿来用。
- **Windows**：微软**故意不预装** C++ 标准库。想编 C++ 的人都得自己解决。

这不是我们的设计缺陷 —— **官方 clang、GCC、MinGW 面对的是同一件事**，只是答案不同：

| 工具链 | 怎么解决 | 代价 |
|---|---|---|
| **官方 clang（我们目前这条路）** | 借用微软那套（VS 里） | 与 Windows 生态兼容最好；用户必须装 VS Build Tools（免费，下载 1.5~2.5 GB、装完 4~7 GB） |
| **MinGW / 小熊猫 C++** | 自己捆一套 | 开箱即用；但 **ABI 不同**（Itanium vs MS），链不上微软编的库和 DLL |
| libc++ + lld | LLVM 自家 STL + 自家链接器 | 干净；但 Windows 上**仍然要** SDK 的导入库（`kernel32.lib` 是系统 DLL 的接口，躲不掉） |

> **一个已经踩到的坑**：项目里曾有 `tools\setup_redpanda_clang.ps1` 去接入**小熊猫 C++**。
> 但小熊猫 C++ 捆的是 **MinGW**，而我们的编译器是 **MSVC ABI** —— 两边标准库与 ABI 不兼容。
> 那个配置能"跑起来"，但用户不能拿它去链 MinGW 编的库。
> **这不是 bug，是底层工具链选择了不同的生态。**

## 三、四个阶段

用"**用户下载之后会经历什么**"来讲最清楚：

### 阶段 1：只发命令行编译器（约 55 MB）
```
下载 55 MB → 解压 → 敲 chinese++ 你好.cpp
→ 报错：#include <cstdio> 找不到
→ 得去装 Visual Studio Build Tools（下载 2 GB、装完 6 GB、要重启）
→ 回来才能编
```
**我们做的工作**：小。**用户感受**：能用，但第一步很重。

> ⚠️ 体积里**必须**包含：`lld-link.exe`、`llvm-ar.exe`、`llvm-lib.exe`、`llvm-ranlib.exe`、`llvm-rc.exe`
> （约 +55 MB，**这五个已于 2026-09-23 编好并装进 `bin\`**），
> 以及 `lib\clang\24\lib\windows\clang_rt.*` 运行时（**2026-09-26 已构建 12 个 / 8.1 MB，
> 已随包**；当日之前是"一个都没有"）。
> 见第五节的实测。少了工具，用户哪怕装好了 VS，CMake 工程照样编不过；
> 少了运行时，`-fsanitize` / `-coverage` / PGO 全都不可用。

### 阶段 2：加 clangd + 安装脚本（约 75 MB）—— 性价比最高

> **0.1 的那个包**：zip **77.8 MB**，未压缩 194.2 MB（361 个文件）—— 见 §7.6。**当前 0.2：zip 80.8 MB / 未压缩 197 MB / 476 个文件（§7.9～§7.12）。**
比阶段 1 多：
- `clangd.exe` → VS Code 里能得到中文高亮与补全
- 上面那四个二进制工具（若阶段 1 已带则不重复）
- 安装脚本：自动加 PATH、检测"你还没装 VS"并给下载链接、生成本机别名
- 带中文名的包装脚本（自动加 `-std=c++20`），用户不用记参数

### 阶段 3：零依赖，把微软那套也捆上（**约 +1 GB**）
```
下载 400~600 MB → 解压 → 直接能编，什么都不用装
```
真实含义是：要编出 `lld-link`、处理 MSVC STL 的版本锁与许可、把 SDK 导入库一起打包 ——
**也就是把自己变成一个 MinGW 级别的完整工具链发行版**。另一个量级的工程，
且每次 VS/SDK 升级都要跟。

### 阶段 4：VS Code 扩展（体积很小）
中文关键字高亮、一键新建中文项目、集成 clangd 与调试。
**这一阶段和上面三个不在一条轴上**：上面解决"能不能编译"，它解决"像不像中文编程"。

## 四、怎么选：三个问题

| 问题 | 是 → |
|---|---|
| 目标用户是**已经在写 C++ 的人**吗？ | 阶段 2 就够（他们大概率已有 VS） |
| 想让**从没装过开发环境的学生**直接用吗？ | 阶段 2 不够 → 阶段 3，或干脆做**一体包**（便携 VS Code + 我们的工具链 + 项目模板），后者其实比纯阶段 3 更值 |
| 最在意"让人觉得这就是中文编程"吗？ | **阶段 4 优先级最高** —— 它决定第一印象 |

**建议顺序**：先做阶段 4 的最小版（见《一键配置-VSCode.md》），拿 10 个真实用户反馈，
再决定要不要为阶段 3 付那 1 GB 的代价。大概率你会发现用户的抱怨不在"装 VS 麻烦"。

## 五、打包时的技术陷阱（都是实测的）

| 陷阱 | 说明 |
|---|---|
| **硬链接过不了 zip** | `chinese++.exe` 是 `clang++.exe` 的硬链接；压缩会把硬链接展开成两份或丢一份。所以**包里只放一个 `chinese++.exe`**，其余名字（`chinese.exe` / `clang.exe`）由安装脚本在装的时候生成 |
| **驱动靠"名字后缀"决定模式** | `++`→g++、`cl`→cl、`cpp`→预处理器。**`chinese++.exe` 这个名字不能改**（改成 `chinese.exe` 就成了 C 模式）。要 C 模式就额外生成一个 `chinese.exe` |
| **目录布局不能拆** | 必须保持 `bin\chinese++.exe` + `lib\clang\24\include\` 的相对关系（resource-dir 是相对 exe 推出来的） |
| **`--version` 别乱改** | 路线图已定：很多工具解析 `clang version ...`。要体现品牌用 CMake 的 `-DCLANG_VENDOR="Chinese++ "`，它只往括号里加内容 |
| **本机构建里白白多占 312 MB** | `bin` 里 `clang.exe`/`clang-cl.exe`/`clang-cpp.exe` 是**各自独立的 78 MB 副本**（只有 `chinese++.exe` 与 `clang++.exe` 是硬链接）。发行时只带一份即可；想在本机省盘可以把它们改成硬链接，但**重编会被 MSBuild 重新拷成副本** |
| **许可** | LLVM/Clang 是 Apache-2.0 with LLVM exceptions → 随包必须附 `LICENSE.TXT` / `NOTICE`。我们的中文表是**额外新增**的文件，同许可。若将来捆 MSVC STL：微软那套已 MIT 开源、可再分发 |
| **🔴 发行包缺一整套二进制工具** | 见下面《这一条是真的会拦住用户》——不是"最好带上"，而是**不带就编不动任何 CMake 项目** |

### 好消息：这些缺件的源码我们全都有，缺的只是"配置 + 编译"

| 缺件 | 源码 | 当前构建配置 | 补的成本 |
|---|---|---|---|
| `llvm-ar` / `llvm-lib` / `llvm-ranlib` | ✅ | **已经配置好了**（`LLVM_TOOL_LLVM_AR_BUILD=ON`，VS 工程 `llvm-ar.vcxproj`/`llvm-lib.vcxproj`/`llvm-ranlib.vcxproj` 都生成了） | **直接 MSBuild，分钟级** |
| `llvm-rc` | ✅ | **已经配置好了**（`LLVM_TOOL_LLVM_RC_BUILD=ON`） | 直接 MSBuild |
| `lld-link` | ✅ `LLVM-main\lld` | ❌ `LLVM_ENABLE_PROJECTS=clang;clang-tools-extra`，`LLVM_TOOL_LLD_BUILD=FALSE` | 加进 projects，重新生成解决方案 |
| `clang_rt.*` | ✅ `LLVM-main\compiler-rt` | ❌ `LLVM_ENABLE_RUNTIMES` 为空 | 加进来重配置 + 编译 |

**临时替代方案（已实测，但不建议作为产品方案）**：把官方 LLVM 的 `bin` 放进 `PATH`，
我们的 clang 就会在那里找到 `lld-link`（clang 的查找顺序是"**驱动所在目录 → PATH**"）。
实验证明**配置阶段立刻恢复**——但也立刻撞上下一个缺件（`clang_rt.profile.lib`）。
所以"借官方的 lld-link"只能当**诊断手段**：官方那套是**一整套**（lld + 二进制工具 + compiler-rt），
缺任何一个都会掉链子；而且它还带版本混搭（19 的链接器 + 24 的编译器）的问题。

两条实测报错原文：

```
# 1) 缺 lld-link.exe —— CMake 4.2 的 Windows-Clang.cmake 第 65 行默认给 -fuse-ld=lld-link
clang: error: unable to execute command: program not executable
clang: error: linker command failed with exit code 1

# 2) 缺 llvm-ar.exe —— CMake 找不到归档器，直接把占位符当命令执行
CMAKE_AR-NOTFOUND qc tinyxml2.lib CMakeFiles/tinyxml2.dir/tinyxml2.cpp.obj
'CMAKE_AR-NOTFOUND' is not recognized as an internal or external command
```

**所以"阶段 1：只发命令行编译器"这个说法得改**：阶段 1 的清单里必须再加

```
bin\lld-link.exe    bin\llvm-ar.exe    bin\llvm-lib.exe    bin\llvm-ranlib.exe
```

（合计约 +10 MB 量级。）**否则用户拿到的是一个"能单独调用、但任何 CMake 工程都用不了"的编译器。**
详细的对照实验与结论见 `E:\Chinese++\third_party\README.md`。

## 七、2026-09-25 实测：体积、重复与许可证

> 上面各阶段的体积是**估计**，这一节是**量出来的**。数字差得比较多，原因是重复。

### 7.1 实测体积

```
build\Release\bin\                650 MB（20 个文件）
build\Release\lib\                926 MB（444 个文件）
   └ lib\*.lib                    918 MB（149 个）← 编译器自己的构建产物，用户不需要
   └ lib\clang\24\                  8 MB ← resource dir，必须随包
```

### 7.2 六成的体积是重复（关键发现）

```
clang.exe / clang-cl.exe / clang-cpp.exe / clang++.exe   四个 SHA256 完全相同
lld.exe / ld.lld.exe / lld-link.exe / wasm-ld.exe        四个 SHA256 完全相同
llvm-ar.exe / llvm-lib.exe / llvm-ranlib.exe             三个 SHA256 完全相同
```

驱动靠 `argv[0]` 分派，所以**那四个是同一个程序**。bin 里
395 MB 的驱动 ＋ 180 MB 的 lld ＋ 24 MB 的 ar，**实际独一份只有 79 + 45 + 8 = 132 MB**。

`chinese++.exe` 与 `clang++.exe` 现在是**硬链接**（共享一份），
但 **zip 不保存硬链接** —— 解压出来就会变成 650 MB。

**所以打包必须"只放独一份 + 安装脚本重建硬链接"**：

```
只放真身：chinese++.exe(79) + lld-link.exe(45) + clangd.exe(45)
          + llvm-ar.exe(8) + llvm-rc.exe(1)                 = 178 MB
安装脚本用 New-Item -ItemType HardLink 建出其余 12 个名字
+ lib\clang\24\include(8 MB)
──────────────────────────────────────────────────────────────
发行包 ≈ 186 MB          而不是 658 MB
```

跨卷或非 NTFS 建不了链接时要**退化成复制**（功能不受影响，只是占地方）。

### 7.3 构建工具不要发

`llvm-tblgen` / `clang-tblgen` / `llvm-min-tblgen` /
`clang-tidy-confusable-chars-gen` / `llvm-lit` —— 那是**构建期**工具，用户不需要。

### 7.4 许可证：**已完成**（2026-09-25）

打包前 `build\Release` 与仓库根目录里 **`LICENSE`/`COPYING`/`NOTICE` 命中 0 个**
—— 这是**法律阻塞项**，不是可选项。已补：

| 文件 | 内容 |
|---|---|
| `licenses\LICENSE.TXT` | LLVM 的 Apache-2.0 with LLVM Exceptions 正文，**与上游逐字节相同**（15141 字节，SHA256 `8d85c1057d742e59…`） |
| `licenses\NOTICE.txt` | 依 Apache-2.0 **§4(b)** 声明「这是修改过的 LLVM」，并说明包内有什么、**没有**分发微软的库 |

**`LICENSE.TXT` 必须逐字节相同**：它是一份法律文本，任何"顺手改得更好读"都会让
附上的许可证不再是那份许可证。所以 `tests\checks\verify_licenses.py` 用 **SHA256 对上游比对**，
而不是查关键词；并检查 `NOTICE.txt` 含 §4(b) 要求的声明。该脚本自带自测，
且做过端到端变异测试（掏空 NOTICE → EXIT=1；还原 → EXIT=0）。

### 7.11 `build_runtimes.ps1` 的两处修复（2026-10-05，都实测）

**① 静态库目标全灭：`CMAKE_AR-NOTFOUND`**（第一次跑到 463/505 就停，**零个 `clang_rt.*` 产物**）
  症状：`cmd /C "... CMAKE_AR-NOTFOUND /nologo /machine:x64 /IGNORE:4221 /out:clang_rt.builtins-x86_64.lib ..."`

  而 **`-DCMAKE_AR=<lib.exe>` 单独不够** —— 日志里的 `-- Performing standalone runtimes build.`
  说明 compiler-rt 是**第二次、嵌套的 cmake configure**，它**不继承**外层的 `CMAKE_AR`
  （实测：外层 cache 已经是我给的那个路径，生成的规则里**仍然是** `CMAKE_AR-NOTFOUND`）。
  修法：**把 `lib.exe` 所在目录放到 PATH 上**（这正是"开发者命令行"提供的东西）。
  机制单独验证过（最小 CMake 工程 + Ninja + clang-cl）：PATH 上有它 ⇒
  `CMAKE_AR:FILEPATH=<…>\lib.exe`；没有 ⇒ `CMAKE_AR-NOTFOUND`。
  ⚠ 已被上一次 configure **烘焙进 `build.ninja`** 的错误值不会自己消失 ⇒ 必须**清掉 `build\_crt_ninja` 重新 configure**
  （这就是为什么第二次、第三次"改了还是报同一个错"）。
  另外脚本现在自己找 `lib.exe`（Visual Studio 各版本的常见根目录，取最新工具集），
  找不到时兜底：把我们自己的 `llvm-ar.exe` 硬链接成 `llvm-lib.exe` 并用它。

**② 产物建出来却不进资源目录**（以前**根本没有这一步**）
  `build_runtimes.ps1` 原来 configure→build→**打印产物**就结束了，而 `make_package.ps1` 要的是
  `<资源目录>\lib\clang\<ver>\lib\windows\` ⇒ 2026-09-26 那 12 个文件是**手工拷的**（"靠人记得"）。
  现在补上这一步：资源目录**不猜**（`chinese++.exe --print-resource-dir` 报，
  实测 `E:\Chinese++\build\Release\lib\clang\24`），拷完**当场判据**：verify.ps1 要求的
  6 个运行库 + 2 个 ignorelist 少一个就 `throw`。
  **③（2026-10-06 补，发布时发现）接口头也要装**：只装运行库不装接口头 ⇒ 用户能链 ASan，
  却不能 `#include <sanitizer/asan_interface.h>`（"实现发了、接口没发"）。
  现在把 `build\_crt_ninja\compiler-rt\include\`（排除 `cmake_install.cmake`）**合并进**
  `<资源目录>\include\`，并自证三个代表头在位 ⇒ 实测 **20 个接口头**（sanitizer 17 / profile 2 / fuzzer 1）。
  **命名例外**：**6** 个旧包里的头**不该在**（本次 `COMPILER_RT_BUILD_ORC/XRAY/MEMPROF=OFF`，
  不发那三个运行时）：`orc_rt\c_api.h`、`xray\*.h`（3 个）、`profile\MemProfData.inc`、
  `sanitizer\memprof_interface.h` —— 所以从旧包同步到发布仓时这 **6** 个删除是**正确的**
  （数字是 `git status` **实读**的；第一版凭印象写成 4 个，漏了 MEMPROF。台账 §18.40 / §18.41）。

### 7.14 §18.48 批1：把 VS 那层「地基」随包发（默认自带，可切回机器上的 VS）

**包内多了什么**（实测）：`lib\stl\` 174 个**开源** MSVC STL 头（7.2 MB，Apache-2.0 WITH LLVM-exception，
每个文件的 SPDX 行就是许可声明）+ `bin\` 10 个 VC++ 运行库 DLL（1.8 MB，app-local 部署）。
⇒ 未压缩 **206 MB / 661 个文件**，zip **82.6 MB**（批1 之前：197 MB / 476 / 80.8 MB）。

**为什么先发这两样**：① 我们的二进制**自己就导入** `MSVCP140.dll` / `VCRUNTIME140.dll` /
`VCRUNTIME140_1.dll`（`dumpbin /dependents` 实测），不随包的话干净机器**连编译器都启动不了**；
② `zhstdlib` 的中文头第 1 行就是 `#include <vector>` ⇒ 没有 STL 头，`#包含 <向量>` 直接编不过。
这两件都属于"能抄的抄"（开源许可 + 微软的 app-local 再发行条款）。

**两种模式（用户可选，自带为默认）**：

| 模式 | 怎么选 | `<驱动名>.cfg` 内容 | `<vector>` 从哪来（`-H` 实测） |
|---|---|---|---|
| `bundled`（默认） | `install.ps1`（不加参数） | 5 条 zhstdlib + 1 条 `lib\stl` = **12 行** | `. …\Chinese++-0.2-win64/lib/stl\vector`（**包内**） |
| `system` | `install.ps1 -Toolchain system` | 只 5 条 zhstdlib = **10 行** | `C:\Program Files\…\MSVC\…\include\vector`（机器上的 VS） |

选择写进 `bin\toolchain.txt`；`verify.ps1` 读它**按模式断言**（bundled 模式必须解析在包内）。
判据：包内自测 **24 项**（比批1 前多 3 项：模式已记录 / 运行库 DLL 在包内 / `<vector>` 来源断言）。

**⚠ 一个踩到的真缺陷（已修）**：包内 `zh_includes.ps1` / `make_zhcfg.ps1` 由 **PowerShell 5.1** 运行，
而 PS 5.1 读**无 BOM** 的文件按 **ANSI 代码页**解码 ⇒ 默认中文 Windows（GBK/936）下汉字目录名变乱码
（实测 `标准库` → `鏍囧噯搴?`，4 个目录名 0/3 对得上真实文件夹），cfg 会指向不存在的目录。
现在：目录名用**码点拼**（源码纯 ASCII），且打包时给非 ASCII 的包内脚本**补 UTF-8 BOM**。

**还没做**（批2/批3）：86 个闭源编译器支撑头手搓等价物、UCRT/Win32 头换 mingw-w64 等价物、
导入库与启动对象自己生成（替掉 `libcmt`/`oldnames`）。⇒ **线上 v0.2 资产保持不动**
（它是批1 之前的包：80.8 MB / 21 项）；地基全部做完后另发新版（v0.3），发布仓那时一起同步。

### 7.15 §18.48 批2：头文件层补齐 —— **不装 VS 也能编 `<窗口>` / `<绘图>`**
