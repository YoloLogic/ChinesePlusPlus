# 预处理指令汉化

> 状态：**已实现**（2026-09-24）
> 表：`LLVM-main\clang\include\clang\Basic\ChineseDirectives.def`（22 条）
> 测试：`tests\13-preprocessor\`（6 项）＋ `tests\checks\verify_chinese_keywords.py` 第 11 节

---

## 一、做了什么

让 `#包含` 与 `#include` 能被识别为**同一条**指令：

```
中文 `#包含`   ─┐
                ├─→  tok::pp_include  →  HandleIncludeDirective
英文 `#include`─┘
```

| 英文 | 中文 | 汉字 | 英文 | 中文 | 汉字 |
|---|---|---|---|---|---|
| `#if` | `#如果` | 2 | `#pragma` | `#编译指示` | 4 |
| `#ifdef` | `#如果已定义` | 5 | `#embed` | `#嵌入` | 2 |
| `#ifndef` | `#如果未定义` | 5 | `#module` | `#模块` | 2 |
| `#elif` | `#否则若` | 3 | `#import` | `#导入` | 2 |
| `#elifdef` | `#否则若已定义` | 6 | `#include_next` | `#包含下一个` | 5 |
| `#elifndef` | `#否则若未定义` | 6 | `#warning` | `#警告` | 2 |
| `#else` | `#否则` | 2 | `#ident` | `#标识` | 2 |
| `#endif` | `#结束如果` | 4 | `#assert` | `#断言` | 2 |
| `#include` | `#包含` | 2 | `#unassert` | `#取消断言` | 4 |
| `#define` | `#定义` | 2 | `#line` | `#行号` | 2 |
| `#undef` | `#取消定义` | 4 | `#error` | `#错误` | 2 |

**有意不收的 6 条**（保持英文）：

| 拼写 | 原因 |
|---|---|
| `__include_macros` | 编译器内部拼写 |
| `__preprocessed_module` | 写进 PCH / 模块文件（.pcm），**动它影响二进制格式兼容** |
| `__preprocessed_import` | 同上 |
| `__public_macro` / `__private_macro` | 同上 |
| `sccs` | 1980 年代 SCCS 遗留，Clang 默认报错 |

## 二、为什么可以**随意混用**（不需要开关）

用户在 2026-09-24 明确要求：

> `#include` `#包含` 按照你的改法用户可以混用吗？我需要可以混合使用且不影响

**可以，而且是结构上保证的，不是靠约定：**

1. 两种拼写都映射到**同一个** `tok::pp_include`。
2. `HandleDirective`（`PPDirectives.cpp:1407`）的分发是
   `switch (II->getPPKeywordID())` —— **只看枚举值，从来不读指令名的拼写**。
3. 所以下面的处理链根本**无法区分**文件里写的是哪一种。

因此**没有开关、没有模式、没有逐文件限制**。也不需要 `-fchinese-directives`
之类的旗标：中文路径只是**多接受**一种拼写，英文路径字节不变。

### 实测

`tests\13-preprocessor\mixed.cpp` 在**同一条条件链**里混用：

```cpp
#if LEVEL == 1
#  定义 PICK 10
#否则若 LEVEL == 2
#  定义 PICK 20
#否则
#  定义 PICK 30
#结束如果
```

### 更强的证据：逐字节相同

`chinese.cpp`（全中文指令）与 `english.cpp`（全英文指令）逻辑相同，
`-E -P` 的产物**逐字节相同**（150 字节）：

```
int from_header(void);

int from_b(void);

int main() {
  return (40 == 40 && 1 == 1 && 1 == 1 && 1 == 1 &&
          7 == 7 && 11 == 11) ? 0 : 1;
}
```

## 三、实现：三处读取者，一张表

新增 `ChineseDirectives.def`，**以英文 PPKEYWORD 名为键**：

```cpp
ZH_DIRECTIVE(include, 包含)
```

展开成 `tok::pp_##EN`，所以**写错英文名编译不过** —— 编译器替我们查拼写。

| 读取者 | 位置 | 作用 |
|---|---|---|
| 指令分发 | `IdentifierTable.cpp` 的 `lookupChineseDirective()` | 非 ASCII 名字 → `tok::pp_*` |
| 跳过路径 | `PPDirectives.cpp` 的 `chineseDirectiveEnglishSpelling()` | 中文拼写**就地换成英文** |
| 依赖扫描 | `DependencyDirectivesScanner.cpp` 的 `.Case(...)` 表 | 见第四节 |

第三处**不能** include 本表（它的 `DirectiveKind` 里没有 `pp_module`），
所以手抄了 13 条 —— 由 `verify_chinese_keywords.py` 第 11 节校核为
「本表 ∩ 扫描器英文表」，两边不会漂移。

## 四、踩到的两个坑（都是"看起来能用"的那种）

### 坑 1：跳过被排除分支的路径**读不到标志位**

`SkipExcludedConditionalBlock()`（`PPDirectives.cpp:544`）为了速度**故意不做
标识符查找**，改用原始字符串比较：

```cpp
if (Directive.starts_with("if"))        // #if / #ifdef / #ifndef
else if (Directive[0] == 'e')           // #endif / #else / #elif
```

中文拼写一条都匹配不上，于是 `#如果 0` 为假时 `#结束如果` 弹不出条件栈，
报 **「条件指令没有终结」**。

**症状极具误导性**：单独一条 `#如果 1 ... #结束如果` 完全正常 ——
因为它走 `HandleDirective` 快路径（读 `getPPKeywordID`），根本不经过这个函数。
只有**条件为假**时才暴露。

修法：不在跳过逻辑里再加一套中文分支（那等于把一台手写状态机复制一遍，
两处必须永远同步），而是把中文拼写**就地换成英文**，
下面所有既有逻辑一个字都不用改。

### 坑 2：依赖扫描器**静默丢依赖**

`DependencyDirectivesScanner.cpp` 也是自有字符串表，而且它的失败语义是反的：

```cpp
if (Kind == pp_none) { skipDirective(Id, First, End); return false; }  // false = 成功
```

头文件写明 `scanSourceForDependencyDirectives` **返回 false 是成功**。
所以漏掉 `#包含` 不是"回退到完整预处理器"，而是**当这条 include 不存在**——
增量编译与 `clang-scan-deps` 会认为头文件没被包含，改了头文件不重编。

### 坑 3（既有的，本次未修）：扫描器的模块门是 ASCII 首字节

`DependencyDirectivesScanner.cpp:970`：

```cpp
if (*First == 'i' || *First == 'e' || *First == 'm' || IsPreprocessedModule)
  return lexModule(First, End);
```

汉字首字节 ≥ 0x80，永远进不去这个分支。也就是说**已经上线的中文模块关键字
`模块` / `导入` 在裸声明形式下是漏的**（`#` 形式不受影响）。
`PPDirectives.cpp` 的跳过路径里也有同类的 ASCII 首字节判断
（`Tok.getRawIdentifier() == "export" || == "module"`、`II->getName()[0] == 'e'`）。

**这是一个独立的既有缺陷，与本次指令汉化不同源**，需要单独处理
（要动 `HandleModuleContextualKeyword` 的交互，风险等级不同）。
本次**记录不修**，因为混进来会让失败原因难以归属。

## 五、一条被推翻的旧结论

`IdentifierTable.cpp` 原文（2026-09-22 写的）：

> 放在这里而不是新增一张 .def 表：标志位已经是唯一数据源，
> 再抄一份拼写就会出现两处需要同步。

**这条对【关键字】成立，对【指令】不成立：**

* 关键字都有标志位（`TokenKey`）；
* `include` / `define` / `if` / `elif` 这些英文**在 `TokenKinds.def` 里没有
  关键字标志位可抄**（它们不是 C++ 关键字）；
* 依赖扫描器**读不到标志位**，只认字符串。

所以指令拼写**必须**自有一张表。本次把原来那 5 行标志位旁路
（`isImportKeyword()` / `isModuleKeyword()`）**替换成统一查表**——
是消除重复，不是增加重复。

⚠ 这正是本项目的复发失败类型：**一条没有理由的规则，看起来就是还没定的规则**。
已记入 `docs\诊断汉化\第三批-待译与术语包.md` 的推翻记录。

## 六、几条容易误解的观察（都实测过）

| 观察 | 结论 |
|---|---|
| `#模块 m;` 报错 | **忠实**。英文 `#module m;` 也报「无效的预处理指令」—— `PPDirectives.cpp:1455` 要求引出名是模块上下文关键字，`#` 形式本来就不合法 |
| `#导入 "x.h"` | **改动前就能用**。`导入` 有 `KEYMODULES` 标志位 → `tok::pp_import` → `HandleImportDirective`。报的是「导入类型库是不受支持的 Microsoft 特性」，与 `#import` 一字不差 |
| `#断言` / `#取消断言` 报错 | **忠实**。`case tok::pp_assert: break;` 是上游未实现（FIXME），英文一样报错 |
| `#否则若` vs `否则` | 是两个**不同**的标识符。汉字是 XID_Continue，词法做最长匹配，`否则若` 不会被切成 `否则` + `若` |
| `如果` / `否则` 既是关键字又是指令名 | **正确**，与英文 `if` / `else` 的双重身份一致。指令名在 `ParsingPreprocessorDirective` 下不做关键字映射 |

## 七、已知不一致（记录，未处理）

有几个**已译诊断**里嵌着英文指令拼写：

```
warning: 主文件中出现 #pragma once [-Wpragma-once-outside-header]
warning: 在主源文件中使用 #include_next；将从包含路径的开头开始搜索 [-Winclude-next-outside-header]
```

现在中文拼写也是合法写法了，这几条读起来就不一致了。**没有改**，因为：

* 诊断里引用的是**规范英文拼写**，它在文档、上游错误信息、搜索引擎里都是通用形式；
* 改成 `#编译指示` 会让英文模式下的用户看到中文，反而更差；
* 编译器里没有 `getDirectiveSpelling()` 这种"对外正式拼写"的概念
  （关键字有，见 `TokenKinds.cpp`），所以没有现成机制可用。

**这是一个需要决策的问题，不是可以顺手改的问题。** 记在这里等着定。

## 八、怎么验证

```powershell
powershell -File E:\Chinese++\tests\13-preprocessor\check.ps1   # 6 项
python E:\Chinese++\tests\checks\verify_chinese_keywords.py     # 第 11 节
python E:\Chinese++\tests\13-preprocessor\sweep.py              # 22 条逐条对拍
powershell -File E:\Chinese++\tests\run_all.ps1
```

`verify_chinese_keywords.py` 第 11 节校核（每条**自带自测**）：

1. 22 条英文名都真实存在于 `TokenKinds.def` 的 `PPKEYWORD`
2. 英文名与译名各自互不重复
3. 汉字数 2–6
4. **字节数 < 20** —— `PPDirectives.cpp` 里有 `char DirectiveBuf[20]`，
   超过就会被跳过逻辑**静默忽略**。这条安全边界是由 2–6 汉字定则推出来的，
   显式钉住，将来有人加 7 字译名会先在脚本里失败
5. 与关键字表重名时，**英文名必须相同**（`如果`↔if、`否则`↔else、
   `模块`↔module、`导入`↔import 可以；把 `#否则` 指给 endif 会报错）
6. 扫描器那 13 条中文 `.Case()` == 本表 ∩ 扫描器英文表
7. `clang/CMakeLists.txt` 仍用 `PATTERN "*.def"` 通配安装

`sweep.py` 的设计要点：**不查"退出码为 0"，而是查"中英行为一致"**。
因为 `#断言` / `#模块` 在英文下本来就是错的，要求退出码 0 就得手工开白名单；
对照英文运行则一条白名单都不需要。但只有一致性还不够（两边一样坏也会通过），
所以每条还带**期望退出码**，并且条件分支用 `static_assert` 断言**走的是哪个分支** ——
第一版扫描只查退出码，因此对第四节那个"跳过路径"的 bug **完全失明**
（`#如果 0` 跳过时找不到 `#否则若`，会一路跑到英文 `#endif`，退出码仍是 0）。
