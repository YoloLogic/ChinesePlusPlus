### P-01 `对齐`（alignas）在属性位置被静默忽略

**判据**：`对齐(N)` 与 `alignas(N)` 必须**同义**。同一份源码，只把 `alignas` 换成 `对齐`，
对 `对齐值(甲)` 的结果不得有任何变化。

**复现命令**（两条只差一个词）：

```powershell
cd E:\Chinese++
'结构 对齐(16) 甲 { 整数 值; };' + "`n" + '整数 主函数(){ 返回 (整数)(对齐值(甲)==16)-1; }' |
  Set-Content -Encoding utf8 build\_review_own\da_jiancha\手工\A_中文.cpp
'struct alignas(16) 甲 { 整数 值; };' + "`n" + '整数 主函数(){ 返回 (整数)(对齐值(甲)==16)-1; }' |
  Set-Content -Encoding utf8 build\_review_own\da_jiancha\手工\B_英文.cpp
build\Release\bin\chinese++.exe -std=c++20 -fsyntax-only build\_review_own\da_jiancha\手工\A_中文.cpp
build\Release\bin\chinese++.exe -std=c++20 -fsyntax-only build\_review_own\da_jiancha\手工\B_英文.cpp
```

**原始输出**（2026-10-03 实测）：

```
=== A_中文 ===
A_中文.cpp:1:8: warning: 未知的属性（属性名） '对齐' 被忽略 [-Wunknown-attributes]
    1 | 结构 对齐(16) 甲 { 整数 值; };
      |      ^~~~
生成了 1 个警告。        ← 退出码 0：编译"成功"，但对齐没有生效

=== B_英文 ===
（无输出，退出码 0）      ← 对齐生效
```

**影响面（已逐位置实测，全部失效）**：

| 写法 | 中文 | 英文 |
|---|---|---|
| `结构 对齐(16) 甲 {...}`（class-key 之后） | ✗ 警告+忽略 | ✓ |
| `对齐(16) 整数 全局;` | ✗ 警告+忽略 | ✓ |
| `结构 甲 { 对齐(16) 整数 值; };`（成员） | ✗ 警告+忽略 | ✓ |
| 函数内 `对齐(16) 整数 局部;` | ✗ 警告+忽略 | ✓ |
| `对齐(16) 结构 甲 {...}`（写在 class-key **之前**） | 报错"属性放错了位置" | 报错"属性放错了位置"（**一致，不算问题**） |

⇒ 也就是**中英之间没有任何一个位置是对称的**：凡英文能用 `alignas` 的地方，中文 `对齐` 全部失效；
唯一"一致"的位置是双方**都**不合法的地方。

**根因**（`llvm-main\clang\include\clang\Basic\AttributeCommonInfo.h:163-168`）：

```cpp
  AttributeCommonInfo(const IdentifierInfo *AttrName, AttributeScopeInfo Scope,
                      SourceRange AttrRange, Form FormUsed)
      : AttributeCommonInfo(
            AttrName, Scope, AttrRange,
            getParsedKind(AttrName, Scope.getName(), FormUsed.getSyntax()),  // ← 按【拼写字符串】查属性表
            FormUsed) {}
```

`getParsedKind` → `AttributeList::getKind("", Name->getName(), AS_Keyword)`。
英文 `"alignas"` 在表里 → `AT_Aligned`；中文 `"对齐"` 不在表里 → `AT_Unknown`
→ Sema 报 `warn_unknown_attribute_ignored` → 属性被丢弃。

**这是"整类"缺陷，不是孤例**：凡是 clang 里**按拼写字符串**而不是按 **token 种类**查关键字的地方，
中文别名都会**静默失效**。本次把这一类扫了一遍，找到的同类点：

| 位置 | 按拼写比较的东西 | 后果 | 是否已登记 |
|---|---|---|---|
| `AttributeCommonInfo.h` `getParsedKind` | 属性名 `"alignas"` | **P-01**（静默忽略） | ✅ |
| `Lex\PPDirectives.cpp:207` | `"override"` / `"final"` | **P-03**（少一个警告） | ✅ |
| 其余（`kw_alignas`、`isCXX11VirtSpecifier`、`TokenKinds.cpp`、`IdentifierTable.cpp`） | —— | 都是**按 token / 按 IdentifierInfo 指针**，中文与英文等价 | 无需修 |

> 📌 词法层已经证明中英**token 完全相同**（`-Xclang -dump-tokens` 两边都是 `alignas`），
> 所以问题一定在"之后再按字符串查一次表"的位置 —— 这条排查方法值得留给后来者。

**修复路径（候选，**尚未实施**）**：
在 `getParsedKind` 查表之前，为**中文别名拼写**做一次"规范名归一"：
把 `对齐` → `alignas`（表来自 `ChineseKeywords.def`，与关键字表同源、不新增第二份拼写清单），
**但保留 `AttrName` 仍是中文 IdentifierInfo**，这样诊断里显示的仍是中文（符合"中文是对外正式拼写"）。

**回归判据（修完必须变成闸门里的一条）**：
`对齐(16) 甲` 与 `alignas(16) 甲` 两条 TU 的 `对齐值(甲)` 必须都等于 16，
且**编译时不得出现 `-Wunknown-attributes`**（不能只看退出码 —— 这条 bug 正是"退出码 0 也算通过"造成的）。

**✅ 修复记录（2026-10-03，已实测）**：

### P-02 诊断打印的**列号是字节偏移**（插入符本身是对的）

> 精确测量（见下）证明**插入符是对的**（按显示宽度，汉字算 2 格）。
> 错的只有**打印出来的 `文件:行:列` 里的列号**。严重度由「高」改为「**中**」。
> 记在这里而不是悄悄改掉：项目的纪律是"宁可漏报不可误报"，误报也必须留下痕迹。

| 目标记号的**字符序**（1 基） | 37 |
| 目标记号的**显示列**（1 基，汉字 2 格） | 59 |
| **插入符实际落点** | 0 基第 **58** 格 = 显示列第 **59** 格 ✅ **与目标记号完全重合** |
| 插入符的 `~` 长度 | `^~~~~~~~~~` = 10 格 = 5 个汉字 × 2 ✅ **宽度也对** |

⇒ **插入符完全正确**；只有 `文件:行:列` 里的 **81** 是错的（既不是显示列 59，也不是字符序 37）。
⇒ 英文行三者在 ASCII 上重合，所以英文源码看不出问题 —— 这正是它一直没被发现的原因。

**影响面（说清边界）**：

1. **终端里看报错：不受影响** —— 插入符画在对的位置，用户照着插入符就能找到。
2. **按 `文件:行:列` 定位的工具：会偏**。`81` 既不是显示列（59）也不是编辑器要的字符序（37）：
   VS Code 的 `$gcc` 之类**问题匹配器**会把光标放到错误位置右边 44 列（81 − 37）的地方。
   本项目 `docs\打包\一键配置-VSCode.md` 主推 VS Code 集成 ⇒ 这一条要修。
3. **clangd 不受影响**（它走 LSP，用 SourceManager 的**偏移**自己换算 UTF-16 列）。
4. **发作频率**：只要该行有汉字（本项目绝大多数行），列号就一定偏。

**根因（是上游行为，不是我们改坏的）**：

- 我们的编译器是 clang **24.0.0git**；对照的上游是 VS 自带的 clang **19.1.5**。
- `TextDiagnostic.cpp` **没有**中文相关改动（`git log` 对该文件无输出）。
- 这一版 clang 内部其实**同时有两套列口径**：`TextDiagnostic.cpp` 里定义了强类型
  `Bytes` 与 `Columns`，插入符走 `SourceColumnMap::byteToContainingColumn()`
  （**字节 → 显示列**，所以插入符是对的）；而打印 `文件:行:列` 的地方仍直接取
  `SourceManager::getColumnNumber()`，那个 API 返回的是**字节**。
- 这一版**没有** `-fdiagnostics-column-unit=display|byte` 选项
  （实测 `error: 未知的实参`，`DiagnosticOptions.h` 里也搜不到）——
  上游是后来才加这个开关的（默认 `display`）。

**修复路径（候选，**尚未实施**，且**要先定口径**）**：

|---|---|---|---|

⚠ 这是**口径决策，不是纯技术选择** ⇒ **已拍板为方案 C**（见第七节 D-01）。
无论选哪个，**回归判据**都要同时钉住两件事：① 打印的列号 == 选定的口径；② 插入符仍落在该记号正下方。

### P-03 `-Wkeyword-macro` 对中文 `重写`/`最终` 不报

**判据**：`#定义 重写 1` 与 `#define override 1` 必须给出**同一类**警告。

**复现命令**：

```powershell
cd E:\Chinese++
build\Release\bin\chinese++.exe -std=c++20 -Wkeyword-macro -fsyntax-only <文件>
```

**原始输出**（2026-10-03 实测）：

```
=== #define override 1 ===
W1.cpp:1:9: warning: 关键字被宏定义隐藏 [-Wkeyword-macro]     ← 有
=== #定义 重写 1 ===
（无输出）                                                  ← 没有 ✗
=== #define final 1 ===
W3.cpp:1:9: warning: 关键字被宏定义隐藏 [-Wkeyword-macro]     ← 有
=== #定义 最终 1 ===
（无输出）                                                  ← 没有 ✗
```

**根因**（`llvm-main\clang\lib\Lex\PPDirectives.cpp:200-212`）：

```cpp
static MacroDiag shouldWarnOnMacroDef(Preprocessor &PP, IdentifierInfo *II) {
  ...
  if (II->isKeyword(Lang)) return MD_KeywordDef;      // 中文普通关键字走这里 ✓
  if (Lang.CPlusPlus11 && (Text == "override" || Text == "final"))   // ← 按拼写比较
    return MD_KeywordDef;
```

`重写`/`最终` 是**上下文关键字**（在 clang 里是普通标识符 + 特殊 IdentifierInfo），
所以 `isKeyword()` 为假，只能靠第二行的**字符串比较** —— 中文拼不出来，于是少一个警告。

**影响面**：只影响一个警告，**不影响正确性**（宏照样能定义、`重写` 照样失效 —— 与英文一致）。
之所以仍然登记：它与 P-01 **是同一个病根**，修 P-01 时应当一并修掉，否则同一类缺陷会再冒出来。

**修复路径（候选）**：把 `Text == "override" || Text == "final"` 换成
"该 IdentifierInfo 是否为 `重写`/`最终` 之一"（`isCXX11VirtSpecifier` 用的那套指针比较）。

**✅ 修复记录（2026-10-03，已实测）**：

| 项 | 内容 |
|---|---|
| 改的文件 | `llvm-main\clang\lib\Lex\PPDirectives.cpp`（**只此一个**） |
| 改法 | 新增 `isChineseVirtSpecifierSpelling(II)`：用 **`ChineseKeywords.def` 的 `ZH_VIRT_SPECIFIER` 宏族**逐个 `II->isStr(#ZH)` 比较 —— 与 `ParseDeclCXX.cpp` 的 `isCXX11VirtSpecifier()` **同一套做法、同一个数据源**。关键是 `#ZH`（字符串化）：.cpp 里**不出现汉字字面量**，所以 `tools\zh_to_en.py`（无锁定证明工具）只解析那个 .def 就够 |
| 判据 | 中文拼写与英文拼写走**同一条规则**：同一个 `Lang.CPlusPlus11` 前提、同一个警告 |

### P-05 关键字当标识符时，诊断不点明"这是关键字"

**判据**：`整数 如果 = 1;` 这种写法，消息必须让初学者看懂"`如果` 是关键字，不能当名字"。

**原始输出**（实测）：

```
D01 `整数 如果 = 1;`      → error: 缺少（种类） 非限定标识符
D02 `整数 返回() {…}`     → error: 缺少（种类） 非限定标识符
D05 `整数 取(整数 常量)`  → error: 缺少 表达式
D07 `模板 <类型名 类型名>`  → error: 缺少（符号） identifier
D08 `枚举 甲 { 默认 = 1 }` → error: 缺少（符号） identifier
```

**根因**：上游 clang 对"关键字出现在需要标识符的位置"就只有 `expected unqualified-id` 这一句
（`err_expected_unqualified_id` / `err_expected`）。**英文用户很少踩**（没人会把 `if` 当变量名），
**中文用户天天会踩** —— 汉语词与标识符在视觉上完全没有区别，`如果` 看起来就是个普通词。

**影响面**：这是**汉语使用者的第一条报错**。它现在既不说"这是关键字"，
也受 P-02 影响把列号报到字节位置 ⇒ 初学者大概率看不懂。

**修复路径（候选）**：在 `Sema`/`Parser` 产生 `expected unqualified-id` 的位置，
若当前 token 是**中文关键字**，改发一条新诊断：「`%0` 是中文关键字，不能用作标识符；
要当名字请换一个词」。这不改变英文行为（英文 token 走的还是原诊断）。

**回归判据**：对 `ChineseKeywords.def` 里 **每一条**关键字各写一个"当变量名"探针，
要求输出的正文里出现该关键字的中文拼写 + "关键字"字样。

**踩到的两个坑（都写进代码注释了，免得后人重踩）**：

1. **tablegen 拒绝诊断正文以大写字母开头**（`Chinese keyword…` 被拒：`G4C611B0E`）⇒ 改成 `the Chinese keyword…`。
2. **`Parser.h` 里不能内联引用 `diag::` 名字** —— clang 的诊断 ID 按类别拆成

   内联会在没包含该头的 TU 里报"不是 `clang::diag` 的成员"。

### P-07 UTF-16 源码被报成"编译器崩溃"

**原始输出**：

```
fatal error: 在（名字） '…\U16.cpp' 中检测到（名字） UTF-16 (LE) 字节序标记，但不支持该编码
PLEASE submit a bug report to https://github.com/llvm/llvm-project/issues/ and include the crash backtrace and dumped files.
Stack dump:
0.	Program arguments: …
```

**上游对照**：VS 自带 clang 19.1.5 只打前两行（fatal error + `1 error generated.`），**退出码 1**，没有崩溃横幅。
我们这边（clang 24）多出"PLEASE submit a bug report"+堆栈。
**无法进一步区分**是"上游 19→24 的变化"还是"我们的改动"（`llvm-main` 不是 git 仓库、没有基线可比）。

**⚠ 重报（2026-10-03 第二轮，严重度由"低"改成"中"）**：这不是"横幅难看"，是**真崩溃** ——
输出里有 `Exception Code: 0xC0000005`（访问违例）。最初的登记把它读成"误报成崩溃"，**低估了**。

**定位过程（把三个被证伪的假设也留下，免得下次重走）**：

| 判别实验 | 结果 | 说明 |
|---|---|---|
| `-fdiagnostics-column-unit=byte` / `-fno-chinese-diagnostics` / `-fno-caret-diagnostics` / `-fdiagnostics-show-location=never` | **四种都照崩** | ⇒ 与诊断正文/插入符/列号（含我新加的 `convertDiagnosticColumn`）**全都无关** |
| **UTF-16 当头文件**（主文件合法） | 干净报错、**不崩** | ⇒ 崩的只有"**主文件**读不出来"这一条路 |
| `-cc1` 直接跑 | 崩 | ⇒ 崩在 **cc1**，不在驱动 |
| `-E` / `-fsyntax-only` / `-S` / `-c` | **四种都崩** | ⇒ 崩点**不在解析循环里**（`-E` 根本不经过 `ParseAST`） |
| 上游 clang 19.1.5 同一文件 | 干净报错、退出码 1 | ⇒ 19→24 之间（或我们的改动）引入了它 |

**三个被证伪的假设（都动过手、都无效，已全部撤回）**：
1. 「`CompilerInstance::InitializeSourceManager` 该检查致命错误」—— **无效**：
   主文件的缓冲区是**懒加载**的（`SourceManager::createFileID` 只在命名管道时立刻读），
   那一刻 `hasFatalErrorOccurred()` 必然为假。
2. 「`ParseAST` 该在进入主文件后检查 `hasFatalErrorOccurred()`」—— **无效**：
   `Diagnostic.cpp:655-661` 写明了这个标志**要见到第二条非 note 诊断**才置位
   （好让 note 能挂在致命错误后面），而这条路径只发出一条致命的 BOM 诊断
   （第二条 `err_pp_error_opening_file` 被静默）⇒ 判据恒为假。
3. 「`ParseAST` 该检查主文件的缓冲区还在不在」—— **无效**：见上表最后一行，
   `-E` 根本不经过 `ParseAST`，崩点在**更早**。

**现在的结论（留给下一轮）**：
- 崩点在 `Preprocessor::EnterMainSourceFile()` 内部或其紧邻处（所有动作都调它，所以 `-E` 也崩）；
- `EnterSourceFile` 在失败时**返回 true**，而 `EnterMainSourceFile:596` **忽略了返回值**
  （`PPLexerChange.cpp:80-85` 的失败分支是干净的：只发诊断 + `return true`）⇒
  这条"静默失败"是最大嫌疑，但**尚未证明**；
- 下一步该做的是**符号化**那 13 帧（本次没有 `llvm-symbolizer.exe`、也没有 `.pdb`，
  所以只能看地址）。可行路径：① 构建 `llvm-symbolizer` / 让 MSVC 出 `.pdb`；
  ② 或按 `EnterMainSourceFile` 的每一步插桩（`errs()` 打点）二分定位。

**为什么仍登记、且不再撤回**：把**用户输入错误**渲染成**编译器崩溃**，无论谁造成都该修；
UTF-16 在 Windows 上是 VS「另存为」的常见选项，真实用户会撞到。

**✅ 修复记录（2026-10-03 第三轮，插桩一击命中）**：

**插桩（这是本次唯一真正有效的手段）**：在上次"三个假设全错"之后，不再猜，直接在
`Preprocessor::EnterMainSourceFile` 与 `EnterSourceFile` 的每一步打 `[ZHTRACE]` 到 stderr，
重建后跑一次 —— 最后一行直接指出崩点：

```
[ZHTRACE] EnterSourceFile(主文件) 返回=1 CurLexer=0x0
[ZHTRACE] markIncluded 之后
Exception Code: 0xC0000005          ← 崩在下一句
```

**根因（两处，都改了）**：

1. **`ContentCache::getBufferOrNone` 的 BOM 分支只 `return std::nullopt`**
   （`SourceManager.cpp:189`）。同文件里"打不开文件"那条路是**缓存一个空缓冲区**交出去
   （原注释："we can't really deal with this situation, just create an empty buffer"），
   只有 BOM 这条一直裸返回 `nullopt` ⇒ 失败**粘住**并往上传。
2. **`Preprocessor::EnterMainSourceFile:596` 忽略了 `EnterSourceFile` 的返回值**。
   于是 `CurLexer` 一直是 `nullptr`，而紧接着 `-std=c++20`（**默认开模块**）那段会执行
   `CurLexer->peekNextPPToken()` ⇒ **空指针解引用** ✓；
   `-E` 那条路更直接：`Preprocessor::Lex` 用 `CLK_Lexer` 解引用空的 `CurLexer`。

**改法**：① BOM 分支照"打不开文件"那条的样子**缓存一个空缓冲区**（`IsBufferInvalid = false`）
⇒ 调用方拿到的是"一个空的源文件"，词法分析立刻 EOF，各动作干净收场，
而**致命诊断已经报过**、退出码仍是 1；② 仍然在 `EnterMainSourceFile` 里**看返回值**
（失败就提前返回）—— 这次改动之后它正常情况不会触发，留着是因为"忽略返回值"正是这个崩溃的根因。

**验证**：`-fsyntax-only` / `-E` / `-S` / `-c` **四种模式全部不再崩**，
各报 **1 条**致命诊断、退出码 1（与上游 19.1.5 的结果一致）；
UTF-16 **头文件**仍干净；合法的 UTF-8 with BOM 照常编过并运行；zhstdlib 用例不受影响。
判据已并入第 21 道守卫（`tools\check_zhdiag_parity.ps1` 第 ④ 节，含"崩溃痕迹"判断的自测）。

> ⚠ 这一节的教训值得单独记：**三个"看起来很有道理"的假设（编译器初始化、ParseAST 两处）
> 全是错的，各自还花了一次重建**。真正定位靠的是**插桩二分**。下次遇到崩溃类问题，
> 直接插桩，不要先改代码猜。

### P-09 诊断里的**类型名**仍是英文（TypePrinter 面）

**来源**：修 P-04 时从同一批证据里拆出来的 —— P-04 修完，42 条探针里剩下 4 处英文残留，

D29 无法初始化 变量 ，其类型为 'int *'，而 右值 的类型为 'int'

（实参是类型对象，不是字符串）。

而 P-09 问的是"**类型**要不要也汉化"。后者影响面大得多（`-ast-print`、模板实例化诊断、
所有类型不匹配的报错），必须单独拍板（见第七节 D-04）。

**影响面（可机器数）**：本次 42 条探针里 4 处；真实项目里的比例未测。
**如果决定做**，判据可以复用第 18 道守卫：把类型名从"已知未修"里挪出来，命中数必须为 0。

**已知未修的登记位置**：`tools\check_zhdiag_leak.ps1` 的 `$已知未修` 表（命中不判失败、但会打印；
修好后守卫会报"条目已消失"，逼着把登记删掉）。

**✅ 修复记录（2026-10-04，决策 D-04 = 统一汉语）**：

**口径先定清楚**（这一条我一开始说得含糊，用户追问了两轮）：

| 东西 | 改之前 | 改之后 |
|---|---|---|
| **库类型名**（`标准::向量`） | **本来就是中文** —— 那是别名层的名字，打印的就是源码里的拼写 | 不变 |

### P-13 诊断里打印的**表达式**仍夹英文关键字（StmtPrinter 那一面）

**来源**：修 P-09 时**测试套件**先撞出来的 —— `静态断言失败，因为不满足要求（表达式）
'sizeof(整数) > 99'`：类型已经中文、运算符还是英文，**一条消息里两种口径**。
它是**另一个打印器**（`StmtPrinter`），与 P-09 的 TypePrinter 是两条不同的路
—— 与 P-07 同一条教训：**判据要覆盖到"另一个入口"**。

**✅ 修复记录（2026-10-04，§18.9）**：

**一句话**：表达式打印器里**所有**"中文关键字表里有译名的"关键字，都改成跟**同一个开关**走
（`-fno-chinese-diagnostics` 一起回退英文）。拼写**一律取自 `ChineseKeywords.def`**
（经 `tok::getKeywordSpelling()`）—— 与关键字表同源，**不在打印器里维护第二份清单**；
表里没有译名的（`__addrspace_cast`、`__uuidof`、`__builtin_bit_cast`…）**自动回退英文**，
不需要枚举。

为此在 `AST/PrettyPrinter.h` 加了**一个** inline 帮手（所有打印器共用）：

```cpp
inline StringRef getPrintedKeywordSpelling(const PrintingPolicy &Policy,
                                          tok::TokenKind K, StringRef English);
```

`English` 就是**原来写死的那个字面量** ⇒ **英文模式下逐字节等于改动前**。
同时把 P-09 加的 `PrintingPolicy::ChineseTypeNames` 改名成 `ChineseSpelling`
—— 它现在管的不只是类型名，还有限定符与表达式关键字，**名字要说得清**。

| 打印路 | 修了什么 | 实测（英文源码 → 中文输出） |
|---|---|---|
| `StmtPrinter::VisitCXXNamedCastExpr` | 四种具名转换 | `static_cast<int>(1.5)` → `静态转换<整数>(1.5)` |
| `StmtPrinter` 布尔/空指针/自身/抛出 | `true`/`false`/`nullptr`/`this`/`throw` | `true == false` → `真值 == 假值` |
| `StmtPrinter` `new`/`delete`/`typeid`/`sizeof...` | 新建 / 删除 / 类型标识 / 大小... | `new A` → `新建 A` |
| `StmtPrinter` 协程三兄弟 | `co_await`/`co_yield`/`co_return` | `co_await x` → `协程等待 x` |
| `APValue` / `ASTDiagnostic` / `TemplateBase` | **诊断专用**的"值 / 模板实参"打印 —— `true`/`false`/`nullptr` 在那几条路里是**另写的字面量**，P-09 那条路管不到 | 布尔模板实参 diff → `真值`/`假值` |
| `ASTConsumers`（`-ast-print` 的 Print 分支） | `-ast-print` 也跟同一个开关 | 见下 |

**顺带定了一条口径（D-08）**：`-ast-print`（`OutputKind == Print`）跟着走中文；
`-ast-dump`（TextNodeDumper / JSONNodeDumper）**故意不动** —— 那是调试 / 机器可读格式，
JSON 的**键名**与记号名必须保持英文，翻了会把读它的工具链弄坏。

**判据换成"正面探针"（第 22 道守卫 `tools\check_zhexpr.ps1`）** —— 这是本条最值得记的一步：
第 18 道守卫靠"26 个词的**全局黑名单扫正文**"，而这一类**不能进那张黑名单**：
同一个词可能正是"**代码里要照写的名字**"（`operator new`、`__super`、`'std::size_t'`），
一扫就误报。⇒ 改成**拿英文源码去编、断言打出中文**：

| 判据 | 内容 |
|---|---|
| **① 诊断探针** | `static_assert(sizeof(int) > 99)` 等 4 条，正文里必须出现 `大小(整数)` / `静态转换<整数>(1.5)` / `真值 == 假值` / `空指针 != 空指针`，且**不许**出现英文拼写 |

### §18.15 结案：§18.9 登记的两处「拿不到 `PrintingPolicy` 的打印 API」—— **都不需要改**（有证据）

长期目标里点名要"处理"这两处。查完的结论是：**两处都不是欠账**，各有各的理由，
而且它们依赖的机制现在**有机器判据**了。

| API | 唯一的调用者 / 现状 | 结论 |
|---|---|---|
| `TemplateArgument::getKindName()` | **只有一个调用者**：`SemaConcept.cpp:3091`，在**约束满足调试树**里（`WriteOccurenceList` / `AddChild`，`-fdump` 那一类） | **按 D-08 保持英文** —— 那是调试 / 机器可读输出，与 `-ast-dump` 同一条口径 |
| `DiagTemplateArg()` | **没有树内调用者**（把整个 `clang/lib` 里的 `<< Arg;` / `<< *Arg;` 都看过：全是 disassembler、驱动实参、属性实参，**没有一个是 `TemplateArgument`**） | **字符串那部分已经被渲染器兜住**（见下）；只有 `Pack` 分支「用默认 `LangOptions` 建策略打印类型」会漏，而它**够不着**（没有调用者） |

**为什么说"字符串那部分已经被兜住"（这是本轮的关键发现）**：
`DiagTemplateArg` 输出的 `"nullptr"`、`"(null template argument)"` 这类**字符串实参**，
渲染时会经过 `Diagnostic.cpp` 的 `getChineseKeywordName()`（P-04 修的那条路）——
**长得像英文关键字的字符串实参一律换成中文拼写**。同一条路也解释了另一个现象：
`SemaAvailability.cpp:501` 把 `TagDecl::getKindName()`（返回 `"struct"`）流进诊断，
渲染出来是 `给（名字） 匿名 结构 加上可用性属性以使这条警告静默` —— **本来就是中文**
（我一开始把它当成"新发现的中文消息夹英文"，实测被这条机制打回来了）。

**因此新增一条探针（第 18 道守卫 **T05**）**，直接把这条机制钉死：
必须出现 `匿名 结构 加上可用性属性`，不许出现 `anonymous struct`。
触发条件**这三条都是踩出来的**：① 要 ObjC++；② 要 **Apple 目标**
（`--target=x86_64-apple-macosx10.15`）—— Windows 目标下 availability 属性被忽略；
③ 必须是**匿名 TagDecl 的字段类型**用到那个被标注的类型
（写成"成员函数里调用一个被标注的函数"不行 —— `findEnclosingDeclToAnnotate()`
会先返回那个函数，走的是另一支）。

⇒ 两处 API 的登记**就此结案**：一处按 D-08 保持英文（证据 = 唯一调用者在调试路径），
一处无需改（证据 = 无树内调用者 + 字符串部分被渲染器兜住，且有 T05 探针钉着）。
