## 三、查出来的东西

### 1. 两个**护栏缺口**（都已补上）

1. **`ZH_CONTEXTUAL_KEYWORD` 此前没有任何机器检查**：py 校验器只在 `ZH_KEYWORD`/`ZH_VIRT_SPECIFIER`/`ZH_OPERATOR_KEYWORD` 三族里查（它自己打印"99 条"）。⇒ 新脚本 A 相把第 4 族也查了：英文名存在性、`SETTER` 必须是 `IdentifierInfo` 的真方法（`setKeywordImport`/`setModuleKeyword`）、中文名必须与 `ZH_KEYWORD` 那行**逐字一致**。
2. **25 条关键字在 `tests\`/`examples\` 里一次都没出现过**（= 登记了没人用 = 无护栏）：
   `汇编 字符8位 字符16位 字符32位 协程等待 协程返回 协程产出 常量转换 立即求值 外部 单精度 跳转 长型 可变 受保护 寄存器 受限 短型 有符号 线程局部 取类型 取无修饰类型 共用体 易变 宽字符`
   ⇒ D 相的探针表把它们**全部**真编真跑了一遍（含 `c11`/`c23`/`c++14` 三种模式的适用性判定）。

### 2. 三条**使用规则**（本次实测撞出来，文档里没有或不清楚）

1. **中文关键字与标识符之间必须留空格**：
   `并非假值` 会被 maximal-munch 切成**一个标识符** `并非假值`，报"使用了未声明的标识符（名字） '并非假值'" ✗
   ⇒ 必须写 `并非 假值`。英文同理（`nottrue` 也不是两个词）。**凡文档/示例里贴中文关键字，都要检查空格**。
2. **是否生效由语言模式决定 —— 判据必须跟着 `.def` 的 FLAGS 走**：
   `受限`(restrict) 只在 **C99+ 的 C 模式**是关键字；`取类型`/`取无修饰类型`(typeof/typeof_unqual) 只在 **C23**；
   `寄存器`(register) 自 **C++17 起被移除**（中文与英文**都**报错，行为一致 ✓，探针改在 `c++14` 下跑）。
   ⚠ 我第一版没看 FLAGS，直接在 `-std=c++20` 下判，把这三条"设计如此"误判成 bug ✗ —— **判据错 ≠ 表错**。
3. **运算符替代拼写的"英文原名"不是 token 名**：
   源码里能写的是 `and`/`or`/`not`/`xor`/`bitand`/`bitor`/`compl`/`and_eq`/`or_eq`/`xor_eq`/`not_eq`
   —— 也就是 `TokenKinds.def` 里 `CXX_KEYWORD_OPERATOR(and, ampamp)` 的**第一个**字段，**不是** `ampamp`。

## 四、工具自己的三个坑（都写进了脚本注释，因为它们是"假通过"的典型）

1. **`& $exe -std=$m …` 在 PowerShell 里不展开 `$m`** ⇒ 每一次探针都"编译失败" ⇒
   真关键字"全部被拒绝"变成**假通过** ✗。现在 C 相带**自测**：`如果` 必须被拒、`这不是关键字` 必须放行；
   **自测不过时，后面的"通过"一律不算数**（纪律：跑 0 条的通过不是通过）。
2. **双引号字符串里的 `@(...)` 不展开**（PowerShell 只展开 `$变量`/`$(子表达式)`）⇒ 会把字面量 `@(` 传给 clang。
3. **`$tk` 作用域**：TokenKinds.def 的正文原先只在 A 相块里读 ⇒ 只跑 `-Only D` 时它是空的，
   运算符的英文拼写取不到 ⇒ 11 条假失败。
