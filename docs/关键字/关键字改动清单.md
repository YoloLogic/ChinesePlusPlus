## 一、怎么重新构建

**先关掉 VS Code / CLion / 小熊猫**（它们开着的 clangd 进程会占住 `clangd.exe`，导致重链失败），然后：

```powershell
powershell -File E:\Chinese++\tools\rebuild_clang.ps1
```

- 只重编受影响的编译单元 + 重链，**不重编 LLVM 基础库**
  - 只改 `ChineseKeywords.def`（3 个 TU 重编）→ 实测约 **1–3 分钟**
  - 改 `Parser.h` 这种被广泛包含的头 → **15–25 分钟**
- 脚本自带：按提交内存自适应并发（`/p:CL_MPCount=1`，避免 MSBuild 内存打爆）、
  失败自动降档重试、**判定为代码错误时立刻停止重试**、日志落在
  `build\_clangd_build\rebuild_*.log`
- 脚本末尾会**重建 `chinese++.exe` 的硬链接**——链接器重写 `clang++.exe` 时
  会把硬链接断开，不重建的话 `chinese++.exe` 会永远停在旧二进制上（见 §九）

## 四、三个设计决定（已按此实现）

### 1. `override` / `final` 只能"增加"，**不能替换英文**

它们在 C++ 里**不是关键字**，而是"有特殊含义的标识符"——
`整数 final = 1;` 是**合法**的。如果替换掉英文拼写，会破坏大量现有代码。

这与那 86 个保留字有本质区别：保留字不可能是标识符，所以中英才可以完全等价。

### 2. 运算符替代拼写是**真关键字**——代价要认

`并且` / `或者` / `并非` 等一旦加入，这些词**就不能再当标识符**了
（`整数 并且 = 1;` 会报错）。这无法避免：`and` / `or` 在 C++ 里本身就是关键字。

译名一律取两字以上，正是为了尽量少与用户标识符冲突。

### 3. 诊断里打印中文

`virtual` / `override` / `final` 的诊断信息会显示中文名（与 86 个关键字一致——
中文是"官方拼写"）。副作用：**英文源码**报错时也显示中文。

---

## 五、特意**没有**做的

**没让运算符的中文进入"正式拼写"**：`getKeywordSpelling(tok::ampamp)` 仍返回空，
所以诊断和 AST 打印照旧显示 `&&`、`||`、`!` 这些**符号**。
理由：运算符就该显示符号，把 `并且` 当成 `&&` 的正式拼写反而奇怪。

## 六、编译后怎么验证

写一个 `测试.cpp`：

```cpp
#include <cstdio>

类型 基类 {
公开:
    动态绑定 空型 打招呼() { std::printf("基类\n"); }
};

类型 派生类 : 公开 基类 {
公开:
    空型 打招呼() 重写 { std::printf("派生类\n"); }
};

类型 密封类 最终 { };          // 最终：不能被继承

整数 main() {
    派生类 丙;
    丙.打招呼();
    如果 (真值 并且 并非 假值) { std::printf("并且/并非 也通了\n"); }

}
```

期望：编译通过，输出「派生类」「并且/并非 也通了」。
同时再写一行 `整数 动态绑定 = 1;` 应该**报错**（旧译名已失效）——这能确认改名生效。

### ④ 包含哪些

```
#include  #define  #undef  #if  #ifdef  #ifndef  #elif  #elifdef  #elifndef
#else  #endif  #defined  #line  #error  #warning  #pragma  #embed
#include_next  #assert  #unassert  #ident  #sccs  #module  #import
#__include_macros  #__public_macro  #__private_macro  #__preprocessed_module
#__preprocessed_import  #not_keyword
```

**为什么重要**：任何 C++ 程序第一行就是 `#include`，所以目前代码顶部必然是英文。

### 怎么改（已查明）

识别逻辑在 `IdentifierInfo::getPPKeywordID()`（`clang/lib/Basic/IdentifierTable.cpp:422`），
是一张**硬编码的完美哈希 switch**，而且**假设 ASCII**：

```cpp
#define HASH(LEN, FIRST, THIRD) ((LEN << 6) + (((FIRST - 'a') - (THIRD - 'a')) & 63))
#define CASE(LEN, FIRST, THIRD, NAME) \
  case HASH(LEN, FIRST, THIRD): \
    return memcmp(Name, #NAME, LEN) ? tok::pp_not_keyword : tok::pp_ ## NAME
```

中文字节长度与哈希都不符合这个设计（直接塞进去会和已有 case 相撞）→
**需要改这一个函数**：在 switch 之前加一张中文判断表。改动自包含。

### 一个待验证的旁证

`#if` / `#else` 里的 `if`、`else` **本身就是 C++ 关键字**，却能正常工作 ——
说明 clang 在 `#` 之后有「把关键字当标识符看待」的机制。因此 `#如果` 很可能也能做，
但**实现时要先实测确认**（`PPDirectives.cpp` 里对 `tok::identifier` 的要求）。

## 九、编译后发现的四个坑（都已修）

编译不只是"把源码变成二进制"，它会暴露一批**静态审查看不出来**的问题。
下面四个都是本轮真实踩到并修掉的。

### 坑一：宏体漏了一个 `#`（编译直接失败）

`ParseDeclCXX.cpp` 里从 `.def` 取中文拼写时写成了：

```cpp
#define ZH_VIRT_SPECIFIER(NAME, ZH) \
    Ident_zh_##NAME = &PP.getIdentifierTable().get(ZH);     // ✗ 少了 #
```

`ZH` 是汉字（如 `重写`），**必须字符串化**成字面量 `"重写"` 才能交给
`getIdentifierTable().get()`。写成 `get(ZH)` 会把汉字当标识符用，报：

```
ChineseKeywords.def(207,1): error C2065: “重写”: 未声明的标识符
```

修法：改成 `get(#ZH)`。

**为什么探针没抓到**：当时的探针把 `ZH_VIRT_SPECIFIER` 定义成**空宏**，只验了 `.def`
表本身，而 bug 在**宏体**里。教训：镜像宏体的探针价值有限（它只能验证"我以为的
宏体"），真正的护栏是**对真实 `.cpp` 跑一次 `-fsyntax-only`**。

### 坑二：`chinese++.exe` 硬链接被链接器断开（最隐蔽）

`chinese++.exe` 是 `clang++.exe` 的硬链接，靠"文件名以 `++` 结尾"被识别成 C++ 模式。
而链接器重写 `clang++.exe` 时是**删除再新建**，硬链接当场断裂 —— `chinese++.exe`
就停在上一次构建的旧二进制上，**没有任何提示**。

本轮踩到：拿 `chinese++.exe` 测新关键字，`虚拟`/`重写`/`最终` 全部不认，一度怀疑
构建没生效。定位办法是直接在二进制里搜译名字符串：

```
新 clang.exe    : 虚拟 ✓  动态绑定 ✗  重写 ✓  最终 ✓
旧 chinese++.exe: 虚拟 ✗  动态绑定 ✓  重写 ✗  最终 ✗
```

修法：`rebuild_clang.ps1` 末尾**每次重建后重新建立硬链接**并打印是否同步。

### 坑三：`模块`/`导入` 光登记成上下文关键字还不够

报错 `invalid preprocessing directive`。根因：clang 把 C++20 模块声明当
**预处理器指令**处理（`Lexer.cpp` 里 `HandleModuleContextualKeyword` 成功后调用
`HandleDirective`），而 `HandleDirective` 用 `getPPKeywordID()` 的返回值去匹配
`case tok::pp_module` / `case tok::pp_import`。

`getPPKeywordID()` 是一张**给 ASCII 设计的 perfect hash 表**（用长度 + 第 1/3 个
字符算桶），汉字进不去 → 返回 `pp_not_keyword` → 掉进 default → 报"未知指令"。

修法：在那个函数里、ASCII 表**之前**加一条中文分支，并且**复用已有标志位**
（`isImportKeyword()` / `isModuleKeyword()`），而不是再抄一份拼写：

```cpp
  if (static_cast<unsigned char>(Name[0]) >= 0x80) {
    if (isImportKeyword()) return tok::pp_import;
    if (isModuleKeyword()) return tok::pp_module;
  }
```

英文走不到这个分支（首字节 < 0x80），行为完全不变。修完中英文**逐字符一致**。

顺带说明：这正是 §八 那张表的**真实价值**——`module`/`import` 是"预处理器指令
中文化"的第一个真实案例，它不是锦上添花，而是 **C++20 模块功能的必要前置**。

### 坑四：验证链本身也会骗人（三次假红灯）

| 假红灯 | 真原因 |
|---|---|
| 探针报绿、MSBuild 报错 | 探针验的是**镜像**，不是真实文件 |
| `unknown type name '虚拟'` | 用的是**过期**的 `chinese++.exe` |
| 构建脚本解析失败 | 脚本被 `edit` 工具**抹掉 BOM**，PowerShell 5.1 按 GBK 读，中文落到语法位置就炸 |

对应的三条护栏现在都在：

1. **对真实 `.cpp` 跑 `-fsyntax-only`**（不是镜像）——挡住了坑一
2. **二进制里搜译名字符串** + 构建脚本自动重建硬链接——挡住了坑二
3. **`rebuild_clang.ps1` 改成纯 ASCII**（脚本是给机器执行的，不给它乱码的机会）；
   含中文的 `make_patch.ps1` 在调用前强制补 BOM

> `Select-Object -Last 22`（会憋住全部输出直到结束），加上父进程被中断后子进程

## 十、译名**已定、不再讨论**的条目

这一节的用途很具体：**防止同一个译名被反复重新提案。**

| 英文 | 中文 | 状态 | 依据 |
|---|---|---|---|
| `class` | **类型** | **已定，不再讨论** | 用户 2026-09-23 明确：*class 必须翻译成 类型*，是与其它 AI 对话讨论的结果 |

**这张表为什么存在（一次真实失误）**：2026-09-23 做诊断汉化时，有人把
「`class` 该不该改译成 `类`」当成了开放问题提出来。理由不是不尊重决定，而是
**决定不可见** —— 翻遍仓库只找到 `诊断汉化-准备.md` 里的一行**陈述**：

```
| class | 类型 | 与关键字 `类型` 一致 |
```

没有理由，也没有「已定」的标记。一个决定如果只以"现状"的形式存在，
后来者就只能把它读成"还没定"。

> **已定的译名要写清「已定」和「谁定的」。只写映射不写状态，等于没记。**

当时讨论的具体论证**没有存进仓库**。要看理由得回去问用户，**别自己编一个**。

### 附：`类` 这个字在正文里的地位（推论，非关键字决定）

`类` **不是关键字**（实测 `类 甲 { };` → `error: 未知的类型名 '类'`），它是普通名词。
诊断汉化对它的处理是：**关键字位置一律「类型」**；正文里作为普通名词出现的
class 沿用「类」（`类模板` / `类中成员` / `最终类` / `抽象类`）。
这是诊断汉化自己的用词规则，不是关键字决定的一部分。

## 十一、译名设计定则（强制，改译名前必读）

### 三个宏族：总数是 **99**，不是 86

`ChineseKeywords.def` 里的译名分三族，用**三个不同的宏**。只看 `ZH_KEYWORD`
会数出 86 —— 真实总数是 **99**：

| 宏 | 条数 | 内容 | 注册路径 |
|---|---|---|---|
| `ZH_KEYWORD` | **86** | 普通关键字（`如果` / `返回` / `类型` …） | `AddKeyword()` |
| `ZH_VIRT_SPECIFIER` | **2** | `override` = 重写、`final` = 最终 | `ParseDeclCXX.cpp` 里做指针比较 |
| `ZH_OPERATOR_KEYWORD` | **11** | 并且 / 或者 / 并非 / 异或 / 位与 / 位或 / 取反 / 与赋值 / 或赋值 / 异或赋值 / 不等于 | `AddCXXOperatorKeyword()` |
| | **99** | | |

> ⚠ **只数一族是踩过的坑。** 2026-09-23 有人（我）用只匹配 `ZH_KEYWORD` 的正则
> 数出 86，据此去改《诊断汉化清单.md》里本来就对的 99。事实是 **99 同时写在三处**：
> 本清单第 7 行、`tests\06-parity` 的输出、以及校核器的三族分解。
> 连**校核器自己**当时都只解析第一族（已修成解析三族）。
> 教训：**要报"全部"，先确认你数的是全部。**

### 三条定则（都是强制的）

| | 定则 | 机器校核 |
|---|---|---|
| 1 | **汉字数在 2–6 之间**（至少两字、最多六字；按【汉字】算，不按总字符数） | `verify_chinese_keywords.py` 第 10 节，**自带自测** |
| 2 | **译名互不重复**（三个宏族一起比） | 第 2 节 |
| 3 | **每个字符都能被 clang 词法分析器切分**（XID_Start / XID_Continue） | 第 4 节 |

**定则 1** 由用户 2026-09-23 明确：*"关键字有一个定则，就是至少要两个汉字，
最多 6 个汉字，无论如何都得遵守这一条"*。

- 「至少两字」的理由：单字关键字极易与用户标识符冲突，汉语本身也以双音节为主。
- 「最多六字」的理由：关键字太长会让代码难读难敲。
  **目前只有一条用满 6 字**：`取无修饰类型` = `typeof_unqual`。
- 汉字数按**汉字**算：表里有一个带数字的译名 `字符8位`（`char8_t`），
  总长 4、汉字 3，合规。

**定则 2** 的理由：两个中文拼写相同会让后注册者覆盖先注册者，其中一个关键字直接失效。
**定则 3** 的理由：切不开就没法当标识符用。
