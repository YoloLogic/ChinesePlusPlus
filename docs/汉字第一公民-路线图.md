# 汉字「第一公民」路线图

> **原则（本项目成立与否的标准）**
>
> 汉字必须是第一公民——否则不叫中文编程，只是 C++ 的一个方言。
>
> **补充：第一公民 ≠ 排他。**
> 汉字可以是最正式、最优先、文档与示例里默认的写法，同时英文依然合法。
> 一旦为了"纯"而删掉英文拼写，那不是更强的中文编程，而是**更弱的 C++**——
> 因为你切断了三十年生态里的一切：第三方库、调试器、现有代码。

## 一、一条判定规则（贯穿所有后续决定）

| 做法 | 例子 | 汉字地位 | 生态 |

| **给已有的东西加一个中文名**（别名 / 多拼写 / 包装） | `如果`、`标准::向量 = std::vector`、`标准::打印 → printf` | ✅ 一等 | **不丢** |

### 追问一步：加中文名会不会"占掉"一个标识符？

**不会额外占。** 中文名继承的约束和英文名**逐条相同**——英文名被限制到什么程度，中文名就被限制到什么程度：

| 名称种类 | 例 | 英文名能不能当标识符 | 加中文名后的代价 |
|---|---|---|---|
| **关键字** | `if` `class` | ❌ 完全不能 | 完全不能——**对称** |
| **上下文关键字** | `override` `final` | ⚠️ 能（该位置之外） | 该位置之外也能——**对称** |
| **宏** | `assert` `NULL` | ⚠️ 含该头后不能，`#undef` 可抢回 | 含该头后不能，`#undef` 可抢回——**对称** |
| **库函数 / 类型名** | `vector` `printf` | ✅ 能（可被用户定义遮蔽） | 放在 `标准::` 里，根本撞不上——**更宽松** |
| **运算符替代拼写** | `and` `or` | ❌ 是关键字，不能 | 不能——**对称** |

**没有一行是"中文比英文更占地方"。** 所以判断"某个中文名该不该加"的标准**不是**占不占名字，而只有一条：
**这个中文名译得对不对。**

（`assert` 的证据：它**不在** `TokenKinds.def` 的 `KEYWORD` 里——所以它不是关键字，是宏；
UCRT `assert.h` L22 自己就写着 `#undef assert`，L26/L36 再重新 `#define`。）

### 2.1 入口点 `main` 能不能加中文拼写

> 用户 2026-09-24 追问：「main 能同时增加中文吗」。
> **能 —— 但不能用关键字那套机制，因为 `main` 不是关键字。**
> （第一版这里写的是「改不了」，**太悲观**，已更正。中文写 `主函数` 之所以
> 链接失败 `LNK1561`，是因为链接器要找的符号名就是 `main`，与能不能加中文无关。）

三条路，全部实测（2026-09-24）：

| 路 | 做法 | 现在能用？ | 代价 |
|---|---|---|---|
| **1 宏** | `#定义 主函数 main` | ✅ **零编译器改动** | 宏是全局文本替换：任何叫 `主函数` 的**变量**也会被换掉；且诊断/调试信息里显示的是 `main`（宏在预处理就换掉了） |
| **2 汇编标号** | `整数 主函数() 汇编("main");` + `整数 主函数(){…}` | ✅ **零编译器改动** | **丢光 `main` 的专属检查**（见下）；也没有 `main` 的隐式 `return 0` |
| **3 改编译器** | 在 IdentifierTable 里把 `主函数` 别名成 `main` 的同一个标识符 | ✅ **已实现**（2026-09-25），见第 2.2 节 | 唯一能给两种拼写**同等语义**；代价是 `主函数` 成为保留名（与 `如果` 占掉 `if` 同性质） |

**路 2 的代价必须实测才看得见**（`main` 的专属检查是按**名字**做的，汇编标号把它绕过去了）：

```
空型 主函数() 汇编("main");            -> 无诊断  ← 但 void main 本该被拒
空型 main()                            -> error: 'main' 必须返回（关键字） 整数
整数 主函数(整数 甲) 汇编("main");      -> 无诊断  ← 但这是非法的 main 参数形式
```

也就是说：路 2 给你一个**链接得上、跑得起来、但编译器不再检查**的 `main`。
非法签名会静默通过，运行时行为未定义 —— 与第 4.0 节 C 层同一类问题（**不报错才是危险**）。

**"同时"的含义**（与关键字一致）：两种拼写**都接受，写哪个都行**，
但**不能同时写两个** —— 那是重复定义符号。这与 `如果`/`if` 的关系完全一样。

**实测：两个都写会被拦住**（两条路都在**编译期**报，不用等链接）：

```
路1 宏：      整数 main(){…}  +  整数 主函数(){…}   -> error: 重定义（名字） 'main'
路2 汇编标号：整数 main(){…}  +  整数 主函数() 汇编("main");…
                                                   -> error: 定义与另一个定义具有相同的修饰名（名字）'main'
```

**"识别为一个东西"在两条路上含义不同** —— 这一点决定了选哪条：

| | 路 1 改名（宏 / 编译器改名） | 路 2 汇编标号 |
|---|---|---|
| 链接符号是同一个 `main` | ✅ | ✅ |
| **编译器内部的名字**是同一个 | ✅ 就是 `main` | ❌ 是两个名字 |
| 两个都写 | ✅ 报重定义 | ✅ 报相同的修饰名 |
| **`main` 的专属检查**（返回类型、参数形式、隐式 `return 0`） | ✅ 生效 | ❌ **失效** |
| 诊断/调试里显示 | `main` | `主函数` |
| `主函数` 还能当别的标识符用 | ❌ 占掉了 | ✅ 还能用 |

### 2.2 路 3 的实现（2026-09-25 已完成）

**实现比原先的设想更干净：不是"`isMain()` 接受中文 + 挂 `asm("main")`"，
而是把 `主函数` 直接解析成 `main` 的同一个 `IdentifierInfo`。**

收口点在 `clang/include/clang/Basic/IdentifierTable.h` 的 `IdentifierTable::get()`：

```cpp 不编译
0
IdentifierInfo &get(StringRef Name) {
  if (!Name.empty() && static_cast<unsigned char>(Name[0]) >= 0x80)
    Name = aliasChineseIdentifier(Name);      // 实现在 IdentifierTable.cpp
  ...
}
```

`aliasChineseIdentifier()` 只有一条规则：`主函数` -> `main`。

**这样"同一个东西"的四条含义全部自动成立，一条都不用手写：**

| 要求 | 为什么自动成立 |
|---|---|
| 符号名是 `main` | 它就是 `main` 这个标识符，不需要 `asm` 标号 |
| `main` 的专属检查生效 | `FunctionDecl::isMain()` 是按名字判的（`Decl.cpp` 里 `isNamed(this,"main")`），名字就是 `main` |
| 同时写两个报重定义 | 同一个名字 → 走常规重定义检查 |
| `主函数` 是保留名 | `整数 主函数 = 5;` 等同于 `整数 main = 5;`，自动报错 |

**比"挂 `asm("main")`"那条路强在哪**：实测那条路会**静默丢掉**上面第二项 ——
`空型 主函数() 汇编("main")` 与 `整数 主函数(整数 甲) 汇编("main")` 都**不报错**。
不报错才是危险的那一类。别名路线没有这个洞。

**实现时踩到的两件事（都记在代码注释里）**

1. **公共头必须纯 ASCII。** 我第一版把中文注释写进了 `IdentifierTable.h`（672 字节），
   而这个头文件会被外部项目包含，那些项目不一定用 `/utf-8` 编译 —— 正是

## 四、标准库方案：**超集式复制**，不是改名式 fork

### 4.0 用户的决定与一条必须先定的粒度问题（2026-09-24）

**用户的打算（原话转述）：**

> 每个库都复制一份，名字翻译成中文，内部的调用方式改成中文，
> **但是依然可以识别英文调用对应上**。这是超大项目，我们**暂时**不好处理。
> **用户想引用哪个就用哪个。**

三句话各自是清楚的，但第三句与第二句**在"成员函数"这一层是冲突的**。
下面用实测把冲突摆出来 —— 因为它现在只是个方案，改起来零成本；
等真开始复制库再发现，代价就是重做。

> 用户 2026-09-24 追问"就是其他库之间可能存在互相引用的情况，对吧" ——
> **对，但那是三层里的第一层（B 层），而且是三层里唯一会大声报错的一层。**
> 完整的三层见下。

#### 实测：三层，一层比一层糟

用一个最小的类模板模拟 `std::vector`（`tools\library_plan_evidence\`，
证据脚本 `run.py`，一条命令可复跑并**自带断言**）：

**A. 同一个文件里同时引** —— 不需要任何库互相引用，用户自己就会撞上

| 场景 | 结果 |
|---|---|
| A1 只引中文副本 | ✅ 通过 |
| A2 引「原库」+「中文副本」（守卫**不同名**） | ❌ `重定义（名字） 'V'`，**两个顺序都报** |
| A3 A2 换个顺序 | ❌ 同上 |
| A4 引「原库」+「中文副本」（守卫**同名**，先引中文） | ✅ 通过 |
| A5 同上但**先引原库** | ❌ `没有名为（成员名） '压入' 的成员` |

A2/A3 说明「两份头各自独立」（最自然的写法）走不通；A4/A5 是标准补救
（中文副本**复用原库的 include guard**），它把"重定义"换成了
**静默的顺序依赖：先被引的赢，另一个整个被跳过**。

**B. 库之间互相引用** —— 报错，但**错误指向第三方库的头**

| 场景 | 结果 |
|---|---|
| B1 先引库（库的头里用了 `压入`），再引英文 `<vector>` | ✅ 通过 |
| B2 先引英文 `<vector>`，再引库 | ❌ `lib_uses_chinese.h:6: 没有名为（成员名） '压入' 的成员` |

B2 的错误指向**用户没写过、也改不了的那个文件**。而且真实项目里
`<vector>` 常被别的头**间接**带进来 —— **顺序根本不在用户手里**。
这一层至少会**大声报错**，虽然报得让人看不懂。

**C. 跨翻译单元：这一层不报错**

三个 TU 各自编译、链接、运行，全部成功，`sizeof` 一致，**零诊断**：

| 场景 | 结果 |
|---|---|
| C1 `a.cpp` 引 `vec_orig.h`、`b.cpp` 引 `vec_zh.h`，各自用各自的成员 | ✅ 编过、链过、跑过、**零诊断** |

C 层没有报错**不是幸运，是标准如此**：两个 TU 里 `my::V<int>` 的定义不同
（一个有 `压入`、一个没有），属 `[basic.def.odr]` 的 **IFNDR**
（ill-formed, **no diagnostic required**）。

这里碰巧能跑，只因为差异仅在**成员函数**、布局相同（`sizeof` 都是 8）。
**一旦中文副本动了数据成员或对齐，跨 TU 传对象就会内存错乱，而依然不会有任何提示。**

> **C 层是三层里唯一致命的一层**：A 层和 B 层至少会拦住你；
> C 层给你一个编得过、链得过、跑得动、看不出任何异常的程序。

#### 结论：粒度必须分两种

| 你要的中文 | 能否做到"每个文件各选各的" | 为什么 |
|---|---|---|
| **类型别名**（`标准::向量<int>`） | ✅ **能** | 别名不碰原库定义，两份可以共存 |
| **自由函数**（`标准::排序(v.begin(), v.end())`） | ✅ **能** | 同上 |
| **成员函数**（`表.压入(x)`） | ❌ **不能** | **成员属于类**，只能加在 `std::vector` 自己的定义里；一旦加进去就是**整条编译命令全局**的，与"哪个头先被引"无关 |
| 改库的内部实现 | ❌ 不能 | 同上，全局 |

所以正确说法是：

> **"用户想引用哪个就用哪个"** 适用于**别名层**；
> **成员级中文**只有**工具链级**的开关（一条编译命令选一套），没有"逐文件选"这回事。

#### 而且成员级中文**根本不需要两份头**

"英文调用照旧能对上"这条要求，在超集式复制里是**免费**的：中文副本是原库的**超集**，
英文成员一个没动。所以 `v.push_back(1)` 和 `v.压入(1)` 在**同一份头**里同时可用 ——
不需要"原库"/"中文库"两个版本，也就不存在引错、引重、顺序问题。

于是最干净的形状是：

| | 做法 |
|---|---|
| 用哪几份库 | 把要中文化的库各复制一份，**只加不改** |
| 怎么指过去 | `-nostdinc++ -isystem <中文STL目录>`（4.2 已写）—— **全局，一条命令选一次** |
| 英文怎么办 | 一个字节没动，照旧可用（超集的含义） |
| "用户想引用哪个" | 变成 **"这次编译用不用中文库"**，而不是"这个文件引哪个头" |

**建议：按这个形状定。** 两份头并行那条路，被上面的实测否掉了。

#### 那三条代价警告，以及 2026-09-27 的更正

`examples\zhstd.h` 头部曾列了"复制一份库改中文"的三条代价
（**该文件已于 2026-09-27 删除**，长期无人使用；三条原文保留在这里，因为它们是**对的**）：

```
❌ 名字改了 → 名字修饰变了 → 和任何预编译库都链不上
❌ std::string / std::exception 这类跨边界类型变成"另一种类型"
❌ 每跟一次库升级都要重放几千个名字的改名
```

本节原先写的是「**那三条针对的是改名式 fork，不是超集式复制**，所以不构成反对」。
**2026-09-27 更正：这个说法不成立。** 用户的方案要**改类名**（`vector` → `向量`）、
**搬名域**（`std` → `标准`），所以那三条**恰恰适用**，而且已被实测逐条印证：

| 原警告 | 2026-09-27 实测 |
|---|---|
| ② 跨边界类型变成"另一种类型" | ✅ **异常捕获实测证实**：第三方抛的 `std::runtime_error`，用 `捕获 (标准::运行时错误&)` **抓不到**（base→derived 不通），且**不报编译错**，异常直接逃出去 |
| ③ 每次跟库升级要重放改名 | ✅ 要抄 **112 个文件 / 120,263 行**，且靠微软内部名（`_Vector_val` 等）对接，升级要重新同步 |
| ① 改名字 → 和预编译库链不上 | ⚠️ 实测比它说的**轻**：只有"把 `std::vector<T>` 写死在模板推导位置"的接口接不了，可显式转换绕过 |

**结论：抄一份这条路可以做，但代价是真的。** 方案细节与"两条路各管一类"的划分见
`docs\标准库汉化\标准库汉化方案.md`。

---

> 想法：不动原来的库，而是**复制**一份，在它之上修改（库名改中文、内置用法改中文），
> 并且**英文依然生效**——用户调用中文库时，英文照旧可用。

这个方向和"fork 一份中文 libc++"**性质完全不同**，关键差别是**只加不改**：

| | 改名式 fork | **超集式复制（本方案）** |
|---|---|---|
| 英文原名 | 被删掉 | **一字不动** |
| 类型身份 / 名字修饰 | 变 | **不变** |
| 预编译的第三方库 | 链不上 | **照链** |
| 第三方源码（写 `std::vector`） | 编不过 | **照编** |

只加不改 → 布局、已有符号、ABI 全不变 → 生态不丢。

### 4.1 一条硬约束：中文成员名必须加在 `namespace std` 里面

| 方案 | 中文名放哪 | 类型身份 | 成员写法 `表.压入(x)` | 生态 |
|---|---|---|---|---|
| **A（目标）** | 改 `std::vector` 自己的定义 | **同一类型** | ✅ | ✅ 不丢 |
| **B（打底）** | `namespace 标准` 放别名 + 自由函数 | 同一类型（别名） | ❌ 只能 `压入(表, x)` | ✅ 不丢 |
| C | `标准::向量` 做成包装类 | ❌ **不同类型** | ✅ | ❌ 断 |

**要"成员语法 + 生态无损"，就必须改 `std` 自己**——成员属于类，一旦包装就换了类型。
而"只加内联转发成员"是安全的：

```cpp 不编译
0
// 在复制出来的那份 vector 头里（即你的 std::vector）
template <class... _Args>
void 压入(_Args&&... __args) { push_back(std::forward<_Args>(__args)...); }
```

### 4.2 实现路径（**不用重建任何 DLL**）

| | 做法 |
|---|---|
| 用哪份 STL | **MSVC 的 STL**——微软已开源（MIT，可再分发），而且我们本来就在用，ABI 完全一致 |
| 要不要重编库 | **不用**：只加内联成员，`msvcprt.dll` 一个字节没动 |
| 怎么指过去 | 用 `-nostdinc++ -isystem <自己的 STL 目录>` |
| 备选 | libc++（为 clang 设计、无 DLL 耦合）——更干净，但等于换一套 STL 工具链，工程更大 |

### 4.3 要注意的点

1. **成员函数不能起别名**——C++ 无此机制，只能加**内联转发成员**（上面那种）。运算符重载成员同理。
2. **运算符符号（`+` `==` `[]` `->`）改不了**——它们不是名字。只能走"运算符替代拼写"那条路（`并且`/`或者` 已做）。
3. **宏可以放心加**（原写作"宏慎加"，**已更正**）——`assert` 本身是宏而不是关键字，所以
   `#define 断言 assert` 与 `assert` 的约束**逐条相同**：包含该头后不能当变量名、`#undef` 可抢回、不包含时随便用。
   **代价对称 ⇒ 边际代价为零。** 详见第一节那张对称表。
4. **头文件名可以加中文副本**（`#include <向量>`）——纯文件操作，天然"只加不改"，最省力的一项。
5. **两个真实代价**：① 头文件变大 → 编译变慢（成百上千个内联转发被反复解析）；
   ② MSVC STL 有**版本锁**（`_MSVC_STL_VERSION` 与 DLL 配对），复制的那份要跟着 VS 升级走。

### 4.4 推进顺序（**不用一次追平几千个名字**）

| 步 | 做什么 | 风险 | 状态 |
|---|---|---|---|
| 1 | `namespace 标准` 放**类型别名**（`模板 <类型名 元素> 使用 向量 = std::vector<元素>;`） | 零（同一类型） | 已验证（取证 `tools\library_plan_evidence\`；`examples\zhstd.h` 已于 2026-09-27 删除） |
| 2 | 放**自由函数**（`标准::排序(v.begin(), v.end())`） | 零（同一函数） | 已验证 |
| 3 | ~~逐步在 `std` 里加**内联转发成员**~~ | 低（只加不改）**但它是全局的**，见 4.0 节 | ✅ **已由另一条路解决**（2026-09-30）：**不改 `std` 自身定义**，改用"复制层 + 派生层"—— `zhstdlib\` 覆盖 **103 / 103 个标准头**（产物 116 个），`标准::向量<整数>`/`表.尾插(1)` 可用，`std::` 原样不动（铁律①）。~~原文：❌ 待做、用户 2026-09-24 已决定暂缓~~ —— **就地废止** |
| 4 | 头文件名中文副本（`<向量>`） | **零（纯文件）** | ✅ **已验证现在就能做**（2026-09-24）：`#包含 <向量>` + 中文 include 目录名，CMake + Ninja 全链路通过；中英名字是同一类型、可互传。样例 `tools\library_plan_evidence\向量` |

> **第 3 步和第 4 步的性质完全不同，别一起看：**
> 第 4 步只是**多一个文件名**（内容是别名，不改 `std::vector` 的定义），
> 所以 4.0 节那三层问题一个都不沾 —— 它**现在就能做**。
> 第 3 步要动 `std::vector` 自己的定义，因此是**全局**的，
> 也是 4.0 节三层问题的来源。

第 1、2 步现在就能做；第 3 步是**纯增加**，不会破坏前两步的用法。

## 五、一共有多少自带的库

> 2026-09-24 实测。**测量工具 `tools\inventory_libraries.py`**（一条命令可复跑；
> 原先是临时脚本，已提升为正式工具 —— 文档里的断言必须能复跑）。
> 结论先给：**面向用户的自带库 = 0 个。**

### 5.1 `build\Release\lib` 里的 149 个 `.lib`：全都是编译器自己的

| 前缀 | 个数 | 是什么 |
|---|---|---|
| `LLVM*` | 74 | `LLVMCore.lib`、`LLVMIRReader.lib` … |

| `clangd*` | 7 | `clangDaemon.lib`、`clangIndex.lib` … |

这些是给**把 clang 当库链接的工具开发者**用的（写 clang-tidy 插件、clangd 扩展之类），
**不是给用户编程用的库**。用户编一个普通程序，一个都用不上。

### 5.2 clang 自带的头文件：287 个，但 19 个以外都不是"标准库"

位置：`build\Release\lib\clang\24\include`（`clang -print-resource-dir` 报出来的）。
**238 个顶层文件 ＋ 7 个子目录共 49 个 ＝ 287。**

| 类别 | 个数 |
|---|---|

| `__stddef_*` / `__float_*` / `__stdarg_*` 这类**拼装碎片**（给上面那些头 include 用的） | 58 |
| GPU / OpenMP / SPIR-V 设备端包装（`__clang_cuda_*`、`__clang_hip_*` …） | 21 |
| **C 语言 freestanding 头** | **19** |

子目录 49 个：`cuda_wrappers` 4 ／ `hlsl` 9 ／ `llvm_libc_wrappers` 7 ／
`llvm_offload_wrappers` 3 ／ `openmp_wrappers` 4 ／ `ppc_wrappers` 13 ／ `zos_wrappers` 9。

**只有那 19 个算"编译器自带、用户能用"的东西**：

```
stddef.h  stdarg.h  stdbool.h  stdalign.h  stdnoreturn.h  stdatomic.h
stdckdint.h  float.h  limits.h  stdint.h  inttypes.h  iso646.h
```

但这**不是"标准库"**，是标准规定的**编译器最低义务**：freestanding 实现必须提供
`stddef.h` / `stdarg.h` / `stdbool.h` / `float.h` / `limits.h` / `stdint.h` 这几个，
否则 `#include <stddef.h>` 都没法用。任何编译器都得有，谈不上"我们的库"。

## 六、一条要一直守住的底线

**中文关键字改动到目前为止，没有让任何一份标准 C++ 代码编不过。**
这是因为：`TokenKinds.def` 零改动、英文拼写永远保留、中文只是加进去的另一个入口。

后续任何一项中文化，都要守住同一条底线：

> **做完之后，随便拿一个开源 C++ 项目，用我们的编译器编，必须照样编得过。**

这条底线比"纯不纯"重要得多——它是这个项目唯一无法被替代的地方。

### 6.1 现在怎么证明它（一条命令）

```powershell
powershell -File E:\Chinese++\tools\verify_third_party.ps1 `
    -Projects tinyxml2,pugixml,fmt,googletest,cJSON,zlib,libuv,lz4
```

把 8 个真实开源项目各编两遍——**一遍用我们的编译器，一遍用 VS 自带的官方 clang**——
然后比较 `configure` / `build` / `ctest` 三个退出码**以及失败用例的集合**。

2026-09-24 实测：

```
cases=8  pass=2  same=6  fail=0
  tinyxml2 / pugixml            PASS（全绿且与官方相同）
  fmt / googletest / cJSON / zlib / libuv / lz4   SAME（和官方错得一模一样）
```

**判据是 `fail=0`**，不是"全绿"。`SAME` 表示我们和官方 clang 在**同一处、以同样方式**失败
（上游或环境问题），这才是"没弄坏东西"的正确读法。

### 6.2 这条底线的能力边界（要说清楚）

它证明的是**"我们没引入回归"**，**不是**"中文编程能用"。

那 8 个项目全是英文代码，一个中文字符都没有——中文特性对它们**零帮助**。
它们能编过，只说明中文关键字/指令/诊断的加入**没有污染英文路径**。

"中文编程到底好不好用"是另一个问题，判据是**第二节那张九行的分层表**，
以及第三节第 3 项（标准库别名层）——那一项做完之前，用中文写的真实程序
必然是"语法中文、库英文"的混合体。
