# 中文 C++ 编译器 使用说明

本项目是一个支持**中文关键字**的 Clang。中文和英文关键字都能用，两者完全等价，
而且**共用同一套 C++ 生态**——标准库、第三方库、调试器、clangd 全都能继续用。

---

> **如果你拿到的是发行包**（`Chinese++-0.2-win64.zip`）：**别照本节下面的路径敲。**
> 解压后双击 `一键安装.cmd` —— 它会建好 9 个别名、写好 `env.cmd`、检测 VS Build Tools、
> 按需装便携 VS Code、**把汉化库的搜索路径写进 `bin\` 里的三个 `<驱动名>.cfg`**、并跑一遍包内自测。
> 之后用包里的 `env.cmd` 开命令行，就能直接敲 `chinese++`，`#包含 <向量>` 开箱可用
> （汉化库 **`zhstdlib\`（119 个头）随包**；**移动过文件夹就再跑一次 `一键安装.cmd`** ——
> 那三个 cfg 里是绝对路径，`常见问题.md` 第四节有专门一条）。
> 本节及以下所有 `E:\Chinese++\build\Release\bin\...` 都是**仓库里的构建树**；
> 发行包里对应的是 **`<包目录>\bin\`**。包内另有两份必读：`常见问题.md`、`中文对照表.md`。

## 一、编译器在哪

构建产物在：

```
E:\Chinese++\build\Release\bin\clang.exe      78 MB
E:\Chinese++\build\Release\bin\clang++.exe    78 MB
E:\Chinese++\build\Release\bin\clangd.exe     45 MB   ← 给 IDE 用的语言服务器
```

`clang++` 用于 C++（自动链接 C++ 标准库），`clang` 用于 C。写 C++ 就用 `clang++.exe`。
`clangd.exe` 不参与编译，只在编辑器里提供补全、跳转和语法高亮——它和编译器用的是
**同一套改过的关键字表**，所以中文关键字在 IDE 里同样不会被标红。

> **`chinese++.exe`**：和 `clang++.exe` 是**同一个文件**（硬链接，不额外占空间）。
> clang 的驱动模式由**程序名的后缀**决定——`clang/lib/Driver/ToolChain.cpp:587`
> 里有一张表 `{"++", "--driver-mode=g++"}`，匹配方式是按后缀遍历。
> 所以**任何以 `++` 结尾的名字都自动是 C++ 模式**：`chinese++.exe`、`zh++.exe`、
> 甚至 `汉语++.exe` 都可以。用它编译中文源码，正好。

**建议加进 PATH**，之后就能直接敲 `clang++`：

```powershell
# 只对当前窗口生效
$env:Path = "E:\Chinese++\build\Release\bin;$env:Path"

# 永久生效（新建窗口后有效）
[Environment]::SetEnvironmentVariable(
  "Path",
  "E:\Chinese++\build\Release\bin;" + [Environment]::GetEnvironmentVariable("Path", "User"),
  "User")
```

> **不用再记搜索路径了**（2026-10-05，§18.30）：`#包含 <向量>` 这类中文头靠的是
> **编译器同目录的 `<驱动名>.cfg`**（`chinese++.cfg` / `clang++.cfg` / `clang.cfg`，
> 由 `tools\make_zhcfg.ps1` 从单一事实来源 `tools\zh_includes.ps1` 生成）。
> 所以命令行只写 `chinese++ -std=c++20 你的.cpp` 就行；**IDE（clangd）读的也是同一份**，
> 中文头不再被标红（以前 clangd 会报 `找不到文件（名字）'向量'`）。
> ⚠ cfg 里是**绝对路径**：**移动或改名本目录之后要重跑一次生成**
> （构建树：`pwsh -File tools\make_zhcfg.ps1`；发行包：重跑 `一键安装`）。

## 二、最快开始

> **文件扩展名：就用 `.cpp`**（决策记录，2026-10-08）。
> 曾考虑把汉语源码的扩展名改成 `.ccpp`，以免与原版 C++ 源码混淆；用户裁定**不改**：
> 「弄混就弄混了，就是 cpp 格式。反而可以更好地推广我们的软件」。
> 中文源文件与原版英文源文件**共用 `.cpp`**；`chinese++.exe` 两种源码都能编
> （中文关键字与英文关键字是同一套 token，见 `docs\关键字\`）。
> ⇒ 所以**没有** `.ccpp` 这个扩展名，也不会新增 —— 这条记在这里，免得以后再有人问/再想一遍。

新建 `示例.cpp`（**必须存成 UTF-8**）：

```cpp
#include <cstdio>
#include <windows.h>

整数 求平方(整数 甲) {
    返回 甲 * 甲;
}

整数 main() {
    // 让控制台按 UTF-8 解码，否则中文会显示成乱码（见第八节常见问题）。
    SetConsoleOutputCP(CP_UTF8);

    对于 (整数 甲 = 1; 甲 <= 5; ++甲) {
        如果 (甲 == 3) { 跳过; }
        std::printf("%d 的平方是 %d\n", 甲, 求平方(甲));
    }
    返回 0;
}
```

编译并运行：

```powershell
E:\Chinese++\build\Release\bin\clang++.exe -std=c++20 示例.cpp -o 示例.exe
.\示例.exe
```

输出：

```
1 的平方是 1
2 的平方是 4
4 的平方是 16
5 的平方是 25
```

## 三、环境要求

| 要求 | 说明 |
|---|---|
| **源文件必须是 UTF-8** | 唯一硬性要求。存成 GBK 会直接词法报错，因为 `如果` 的 GBK 字节不是合法 UTF-8 |
| MSVC / Windows SDK | 已自动探测，**无需**手动配置环境变量或运行 `vcvars` |
| 无需任何字符库 | clang 自带完整 Unicode 数据（XID 属性表、UTF-8 编解码） |

在编辑器里把默认编码设为 UTF-8（VS Code：`files.encoding` → `utf8`；CLion：`File Encodings` → `UTF-8`）。

## 四、书写注意

中文关键字与英文关键字遵循**完全相同的 C++ 词法规则**：

```cpp
如果(甲 > 0) { 返回 甲; }   // ✅ 括号天然分隔，不用空格
返回 甲;                     // ✅ 关键字后跟标识符，需要空格
返回甲;                      // ❌ 会被读成一个标识符「返回甲」
```

| 写法 | 结果 |
|---|---|
| `如果(` | ✅ `(` 不是标识符字符，自动分隔 |
| `返回 甲` | ✅ 空格分隔 |
| `返回甲` | ❌ 整体是一个标识符 |
| `整数 甲` | ✅ |
| `整数甲` | ❌ 整体是一个标识符 |
| `并非 假值` | ✅ `!false` |
| `并非假值` | ❌ 整体是一个标识符（`并非`=`!`、`假值`=`false`，都是汉字） |

> 中文没有词间空格的习惯，所以这里比英文更容易疏忽。规则本身和英文一模一样
> （英文写 `returnx` 也是同一个标识符）。
> **遇到"未声明的标识符"却看不出哪里写错时，先找找是不是两个汉字关键字挨在一起了。**

#### 还有三个"看着奇怪其实合法"的坑（2026-10-04 实测，都进了用例）

```cpp
整数 ａｂｃ = 1;      // ① 全角字母**能**作标识符（Unicode Ll）—— 但别用
整数 甲１ = 2;        //    全角数字同理（Nd）。与半角是**两个不同的标识符**
整数 \u4e2d\u6587 = 7;  // ② 通用字符名 `\u4e2d\u6587` 就是 `中文`，同一个标识符
整数 中 = 1;          // ③ U+4E2D 统一汉字
整数 中 = 2;          //    U+F900 兼容汉字 —— **另一个标识符**，屏幕上看着一样
```

| 现象 | 实测结论 | 建议 |
|---|---|---|
| ① 全角字母/数字作标识符 | **编得过**（上游 clang 同样如此） | **别用**：看着就像写错，而且和半角不是同一个名字 |
| ② 通用字符名 `\uXXXX` | 与对应汉字**是同一个标识符**，可以互换 | 正常写汉字即可；UCN 只是同一条词法路径 |
| ③ 兼容汉字（U+F900 区） | 与统一汉字**是两个标识符**，clang **不做 NFC/NFKC 归一化**（上游行为） | 从 PDF／旧字库**复制粘贴**时要小心：编译器说"未声明的标识符"而肉眼看不出差别 |

> 这三条都在 `tests\12-diagnostics\77~79*.cpp` 里钉着（行为变了就会红）。
> 另外：英文 `'ab'` 是**多字符常量**（只警告），汉字 `'中'` 是 3 个 UTF-8 字节、
> `char` 放不下 ⇒ **报错**；要装一个汉字用 `u8'中'`/`u'中'`/`U'中'` 或宽字符类型。
> 见 `tests\12-diagnostics\80~82*.cpp`。

**中英可以混写**，同一个文件里随便用：

```cpp
整数 甲 = 1;
int 乙 = 2;
如果 (甲 < 乙) { return 乙; }
```

### Windows 控制台里中文乱码（必看）

编译器把中文字符串按 **UTF-8** 编进程序（clang 的默认行为，也是跨平台一致的
唯一选择）。而中文版 Windows 控制台默认代码页是 **GBK(936)**，拿 GBK 去解释
UTF-8 字节 → 中文全变乱码。实测同一份 226 字节输出的两种解释方式：

```
按 UTF-8 解释  →  圆 面积 = 12.5664
按 GBK  解释  →  鍦?闈㈢Н = 12.5664        ← 乱码就长这样
```

**根治办法**：程序开头调用一次（用 `examples\中文控制台.h`，只多两行）

```cpp
#include "中文控制台.h"

整数 main() {
  启用中文控制台();     // Windows 下把控制台改成 UTF-8；其他平台是空操作
  printf("圆 面积 = %.4f\n", 3.14159265358979 * 4);
  返回 0;
}
```

**不改程序的办法**：运行前先在终端里执行 `chcp 65001`。

**VS Code 里怎么办**：两条路，**建议两条都做**（互不冲突）：

1. **程序侧（不依赖终端）**：如上一段调用 `启用中文控制台()`。这样双击 exe、
   在任意终端跑、换任何编辑器都不乱码。
2. **终端侧（一次性，一劳永逸）**：把终端设成 UTF-8。**本机已经装好了**，装法是：

```powershell
# 装上（往你自己的 PowerShell $PROFILE 里加一段带标记的块）
powershell -File E:\Chinese++\tools\setup_utf8_terminal.ps1

# 撤销（逐字节还原，见下）
powershell -File E:\Chinese++\tools\setup_utf8_terminal.ps1 -Undo
```

**"两层乱码"是什么意思** —— 这是关键，只治一层会剩一半：

| 层 | 什么时候 | 为什么乱 |
|---|---|---|
| ① 你的程序打印的中文 | **运行时** | 程序发 UTF-8 字节，GBK 终端按 GBK 解释 |
| ② **编译器自己的中文报错** | **编译时** | 诊断也是 UTF-8 字节，**同样**被 GBK 解释成花屏 |

终端一旦是 65001，**①②一起解决**；而 `启用中文控制台()` 只能治 ①。

> ### 为什么把 chcp 写进 `.vscode\settings.json` 行不通（**踩过两次，别再试**）
>
> 正确的做法是**改用户自己的 `$PROFILE`**（上面那个脚本），**不是**改 VS Code 的终端配置。
> 两次失败记录：
>
> | 写法 | 结果 |
> |---|---|
> | `args: ["-NoExit","-Command","chcp 65001 > $null; [Console]::OutputEncoding = …"]`（长命令） | ❌ 终端一开就报 `表达式或语句中包含意外的标记"-Command"`（VS Code 拼命令行时丢了引号） |
> | `args: ["-NoExit","-Command","chcp 65001"]`（短命令） | ❌ 终端一开就报 `参数格式不正确 - -Command` |
>
> **两次的根因是同一个**：命令行里出现了**第二个 `-Command`**
> （VS Code 的 shell 集成 / conda 注入会再加一个），而 PowerShell **只认第一个**
> `-Command`，把后面的全当脚本文本 —— 于是实际执行的是
> `chcp 65001 -Command …`，chcp 收到 `-Command` 就报错。
> **教训：终端配置的 `args` 里永远不要放 `-Command`**，它必须独占且只能出现一次，
> 而"别人也要用 `-Command`"这件事你控制不了。
>
> 另外两种**实测也不可行**的写法：
>
> | 写法 | 结果 |
> |---|---|
> | `"chcp 65001>nul"` | ❌ PowerShell 把 `65001>nul` 当成**一个参数**传给 chcp → `Parameter format not correct`，代码页没变 |
> | `"[Console]::OutputEncoding=[Text.Encoding]::UTF8"` | ⚠️ **惰性**：要等 .NET 第一次真的往控制台写东西才生效，当场 `chcp` 查还是 936，不可靠 |
>
> ### 改 `$PROFILE` 会不会弄坏别的工具？—— 不会，实测过
>
> | 工具 | 在 CP936 终端 | 在 CP65001 终端 |
> |---|---|---|
> | 我们的 clang（**固定**发 UTF-8） | ❌ 乱码 | ✅ 正常 |
> | MSVC 的 `cl.exe`（发 GBK） | ✅ 正常 | ✅ **也正常** —— 它会**跟着代码页**改成 UTF-8 输出 |
>
> `cl.exe` 是"跟着代码页走"的（实测它自己在 65001 下输出了正确的中文），
> 所以把终端设成 UTF-8 **不会**让 MSVC 的报错变乱码。

> ### 那个脚本的可逆性是被证明过的，不是"应该没问题"
>
> 安装时会在块首行写入 `prev-chars=<原字符数>`；撤销时按它**截断回原长度**。
> 当时的验收记录：
>
> ```
> 基线           269 字节  SHA256 前16 0F9125A2EB391C3A
> 安装后         830 字节  含 prev-chars=269，conda 段落完好，BOM 仍为 False
> 有效验证       父控制台先 chcp 936 → 新 PowerShell 报 65001   ← 只有 profile 能做到
> 撤销后         269 字节  SHA256 前16 0F9125A2EB391C3A          ← 与基线逐字节一致
> ```
>
> （若你在安装之后又往 profile 里加了别的内容，撤销会退回"按标记删除"，
> 保留你后加的部分，只在末尾空行上可能有差异，脚本会打印 `note` 告诉你。）

> 已验证：在一个**显式设为 936** 的控制台里运行演示程序，程序调用
> `启用中文控制台()` 之后中文输出完全正常——说明这个办法不依赖终端设置。
>
> `examples\` 下 6 个老示例（`expr_calc` / `hanoi` / `life` / `matrix` /
> `charfreq` / `keywords_vs_names`）各自直接写着
> `SetConsoleOutputCP(CP_UTF8)`；新写的程序建议改用上面这个共享头，避免重复。

### 上下文关键字（第六节、第八节）

| 中文 | 英文 | 说明 |
|---|---|---|
| 重写 | override | 写在虚函数声明之后 |

这四个在 C++ 里**不是关键字**，而是"只在特定位置才有特殊含义的标识符"。
所以它们**不可能替换英文**——`整数 final = 7;`、`int module = 1;` 这类写法必须继续合法。

四行同时编译通过。

### 运算符替代拼写（第七节，11 个）

| 中文 | 等于 | 符号 | | 中文 | 等于 | 符号 |
|---|---|---|---|---|---|---|
| 并且 | and | `&&` | | 取反 | compl | `~` |
| 或者 | or | `\|\|` | | 与赋值 | and_eq | `&=` |
| 并非 | not | `!` | | 或赋值 | or_eq | `\|=` |
| 异或 | xor | `^` | | 异或赋值 | xor_eq | `^=` |
| 位与 | bitand | `&` | | 不等于 | not_eq | `!=` |
| 位或 | bitor | `\|` | | | | |

它们映射到与符号**完全同一个 token**，所以 `a 并且 b` ≡ `a and b` ≡ `a && b`。
注意这些中文词是**真关键字**，不能再当变量名——但英文的 `and`/`or` 本来也不能，
代价是对称的，没有额外损失。

#### 列号：为什么汉语源码要专门管这件事（2026-10-03）

`文件:行:列` 里的**列**以前一直是**字节偏移**。汉语一个字占 3 个字节，于是同一个位置
会数出三个完全不同的数（同一行实测：**字节 81 / 显示列 59 / 字符序 37**）：

```
整数 甲乙丙丁戊己庚辛 = 1; 整数 结果 = 甲乙丙丁戊己庚辛 + 未定义名字;
                                                       ^~~~~~~~~~
                                                       插入符一直是对的（按显示宽度）
```

| 开关 | 列号 | 谁需要它 |
|---|---|---|
| `-fdiagnostics-column-unit=byte` | 81 | 想和旧版本/老工具逐字节对拍时 |
| `-fdiagnostics-column-unit=display`（**默认**） | 59 | 终端里看 —— 与插入符同一口径 |
| `-fdiagnostics-column-unit=character` | 37 | **编辑器的问题匹配器**（VS Code 按 UTF-16 列解析，汉字算 1 列） |

> 用 VS Code 看报错、点"下一个错误"却跳偏了，就把 `character` 加进编译参数。
> 只影响**给人看的** `文件:行:列` 前缀；`-fdiagnostics-parseable-fixits` 那些
> 机器格式仍按字节，不受影响。

第一批已经中文的：声明末尾缺分号、未知类型名、未声明的标识符、

### 预处理指令也中文化了（`#include` → `#包含`）

**中英两种写法可以随意混用**，同一个文件、同一条 `#if` 链里混着写都行，
不需要任何开关，也不会影响编译结果 —— 两种拼写解析出的是**同一个内部枚举**，
编译器后续根本区分不出你写的是哪一种。

```cpp
#包含 <cstdio>          // 中文
#include <vector>        // 英文，混用没问题

#如果 平台 == 1          // 中文
#  定义 大小 64
#否则若 平台 == 2        // 中文
#  定义 大小 128
#else                    // 英文
#  定义 大小 32
#结束如果                // 中文
```

对照表（22 条）：

| | | | |
|---|---|---|---|
| `#include` → `#包含` | `#define` → `#定义` | `#undef` → `#取消定义` | `#if` → `#如果` |
| `#ifdef` → `#如果已定义` | `#ifndef` → `#如果未定义` | `#elif` → `#否则若` | `#elifdef` → `#否则若已定义` |
| `#elifndef` → `#否则若未定义` | `#else` → `#否则` | `#endif` → `#结束如果` | `#line` → `#行号` |
| `#error` → `#错误` | `#warning` → `#警告` | `#pragma` → `#编译指示` | `#embed` → `#嵌入` |
| `#include_next` → `#包含下一个` | `#ident` → `#标识` | `#assert` → `#断言` | `#unassert` → `#取消断言` |
| `#module` → `#模块` | `#import` → `#导入` | | |

**几条别误会：**

- **`#模块 m;` 会报错，这是对的**。英文 `#module m;` 同样报错 —— `#` 形式的
  `module` 在 Clang 里本来就不合法。声明模块要写**不带 `#`** 的 `模块 m;`。
- **`#导入 "x.h"` 早就可用**，走的是 ObjC 风格的 `#import` 通道
  （报"导入类型库是不受支持的 Microsoft 特性"，与英文一字不差）。
- **`#断言` / `#取消断言` 会报错**，因为上游 Clang 就没实现这两个指令
  （源码里写着 FIXME），英文一样报错。
- **`#if` 里的 `defined` 仍是英文**：`#如果 defined(某宏)` 中 `defined` 不译。
- **`#pragma` 后面的名字仍是英文**：`#编译指示 once`。这一层是各编译器的
  自定义命名空间，没有统一标准，不适合汉化。同理诊断正文里出现的
  `#pragma omp atomic` 这类**整条指令名不全在我们的表里**的写法也保持英文。
- **诊断正文里的指令拼写恒为中文**，跟你敲的是哪种写法无关 —— 与关键字方针一致：

  ```
  #elifdef A    （英文写法）  →  warning: 使用 '#否则若已定义' 指令是 C++23 扩展
  #否则若已定义 A（中文写法）  →  warning: 使用 '#否则若已定义' 指令是 C++23 扩展
  ```

  这两行输出**一字不差**。同样的，敲英文 `static_assert` 诊断也输出 `（关键字） 静态断言`。
  也就是说：中文是**对外正式拼写**，英文是**同样合法的输入拼写**。
- **指令名当普通变量名照样可以**：`整数 包含 = 1;` 编译通过。
  只有出现在 `#` 之后才会被当成指令。

下面 6 条**有意保持英文**：`__include_macros`、`__preprocessed_module`、
`__preprocessed_import`、`__public_macro`、`__private_macro`（前 5 条是编译器
自己写进 PCH / 模块文件 `.pcm` 的内部拼写，改动会影响二进制格式兼容）、
`sccs`（1980 年代遗留，默认报错）。

设计说明与踩过的坑见 [`预处理指令汉化/预处理指令汉化.md`](预处理指令汉化/预处理指令汉化.md)。

### C 运行库也有中文名了（2026-10-04 起，陆续做）

C++ 那半边早就汉化了（`标准::向量` / `标准::排序`）。**C 运行库**（`printf` / `malloc` / `strlen`…）
的符号在微软的 DLL 里、改不了，所以我们用「**加一个中文名转发到原名**」的办法：

```cpp
#包含 <C标准输入输出>
整数 主函数(){
    标准::格式化输出("甲=%d 双=%.2f\n", 42, 2.5);        // printf
    标准::格式化输出到(标准::标准错误, "出错了\n");         // fprintf
    字符 缓冲[64];
    标准::格式化到字符串(缓冲, "%d", 7);                   // sprintf
    标准::限长格式化到字符串(缓冲, sizeof(缓冲), "%d", 8);  // snprintf（安全版）
    整数 甲 = 0, 乙 = 0;
    标准::从字符串格式化输入("3 4", "%d %d", &甲, &乙);    // sscanf
    标准::格式化输入("%d", &甲);                           // scanf（从键盘）
    返回 甲 + 乙;
}
```

**英文原名照旧能用**（`printf(...)` 一个字符都不用改），原头一个字节没动 —— 只是多了名字。

| 家族 | 中文名 |
|---|---|
| 格式化到屏幕 / 文件 / 字符串 | `格式化输出`(printf) / `格式化输出到`(fprintf) / `格式化到字符串`(sprintf) / `限长格式化到字符串`(snprintf) |
| 从键盘 / 文件 / 字符串读入 | `格式化输入`(scanf) / `从文件格式化输入`(fscanf) / `从字符串格式化输入`(sscanf) |
| 文件的其他操作 | `删除文件` / `重命名文件` / `临时文件` / `临时文件名` / `取文件位置` / `回到开头` / `放回字符` / `到文件尾` / `文件有错` / `清错误` / `设置缓冲` / `输出错误信息` |

> 名字按**教材口径**定（`printf` = 格式化输出），依据是「**先查既有译名表、再新造**」的规矩：
> `格式` / `输出` / `输入` 都在诊断表里，`限长` 沿 `限时共享互斥量`（`shared_timed_mutex`）的构词。
> **`v` 前缀那一族**（`vprintf` 一家）也有中文名了：`标准::可变参数表`（= `va_list`）＋
> `可变参数表格式化输出` / `可变参数表格式化到字符串` … 见下面的例子。
> **边界（不是欠账）**：`gets` 做不了（C11 已删除，这套 STL 里 `std::gets` 根本不存在）；
> `va_start` 那族宏只能 `#定义`，用时**不加** `标准::`。
> 还没做：**Windows 系统 API** 的计划内批次**已全部做完**（五批 104 个名字，见下一节）；
> 明确不做的清单也在下一节末尾。

**自己写变参函数时**（`va_list` 那一族）：

```cpp
#包含 <C变参>
#包含 <C标准输入输出>
整数 求和(整数 个数, ...){
    标准::可变参数表 表;              // va_list
    开始可变参数表(表, 个数);          // va_start（宏，不加 标准::）
    整数 合计 = 0;
    对于 (整数 甲 = 0; 甲 < 个数; ++甲) { 合计 += 取可变参数项(表, 整数); }   // va_arg
    结束可变参数表(表);                // va_end
    返回 合计;
}
整数 主函数(){ 返回 求和(3, 1, 2, 3) - 6; }
```

> 还有 `复制可变参数表`(va_copy)：复制出来的那份**停在开头**，所以能把同一批实参重读一遍
> （这一点容易搞错，`tools\make_zhc.ps1` 的 `C变参` 用例断言的就是它：读出来是 7、7、9）。

### Windows 系统 API 也有中文名了（2026-10-04 起，分批做）

系统 API（`SetConsoleOutputCP` / `CreateFileW` / `WriteFile`…）和 C 运行库一样在系统的 DLL 里，
所以我们用**同一种办法**：头名汉语化、每个函数加一个中文名转发到 `…W` 真函数。

```cpp
#包含 <Windows系统>
整数 主函数(){
    标准::设置控制台输出代码页(65001);                          // SetConsoleOutputCP：让控制台按 UTF-8 收

    标准::句柄 出 = 标准::取标准句柄(标准::标准输出句柄);        // GetStdHandle(STD_OUTPUT_HANDLE)
    标准::双字 写了 = 0;

    如果 (文 == 标准::无效句柄) { 返回 1; }                     // INVALID_HANDLE_VALUE
    标准::写句柄(文, "abc", 3, &写了, 空指针);                  // WriteFile
    标准::关闭句柄(文);                                        // CloseHandle
    标准::睡眠(0);                                            // Sleep
    标准::设置最后错误(0);
    如果 (标准::取最后错误() != 0) { 返回 2; }                  // SetLastError / GetLastError
    返回 0;
}

>
> ⚠ 用 `等待单个对象` / `等待多个对象` 时**别把 `无限等待` 写进会真跑到的路径** ——
> 它会一直等下去。要"等一会儿就返回"就给毫秒数（`标准::等待超时` 就是那种情况的返回值）：

```cpp
#包含 <Windows系统>
整数 主函数(){
    标准::句柄 事 = 标准::创建事件(空指针, 真值, 假值, 空指针);   // 手动重置、未触发
    如果 (事 == 标准::无效句柄) { 返回 1; }
    标准::设置事件(事);
    标准::双字 果 = 标准::等待单个对象(事, 1000);               // 最多等 1 秒
    如果 (果 != 标准::等待成功) { 返回 2; }
    标准::关闭句柄(事);

    标准::临界区 区;                     // CRITICAL_SECTION：初始化 → 进入 → 离开 → 删除
    标准::初始化临界区(&区);
    标准::进入临界区(&区);
    标准::离开临界区(&区);
    标准::删除临界区(&区);
    返回 0;
}
```

**内存**：`申请虚拟内存`(`VirtualAlloc`) 是页级的（所以要说清"提交/保留"与"页保护"），
堆那一族则是在**堆句柄**上分配（`从堆分配` ≠ `malloc`，它多一个堆参数）：

```cpp
#包含 <Windows系统>
整数 主函数(){
    空型* 页 = 标准::申请虚拟内存(空指针, 4096,
                    标准::提交内存 | 标准::保留内存, 标准::可读写页);   // 4KB，可读写
    如果 (页 == 空指针) { 返回 1; }
    ((字符*)页)[0] = 'a';
    标准::内存基本信息 信息;
    如果 (标准::取内存信息(页, &信息, sizeof(标准::内存基本信息)) == 0) { 返回 2; }
    标准::双字 旧保护 = 0;
    标准::设置内存保护(页, 4096, 标准::可读写页, &旧保护);
    如果 (标准::释放虚拟内存(页, 0, 标准::释放区域) == 0) { 返回 3; }  // 释放必须 size=0 + 释放区域

    标准::句柄 堆 = 标准::取进程堆();                    // 也可以 `标准::创建堆(0,0,0)` 建私有的
    空型* 块 = 标准::从堆分配(堆, 0, 64);
    如果 (块 == 空指针) { 返回 4; }
    空型* 大块 = 标准::调整堆内存(堆, 0, 块, 128);        // 失败时原块仍有效
    如果 (大块 == 空指针) { 返回 5; }
    如果 (标准::释放堆内存(堆, 0, 大块) == 0) { 返回 6; }
    返回 0;
}
```

**注册表与环境变量**：⚠ 注册表那一族在 `Advapi32.dll` 里，**要自己链 `advapi32.lib`**
（MSVC 也一样；`<Windows系统>` 不替你自动链 —— 本项目只加名字，不改链接语义）：

```cpp
#包含 <Windows系统>
#pragma comment(lib, "advapi32.lib")     // 命令行写 -ladvapi32 也一样
整数 主函数(){
    标准::写环境变量(L"我的变量", L"甲");                  // SetEnvironmentVariableW
    宽字符 缓冲[64] = {0};
    如果 (标准::读环境变量(L"我的变量", 缓冲, 64) == 0) { 返回 1; }
    标准::写环境变量(L"我的变量", 空指针);                 // 传空指针 = 删除这个变量

    标准::注册表键 键 = 空指针;                            // HKEY，与 句柄(HANDLE) 不是一种类型
    如果 (标准::创建注册表键(标准::当前用户键, L"Software\\我的程序", 0, 空指针, 0,
                              标准::键可读 | 标准::键可写, 空指针, &键, 空指针) != 0) { 返回 2; }
    标准::双字 值 = 7;
    标准::写注册表值(键, L"数", 0, 标准::双字值类型, (常量 无符号 字符*)&值, sizeof(值));
    标准::双字 读回 = 0, 长度 = sizeof(读回), 值类型 = 0;   // ⚠ 别把变量取名 `类型`：它是中文关键字
    标准::读注册表值(键, L"数", 空指针, &值类型, (无符号 字符*)&读回, &长度);
    如果 (读回 != 7) { 返回 3; }
    标准::关闭注册表键(键);
    返回 0;
}
```

> 两个类型细节（都实测过）：`读注册表值` / `写注册表值` 的数据参数是 `LPBYTE`
> （`unsigned char*`）⇒ 要写 `(无符号 字符*)&值`；`Reserved` 那类 `DWORD` 参数写 `0`，
> **不能写 `空指针`**（`nullptr` 转不了 `DWORD`）。

**动态库与计时**：`加载动态库` 的库名是**宽**字符串，而 `取函数地址` 的函数名是**窄**字符串
（它是唯一没有 `W` 变体的 API）；取回来的 `FARPROC` 要**自己转成正确的函数指针类型**才能调用：

```cpp
#包含 <Windows系统>

    标准::取性能频率(&频率);
    标准::取性能计数(&起刻);
    标准::睡眠(1);
    标准::取性能计数(&止刻);
    如果 (止刻.QuadPart <= 起刻.QuadPart) { 返回 4; }

### 窗口 GUI：`<窗口>`（第四轨道，2026-10-05 起：第一批最小一块 + 第二批消息）

GUI 这一批与前面不同：**结构体的成员名不能加中文别名**（C++ 不给"别人的类型"加别名成员），
所以走「**复制体 + 包装**」—— 我们自己复制一份结构体，**中文成员名与英文成员名同时可用**
（同一个存储），转换在库里替你做一次。**微软的头一个字节没动。**

```cpp
#包含 <窗口>
#包含 <C标准整数>
#pragma comment(lib, "user32.lib")
整数 收到消息数 = 0;
标准::指针整数 我的窗口过程(标准::窗口句柄 窗, 无符号 整数 消息,
                          标准::无符号指针整数 甲, 标准::指针整数 乙){
    收到消息数++;
    如果 (消息 == WM_DESTROY) { PostQuitMessage(0); 返回 0; }
    返回 DefWindowProcW(窗, 消息, 甲, 乙);
}
整数 主函数(){
    标准::窗口类 类 = {0};                  // WNDCLASSEXW 的复制体
    类.cbSize        = sizeof(标准::窗口类);
    类.窗口过程      = 我的窗口过程;         // 中文成员名
    类.lpfnWndProc   = 我的窗口过程;         // 英文成员名（同一存储，两种写法都对）
    类.hInstance     = GetModuleHandleW(空指针);
    类.lpszClassName = L"我的窗口类";
    如果 (!标准::注册窗口类(类)) { 返回 1; }
    标准::窗口句柄 窗 = 标准::创建消息窗口(L"我的窗口类", L"标题");  // message-only：不弹窗
    如果 (窗 == 空指针) { 返回 2; }
    PostMessageW(窗, WM_CLOSE, 0, 0);
    标准::消息 消 = {0};                    // MSG 的复制体
    每当 (标准::取消息(消) > 0) {            // 收的是我们的 `消息`，不是 SDK 的 `MSG`
        如果 (消.消息值 == 标准::关闭消息) { 收到消息数++; }   // 中文成员名 + 中文消息码
        (空型)消.hwnd; (空型)消.message; (空型)消.wParam;      // 英文成员名照旧可用
        标准::翻译消息(消);                   // TranslateMessage
        标准::派发消息(消);                   // DispatchMessage
    }
    返回 0;
}
```

⚠ 四条注意：

1. **要链 `user32.lib`**（GUI 函数在 user32.dll；命令行 `-luser32`，或像注册表那样写
   `#pragma comment(lib, "user32.lib")`）。产品头**不替用户自动链**（铁律①）。
2. **我们的 `窗口类` / `消息` ≠ 微软的 `WNDCLASSEXW` / `MSG`**（布局相同、类型不同）⇒ 与原生 Win32 代码混用要显式转换；
   这是"复制体"这条路的代价（与 `标准::向量` vs `std::vector` 同源，见方案 §3.4.4）。
3. **布局漂移当场编译报错**：产品头里有一张断言表（`sizeof` + 逐成员 `offsetof` 对拍）——
   SDK 一升级改了字段就编不过，**这是故意的**（`窗口类` 与 `消息` 各一张）。
4. **include 顺序随便**：先 `#include <windows.h>` 再 `#包含 <窗口>` 也编得过（实测）。
   原先不行 —— `rpcndr.h:202` 的全局 `typedef unsigned char byte;` 会与标准库那份撞名
   （实测 16 条「对（名字）'byte' 的引用有歧义」）。§18.31 已把《通用内部件》里那 5 处
   `byte` 限定成 `_STD byte`；GUI 那条用例就是**按"微软头在前"的顺序**写的，防止它回退。

### 第三批：一个控件（按钮）—— 真实窗口但**不显示**，所以不弹窗、也不要消息泵

```cpp
#包含 <窗口>
#包含 <C标准整数>
#pragma comment(lib, "user32.lib")
整数 收到点击 = 0;
标准::窗口句柄 我的按钮 = 空指针;
标准::指针整数 窗口过程(标准::窗口句柄 窗, 无符号 整数 消息, 标准::无符号指针整数 甲, 标准::指针整数 乙){
    如果 (消息 == 标准::命令消息
        && (整数)(甲 & 0xFFFF) == 1001                        // 控件标识（在 甲 的低 16 位）
        && (整数)((甲 >> 16) & 0xFFFF) == 标准::点击通知) {     // 通知码 = BN_CLICKED
        收到点击++;
    }
    返回 DefWindowProcW(窗, 消息, 甲, 乙);
}
整数 主函数(){
    标准::窗口类 类 = {0};
    类.cbSize = sizeof(标准::窗口类);
    类.窗口过程 = 窗口过程;
    类.hInstance = GetModuleHandleW(空指针);
    类.lpszClassName = L"我的窗口类";
    如果 (!标准::注册窗口类(类)) { 返回 1; }
    标准::窗口句柄 窗 = CreateWindowExW(0, L"我的窗口类", L"标题", 0, 0, 0, 240, 120,
                                        空指针, 空指针, 类.hInstance, 空指针);   // 不 ShowWindow ⇒ 不弹窗
    如果 (窗 == 空指针) { 返回 2; }
    我的按钮 = 标准::创建按钮(窗, L"点我", 1001, 10, 10, 100, 32);
    如果 (我的按钮 == 空指针) { 返回 3; }
    标准::发送消息(我的按钮, 标准::按钮点击, 0, 0);      // 同步：窗口过程里会收到 WM_COMMAND
    标准::销毁窗口(我的按钮); 标准::销毁窗口(窗);
    返回 收到点击 == 1 ? 0 : 4;
}
```

> ⚠ **`WM_COMMAND` 的哪一半是什么**：`甲`（`wParam`）的**低 16 位是控件标识**、
> **高 16 位是通知码**（`点击通知` = `BN_CLICKED` = 0）；`乙`（`lParam`）是**子窗口句柄**。
> 这条是实测踩出来的（我第一版按 `乙` 取码，打出来的是句柄的两半）。

现在有：`窗口类`、`消息` + 消息码 `销毁消息` / `关闭消息` / `绘制消息` / `退出消息` / `计时器消息`
+ `注册窗口类` / `创建消息窗口` / `取消息` / `翻译消息` / `派发消息`
+ **第三批**：`显示窗口` / `更新窗口` / `销毁窗口` / `设置窗口标题` / `取窗口标题` / `取窗口矩形` /
`发送消息` / `投递消息` / **`创建按钮`** / `消息框`（阻塞，只在永假分支）
+ 常量 `子窗口` / `可见` / `命令消息` / `点击通知` / `按钮点击` / `隐藏`
（以上都在真跑用例里：message-only window + 一个**隐藏**的真实窗口 + 按钮，
不弹窗、不阻塞、不需要消息泵）。GDI 与其它控件按批推进；
其余消息码**等有真实用例再加**（本项目一贯口径：没有真实用例不空写）。

### 绘图（GDI）：`<绘图>`（第四轨道第四批，2026-10-05）

GDI（画图那一套）**另起一个头**：函数在 `gdi32.dll`、声明在 `wingdi.h`，与"窗口"是两件事。
机制与 `<窗口>` 完全一样：**加中文名、微软的头一个字节没动**。
⚠ **要链 `gdi32.lib`**（命令行 `-lgdi32`，或像下面这样写 `#pragma comment(lib, "gdi32.lib")`）。

```cpp
#包含 <窗口>
#包含 <绘图>
#包含 <C标准整数>
#pragma comment(lib, "user32.lib")
#pragma comment(lib, "gdi32.lib")
标准::画刷 白刷 = 空指针;
整数 画过 = 0;
标准::指针整数 窗口过程(标准::窗口句柄 窗, 无符号 整数 消息, 标准::无符号指针整数 甲, 标准::指针整数 乙){
    如果 (消息 == 标准::绘制消息) {                     // WM_PAINT
        PAINTSTRUCT 绘制信息 = {0};
        标准::设备上下文 上下文 = 标准::开始绘制(窗, &绘制信息);
        如果 (上下文 != 空指针) {
            RECT 框 = {0, 0, 120, 60};
            标准::填充矩形(上下文, &框, 白刷);
            标准::画矩形(上下文, 0, 0, 100, 40);
            标准::画椭圆(上下文, 0, 0, 60, 30);
            标准::画线(上下文, 0, 0, 100, 40);           // MoveToEx + LineTo 合成一个名字
            标准::输出文本(上下文, 4, 4, L"你好", 2);
            画过++;
        }
        标准::结束绘制(窗, &绘制信息);
    }
    返回 DefWindowProcW(窗, 消息, 甲, 乙);
}
整数 主函数(){
    标准::窗口类 类 = {0};
    类.cbSize = sizeof(标准::窗口类);
    类.窗口过程 = 窗口过程;
    类.hInstance = GetModuleHandleW(空指针);
    类.lpszClassName = L"我的绘图层";
    如果 (!标准::注册窗口类(类)) { 返回 1; }
    标准::窗口句柄 窗 = CreateWindowExW(0, L"我的绘图层", L"绘图", 0, 0, 0, 200, 100,
                                        空指针, 空指针, 类.hInstance, 空指针);   // 不 ShowWindow ⇒ 不弹窗
    如果 (窗 == 空指针) { 返回 2; }
    白刷 = 标准::创建实心画刷(0x00FFFFFF);
    标准::设备上下文 上下文 = 标准::取窗口设备上下文(窗);
    如果 (上下文 != 空指针) {
        (空型)标准::设文本颜色(上下文, 0x000000FF);
        标准::画矩形(上下文, 0, 0, 40, 20);
        (空型)标准::取设备能力(上下文, 8);                // HORZRES
        标准::释放设备上下文(窗, 上下文);
    }
    标准::无效化矩形(窗, 空指针, 1);
    标准::发送消息(窗, 标准::绘制消息, 0, 0);             // 见下面第 2 条注意
    标准::删除绘图对象((标准::绘图对象)白刷);
    标准::销毁窗口(窗);
    返回 (画过 >= 1) ? 0 : 3;
}
```

⚠ 三条注意：

1. **要链 `gdi32.lib`**；`创建实心画刷`／`创建画笔` 拿到的对象用完要 `删除绘图对象`（GDI 对象不是 C++ 对象）。
2. **隐藏窗口上 `无效化矩形` + `更新窗口` 投不出 `WM_PAINT`**（实测：paints=0）。要让窗口过程真的走一遍，
   就**同步投**（例子里 `标准::发送消息(窗, 标准::绘制消息, 0, 0)`）—— 这样窗口一直隐藏、也不弹窗；
   真要显示才 `标准::显示窗口(窗, 1)`（= `SW_SHOWNORMAL`）。
3. `画线` 是**两个 SDK 调用的合成**（`MoveToEx` + `LineTo`）：中文侧只给你一个名字，
   这就是"包装层"的价值。`PAINTSTRUCT` / `RECT` **照用 SDK 的**（简单结构体不做复制体，
   与 `POINT` 同口径）；`颜色参考` 只是 `COLORREF` 的**别名**，与 SDK 是同一个类型。

⚠ 四条注意：

1. 控件必须建在**真实窗口**里（message-only window 不行）；不 `ShowWindow` 就**不弹窗**。
2. **控件文本走 `取窗口标题` / `设置窗口标题`** —— 那正是 `GetWindowTextW` / `SetWindowTextW`，
   编辑框、按钮、静态文本都通用；勾选与列表项则走**消息**（`设置勾选` / `取勾选` / `添加列表项` / …）。
3. **`启用窗口` 的返回值不要当判据**（实测：本来启用时 `EnableWindow(h, 0)` 返回 **0**、
   再 `EnableWindow(h, 1)` 返回 **1**，与"返回之前的状态"的常见说法不符）⇒ 判**状态**用 `是否启用`。
4. `取窗口位置`(`GetWindowRect`，**屏幕**坐标) 与 `取窗口矩形`(`GetClientRect`，**客户区**) 是两件事。

### 菜单：`标准::菜单句柄`（第四轨道第六批，2026-10-05）

菜单是**挂在窗口上的数据**（不是控件），所以**隐藏窗口上也能建、能挂、能查**，不需要弹窗。

```cpp
#包含 <窗口>
#包含 <C标准整数>
#pragma comment(lib, "user32.lib")
整数 主函数(){
    标准::窗口类 类 = {0};
    类.cbSize = sizeof(标准::窗口类);
    类.hInstance = GetModuleHandleW(空指针);
    类.lpszClassName = L"我的菜单层";

    标准::窗口句柄 窗 = CreateWindowExW(0, L"我的菜单层", L"菜单", 0, 0, 0, 240, 120,
                                        空指针, 空指针, 类.hInstance, 空指针);   // 不 ShowWindow ⇒ 不弹窗
    如果 (窗 == 空指针) { 返回 2; }
    标准::菜单句柄 菜单 = 标准::创建菜单();
    标准::菜单句柄 子菜单 = 标准::创建弹出菜单();
    如果 (菜单 == 空指针 || 子菜单 == 空指针) { 返回 3; }
    如果 (!标准::追加菜单项(子菜单, 标准::字符串项, 11, L"子项")) { 返回 4; }
    如果 (!标准::追加菜单项(菜单, 标准::字符串项, 1, L"打开")) { 返回 5; }
    如果 (!标准::追加菜单项(菜单, 标准::弹出项, (标准::无符号指针整数)子菜单, L"更多")) { 返回 6; }
    如果 (!标准::设置窗口菜单(窗, 菜单)) { 返回 7; }

    标准::删除菜单(子菜单);

1. **`TrackPopupMenu`（右键弹出菜单）故意没做名字** —— 它会**阻塞**、需要消息泵（同 `消息框` 的纪律：
   挂死比红更贵）。要做的话是后续批次的事，且必须想清楚怎么在用例里不阻塞。
2. 菜单项数量、子菜单都用**句柄**查询（`取菜单项数` / `取子菜单`）；用完**先 `设置窗口菜单(窗, 空指针)`

### 组合框 / 进度条：通用控件（第四轨道第七批，2026-10-06）

```cpp
#包含 <窗口>
#包含 <绘图>
#包含 <C标准整数>
#pragma comment(lib, "user32.lib")
#pragma comment(lib, "comctl32.lib")        // 通用控件（进度条）在 comctl32.dll
整数 主函数(){

    标准::窗口句柄 组 = 标准::创建组合框(窗, L"", 1006, 10, 10, 140, 120);

    如果 (组 == 空指针 || 进 == 空指针) { 返回 4; }
    标准::发送消息(组, 标准::添加组合项, 0, (标准::指针整数)L"甲");
    标准::发送消息(组, 标准::添加组合项, 0, (标准::指针整数)L"乙");
    如果 ((整数)标准::发送消息(组, 标准::取组合项数, 0, 0) != 2) { 返回 5; }
    标准::发送消息(组, 标准::选择组合项, 1, 0);
    如果 ((整数)标准::发送消息(组, 标准::取组合选择, 0, 0) != 1) { 返回 6; }
    标准::发送消息(进, 标准::设进度范围, 0, (标准::指针整数)100);
    标准::发送消息(进, 标准::设进度值, 42, 0);
    如果 ((整数)标准::发送消息(进, 标准::取进度值, 0, 0) != 42) { 返回 7; }
    如果 (标准::取系统度量(标准::屏幕宽) <= 0) { 返回 8; }        // 这几个常量就是给它用的

```

⚠ 三条注意：

1. **进度条是"通用控件"**（在 `comctl32.dll`）：要链 **`comctl32.lib`**，
   并且**先 `初始化通用控件(标准::控件进度条)`** 再 `创建进度条`。
   `commctrl.h` 不用你写 —— **`<窗口>` 已经替你引了**（产品头里在 `inc` 列表里）。
2. 组合框 / 进度条拿到的都是**普通窗口句柄**（`标准::窗口句柄`），一律用**消息**操作：
   `添加组合项` / `取组合项数` / `选择组合项` / `取组合选择`、`设进度范围` / `设进度值` / `取进度值`。
3. **`取系统度量` 在 `<绘图>` 里**（不在 `<窗口>`），所以要用它就得 `#包含 <绘图>`；
   索引常量：`屏幕宽` / `屏幕高` / `标题栏高` / `窗口边框宽` / `图标宽` / `图标高` / `显示器数`。

### 位图 / 双缓冲 / 字体（第四轨道第八批，2026-10-06）

双缓冲就三步：**建内存 DC → 建兼容位图并选进去 → 画完 `位块传送` 到窗口 DC**。

```cpp
#包含 <窗口>
#包含 <绘图>
#包含 <C标准整数>
#pragma comment(lib, "user32.lib")
#pragma comment(lib, "gdi32.lib")
整数 主函数(){
    标准::窗口类 类 = {0};
    类.cbSize = sizeof(标准::窗口类);
    类.hInstance = GetModuleHandleW(空指针);
    类.lpszClassName = L"我的双缓冲层";
    如果 (!标准::注册窗口类(类)) { 返回 1; }
    标准::窗口句柄 窗 = CreateWindowExW(0, L"我的双缓冲层", L"画", 0, 0, 0, 240, 120,
                                        空指针, 空指针, 类.hInstance, 空指针);   // 不 ShowWindow ⇒ 不弹窗
    如果 (窗 == 空指针) { 返回 2; }
    标准::设备上下文 窗上下文 = 标准::取窗口设备上下文(窗);
    标准::设备上下文 内存 = 标准::创建兼容设备上下文(窗上下文);
    标准::位图 图 = 标准::创建兼容位图(窗上下文, 240, 120);
    如果 (内存 == 空指针 || 图 == 空指针) { 返回 3; }
    标准::绘图对象 旧图 = 标准::选择对象(内存, (标准::绘图对象)图);   // 位图选进内存 DC
    标准::设像素(内存, 4, 4, 0x0000FF00);                          // 直接点一个像素
    标准::画笔 笔 = 标准::创建画笔(标准::实心笔, 2, 0x00FF0000);
    标准::绘图对象 旧笔 = 标准::选择对象(内存, (标准::绘图对象)笔);
    标准::画线(内存, 0, 0, 200, 100);
    标准::字体 字 = 标准::创建字体(-16, 0, 700, L"SimSun");          // 14 个形参压成 4 个
    标准::绘图对象 旧字 = 标准::选择对象(内存, (标准::绘图对象)字);
    整数 文宽 = 0, 文高 = 0;
    如果 (!标准::取文本范围(内存, L"你好", 2, &文宽, &文高)) { 返回 4; }
    如果 (!标准::位块传送(窗上下文, 0, 0, 240, 120, 内存, 0, 0, 标准::位传送复制)) { 返回 5; }
    整数 图宽 = 0, 图高 = 0;
    如果 (!标准::取位图尺寸(图, &图宽, &图高)) { 返回 6; }
    标准::选择对象(内存, 旧字); 标准::选择对象(内存, 旧笔); 标准::选择对象(内存, 旧图);
    标准::删除绘图对象((标准::绘图对象)字); 标准::删除绘图对象((标准::绘图对象)笔);
    标准::删除绘图对象((标准::绘图对象)图);
    标准::删除兼容设备上下文(内存);
    标准::释放设备上下文(窗, 窗上下文);
    标准::销毁窗口(窗);
    返回 0;
}
```

> **从文件装入位图**：`标准::装入位图(L"图片.bmp", 0, 0)`（内部用 `LoadImageW` + `从文件装入`）。
> 想自己造一张图来试，可以 `标准::创建文件` / `标准::写句柄` 写一个 24 位 BMP（用例里就是这么真跑的）。

⚠ 三条注意：

1. **GDI 对象用完要删**：`删除绘图对象`（位图/画笔/字体）＋ `删除兼容设备上下文`（内存 DC）；
   窗口 DC 用 `释放设备上下文`。**选进 DC 的对象，删之前先把旧对象选回去**（用例就是这么做的）。
2. `BITMAP` / `SIZE` 这类简单结构体**照用 SDK 的**（我们不做复制体）；
   `取位图尺寸` / `取文本范围` 已经把结构体藏在库里，你只给两个 `整数*`。
3. `标准::删除文件`（删临时文件用）是 **C 运行库那一轨**的 `remove`，
   所以要 `#包含 <C标准输入输出>`，而且它收**窄**字符串。

### clangd（负责语法高亮与补全）

clangd 只做语法分析、不生成代码，它的关键字表来自

三种选择，按"要不要额外装东西"排列：

| 方案 | 标红 | 编译 | 说明 |
|---|---|---|---|
| **CLion**（已装） | 关掉即可 | 正常 | 换不了 clangd（见下）；取消勾选「显示来自 clangd 的错误和警告」就不标红 |

| **VS Code + clangd 扩展** | 不标红 | 正常 | 唯一能同时拿到中文补全/跳转的方案，需要另装 VS Code |

#### 为什么 CLion 换不了 clangd

CLion 强制使用它自带的那份 clangd，**没有"自定义 clangd 路径"这个设置**：
`ClangdSettings$StoredState` 里只有 `clangdEnabled`、`clangdShowErrors`、
`clangTidyViaClangd`、`navigationViaClangd`、`parameterInfoViaClangd`、
`formatViaClangd`、`completionType`、`clangdMessagesFilters` 八项；
路径在 `ProcessServerConnectionProvider` 里写死为 `<IDE>/bin/clang/<平台>/bin/clangd`。

而且那份 clangd 是 **JetBrains 改过的深度分支**（实测版本 23.0.0git，二进制里有
`clionDidOpen`、`clionCompletion`、`clionFindUsages`、`clionGetIndexSummary`、
`ClionClangdLSPServer`、`clion_clangd_inmemory_directory` 等 369 个专有标识符），
拿我们构建的上游 clangd 去替换会把 CLion 的语言服务集成打坏。
**所以不要替换 CLion 里的那个 clangd.exe。**

#### CLion 上试过什么，为什么到此为止

试过两条注入路线。两条都能让 **CLion 那个 clangd 二进制本身**正确解析中文源码，
但 **CLion 2026.1.2 里始终仍然标红**，已放弃：

1. **`.clangd` 的 `CompileFlags.Add`** —— 读 clangd 源码可知，它是在 `CommandMangler`
   里应用的，而 `CommandMangler` 只在 `GlobalCompilationDatabase::getCompileCommand`
   这一层被调用（`clang-tools-extra/clangd/GlobalCompilationDatabase.cpp:813/823`）。
   CLion 把编译命令**直接推**给 clangd，绕过了这一层。
   实测：CLion 的 clangd 在 `--check` 模式下会打印 `Loading config file at ...\.clangd`
   且命令里有 `-include`；CLion 实时服务里两者都没有。
2. **CMake `target_compile_options(-include <垫片>)`** —— 标志确实进了编译命令
   （`cmake-build-*/compile_commands.json` 里能看到），CLion 也重新配置过（23:59:48），
   但标红依旧。

**旁证**：把垫片用 `#include` 直接写进源文件（这样不经过任何标志传递），再用 CLion
那个 clangd 加 `--enable-config=0`、不给编译数据库跑 `--check`，结果是
`All checks completed, 0 errors`。也就是说 **clangd 本身完全没问题**，问题在 CLion
这一侧的管道——2026.1 是 nova 架构，clangd 跑在 ReSharper 后端进程里，
它没有把源文件的最新内容交给 clangd。这一段没有继续深挖。

**当前状态**：源文件与 `CMakeLists.txt` 已全部还原到我介入之前的样子，
`.clangd` 已删除，没有留下任何东西。

**Q：报错 `error: expected ')'` 但代码看起来没错？**
A：检查关键字与相邻标识符之间是否漏了空格：`返回甲` 要写成 `返回 甲`。

**Q：报 `unexpected character` 或一堆奇怪错误？**
A：源文件不是 UTF-8。改成 UTF-8 保存即可。

**Q：程序跑起来中文是乱码（显示成「涓枃」这种）？**
A：这**不是文件编码问题，是控制台编码问题**。本编译器用 UTF-8 作执行字符集，
字符串常量是 UTF-8 字节；而中文 Windows 的 cmd / 控制台默认按 GBK(936) 解码，
于是把 UTF-8 字节当 GBK 读，就花了。两种解决办法：

1. **程序里加两行（推荐，一劳永逸）**：

```cpp
#include <windows.h>

整数 main() {
    SetConsoleOutputCP(CP_UTF8);   // 让控制台按 UTF-8 解码
    ...
}
```

2. **运行时先切代码页**：`chcp 65001` 之后再运行程序。

`zhcpp-demo\demo.cpp` 一直带着这两行；`中文项目示例\示例.cpp` 与
`examples\expr_calc.cpp` 也已补上。

> 顺带说明：**不能靠编译器解决**。clang 不接受 `-fexec-charset=GBK`
> （实测报 `invalid value 'GBK'`），所以小熊猫C++ 里「将可执行文件中的字符串
> 转码为」那一项对我们这套编译器无效，必须关掉（我们的配置集已经关了）。
> 在 CLion 里看不到这个问题，是因为它的运行输出窗口本身就是按 UTF-8 解析的。

**Q：`std` 是什么意思？它不是关键字吗？为什么到处都是它？**
A：**它不是关键字，是「名字」。**

- **关键字**是语言的一部分，一共 **99** 个（见第五节），都有中文别名：
  `如果`、`类型`、`返回`、`名域`、`使用`…
- **`std` 是 C++ 标准库所在名域的「名字」**（std = standard）。标准库头文件里写的
  就是 `namespace std { … }`——它和你自己写 `名域 我的名域 { }` 起名字没有本质区别。

| 写法 | 是什么 | 有中文别名吗 |
|---|---|---|
| `名域` | 关键字（= namespace） | ✅ |
| `std` | 标准库名域的名字 | ❌ 别人起的名字 |
| `::` | 作用域解析运算符 | 不是关键字 |
| `printf` / `vector` / `main` | 名字 | ❌ 连 `main` 也不是关键字 |

为什么标准库不能中文化？那些名字长在标准库自己的源码里；要改就得改整套标准库，
那样就不再是"共用同一套 C++ 生态"了——第三方库、调试器、现有代码都会受影响。
本项目的设计正是**关键字中文化、生态保持原样**。

实用技巧：嫌 `std::` 啰嗦可以把它引入——`使用 名域 std;` 等价于 `using namespace std;`。
可运行的对照例子见 `examples\keywords_vs_names.cpp`。

**Q：中文代码和英文代码能混在一个文件里吗？**
A：可以，任意比例混写都行，两者产出完全相同的 AST。

**Q：能不能把标准库也复制一份、改成中文（比如 `std::向量`）？**
A：技术上做得到，但代价极大，而且会摧毁"不锁定"这个性质。关键区别在于**换的是什么**：

| 改动对象 | 换掉的是 | 代价 |
|---|---|---|
| 关键字 `如果` / `整数` | **拼写** | 同一个 token，零代价（已做到） |
| 库名字 `std::vector` | **类型身份** | `标准::向量` 与 `std::vector` 变成**两种不同的类型** |

一旦库名字改了：

- 名字修饰（mangling）变了 → 和**预编译的**第三方库对不上
  （实测**比这轻**：只有"把 `std::vector<T>` 写死在模板推导位置"的接口接不了，可显式转换绕过）；
- `std::string` 这类在库里显式实例化的类型，两套库的 `string` 不能直接互相传参（可转换）；
- 异常 / RTTI 跨边界失配 —— **注意方向**（2026-09-27 实测更正）：你的（派生的）异常
  **能**被第三方的 `捕获 (std::exception&)` 抓到；但**第三方抛的** `std::runtime_error`，
  用你的 `捕获 (标准::运行时错误&)` **抓不到**（base→derived 永远不通），
  而且**不报编译错**，异常直接逃出去；
- 而 **MSVC 的 STL 是预编译的 DLL，没法重编**，只能改去 fork libc++，那是另一个独立大工程；
- 规模实测：公开名字 **2,128 个**，要抄 **112 个文件 / 120,263 行**，且每次跟进上游都要重新同步。

**做法有两条，各管一类**（2026-09-27 定案，详见 `docs\标准库汉化\标准库汉化方案.md`）：

```cpp 不编译
0
// 路一：只要中文类型名、要零风险、要类型身份不变 —— 用别名
模板 <类型名 元素> 使用 向量 = std::vector<元素>;
使用 字符串     = std::string;
使用 运行时错误 = std::runtime_error;   // 异常这类【必须】走别名，见下

// 路二：要中文【成员名】（表.压入(1)） —— 抄一份 + 派生兼容层
```

**路一**里 `标准::向量<int>` **就是** `std::vector<int>`（同一类型、同一 ABI），
可以直接传给只认 `std::vector` 的第三方库 —— 这是 `tools\library_plan_evidence\run.py`
现场断言过的。

**路二**换来的是中文成员名，代价是 `标准::向量<int>` 成了**另一个类型**。实测它仍能传给
非模板 / 泛型 / 迭代器接口（靠转换运算符），只有一种接口接不了：把 `std::vector<T>`
**写死在模板推导位置**的（`模板 <类型名 T> 空型 f(常量 std::vector<T>&)` ——
模板推导不考虑用户定义的转换）。绕过它就是显式转换一次。

**⚠️ 有一条硬约束**：**异常、RTTI、跨预编译库的类型**（`std::string`、`path`…）
**只能走路一**。理由是实测出来的：`捕获 (X&)` 能接住抛出的 `Y`，当且仅当 `Y` 可转换为 `X`，
所以 **base → derived 永远不通** —— 第三方抛的 `std::runtime_error`，
用 `捕获 (标准::运行时错误&)` **抓不到**，而且**不报编译错**，异常直接逃出去。

> 两个真实限制：**类型可以起别名，函数只能内联包一层**——`使用 std::sort;` 只搬名字
> 不改名，想要「排序」必须自己写一层内联转发（零开销，但它是新函数）；变参函数
> （`printf` 这类）没法完美转发，只能原样引入。

**Q：用中文关键字写的代码，能交给别人、或拿到没有这个编译器的机器上编译吗？**
A：**能，而且不用改一行业务逻辑。**

关键字改动只在**词法层**（token 拼写），语法树、ABI、运行时都没变。所以只要把关键字
按表换回英文，它就变成一份普通 C++ 文件。工具已经写好：

```powershell
python E:\Chinese++\tools\zh_to_en.py 我的程序.cpp 我的程序.english.cpp
```

替换是**精确**的：只替换「整段等于某个中文关键字」的标识符，你自己起的中文名字
（类型名、变量名）原样保留。实测：拿 VS 自带的**原版 clang 19.1.5** 编译转换后的
`expr_calc.cpp`——

| | 原版 clang 19.1.5 |
|---|---|
| 编译中文关键字版本 | ❌ `error: unknown type name '名域'` |
| 编译机械转换后的英文版本 | ✅ 退出码 0 |
| 运行输出 | 与中文版**逐字节一致** |

也就是说：**中文源码没有锁定**。反过来，这也意味着中文关键字不影响性能、不影响
调试信息、不影响与任何现有 C++ 库互操作。

**Q：编译出来的程序性能有影响吗？**
A：没有。中文关键字在词法阶段就映射到了与英文相同的 token，之后的编译流程完全一致。

**Q：能把它装到别的机器上吗？**
A：目前只有本机构建产物，运行时依赖 MSVC 运行时库（`msvcp140.dll` 等）。要分发需一并打包或使用静态运行时。

## 九、重新构建 clangd

构建树在 `E:\Chinese++\build\`（CMake + Visual Studio 生成器）。
补完 clang-tools-extra 并产出 `clangd.exe` 用这个脚本：

```powershell
powershell -File E:\Chinese++\tools\build_clangd.ps1
```

它会自己按当前可用内存算出并发度，失败就逐级降档重试（8 → 4 → 2 → 1）。

### 为什么不能直接 `msbuild LLVM.sln`（重要）

2026-09-21 那次构建失败**不是**生成器的稳定性问题，系统事件日志写得很清楚：

| 时间 | 事件 |
|---|---|
| 22:43:05 | `CL.exe` 崩溃，出错模块 `c1xx.dll`，异常码 `0xc00000fd`（栈溢出） |
| 22:43:05 | `CL.exe` 崩溃，异常码 `0xe06d7363`（C++ 异常，通常是 `bad_alloc`） |
| 22:43:08+ | `MSBuild.exe` 未处理异常 `System.OutOfMemoryException` |

真实原因是**内存被打爆**：本机 32 个逻辑 CPU，MSBuild 默认按 32 路并行开项目，
而 `clang-tools-extra` 的每个 `.vcxproj` 里都写死了
`<MultiProcessorCompilation>true</MultiProcessorCompilation>`（即 `/MP`），
每个项目内部再各自开一批 `c1xx`，单进程峰值 1.5–3 GB，
而本机提交上限（内存 + 页面文件）只有约 **36 GB**。

**换成 Ninja 并不解决问题**——Ninja 的默认并行度同样是"CPU 核数"，不加 `-j` 会以
完全相同的方式爆掉，还要白白重编已经完成的 122 个静态库。

两条要点：

1. 必须 `msbuild <...>\clangd.vcxproj ... /p:CL_MPCount=1 /m:N`。
   `/p:CL_MPCount=1` 让每个项目只开 1 个 `c1xx`，`/m:N` 才是真正的并发上限。
2. **不要**写 `msbuild LLVM.sln /t:clangd`。MSBuild 会把目标名传播给被引用的项目，
   而 `ZERO_CHECK.vcxproj` 没有 `clangd` 目标，直接报 `MSB4057`。直接编 vcxproj 即可。

### 改了中文关键字之后：用 rebuild_clang.ps1

`ChineseKeywords.def`、`IdentifierTable.cpp`、`ParseDeclCXX.cpp` 这些文件改动之后：

```powershell
powershell -File E:\Chinese++\tools\rebuild_clang.ps1
```

它先编 `clang.vcxproj`、再编 `clangd.vcxproj`（参数就是上面两条要点：
`/p:CL_MPCount=1` + 按提交水位算出的 `/m:N`），失败降级重试 6 → 3 → 1；
但**一旦判定是代码错误（`error C####` / `error LNK####`）就立刻停止重试**，
不再白等后面两轮。

`clangd.exe` 必须一起重链——它也链接 `clangParse`/`clangSema`/`clangBasic`，
不重链的话 IDE 里认不出新增的中文拼写。

### 这个脚本上踩过的两个坑（都极难查，务必保留现有写法）

**坑一：`chinese++.exe` 是 `clang++.exe` 的硬链接，重链会把它断开。**

`chinese++.exe` 之所以被驱动当成 C++ 模式，靠的只是**文件名以 `++` 结尾**这一条规则
（`clang/lib/Driver/ToolChain.cpp`：`{"++", "--driver-mode=g++"}`，按后缀匹配）。
而链接器重写 `clang++.exe` 时是**删除再新建**，硬链接当场断裂 —— `chinese++.exe`
就永久停在上一次构建的旧二进制上，**没有任何提示**。

2026-09-22 实测踩到：用 `chinese++.exe` 编译新关键字全部不认。定位办法是直接在
二进制里搜译名字符串：

```powershell
$s=[System.Text.Encoding]::UTF8.GetString([IO.File]::ReadAllBytes('E:\Chinese++\build\Release\bin\clang.exe'))
$s.IndexOf('虚拟')          # 新二进制里应该有
$s.IndexOf('动态绑定')       # 应该没有（旧译名已删）
```

所以脚本末尾**必须**保留重新建立硬链接那一段。

**坑二：脚本本身不能含中文（现已改成纯 ASCII）。**

PowerShell 5.1 对**没有 UTF-8 BOM** 的文件按 GBK 解码。中文出现在**注释**里多数时候
只是显示乱码，但出现在**代码位置**（哈希表的键名、字符串字面量）会直接解析失败：

```
At rebuild_clang.ps1:22 char:9
+     @{ 鍚?= 'clang.exe'; 宸ョ▼ = Join-Path ...
Missing '=' operator after key in hash literal.
```

而**几乎每次用工具编辑保存都会把 BOM 抹掉**（本项目的 `edit` 工具就会），
"每次记得补 BOM"这个办法已经失败过三次。既然脚本是给机器执行的，
现在的做法是：**`tools\rebuild_clang.ps1` 保持纯 ASCII（含注释全英文）**，
中文设计说明写在本文档里。想确认它仍是纯 ASCII：

```powershell
$b=[IO.File]::ReadAllBytes('E:\Chinese++\tools\rebuild_clang.ps1')
@($b | Where-Object { $_ -gt 127 }).Count    # 必须是 0
```

## 十、改了哪些 LLVM 源文件（升级 LLVM 时看这里）

`LLVM-main` **不是 git 仓库**，所以改动以补丁文件形式保存：

```
E:\Chinese++\patches\zh-keywords.patch      中文关键字（99 个拼写）
E:\Chinese++\patches\zh-diagnostics.patch   中文诊断正文（当前 81 条）
```

两份补丁都是**只加不改**，可以分别使用。但 `zh-diagnostics.patch`
**依赖 `zh-keywords.patch` 里的那一行全局 `/utf-8`**
（见下面 ③ 的说明）——只上诊断补丁的话，中文会成为乱码。

**用法**（把补丁套到新的 LLVM 源码上）：

```powershell
cd E:\新的LLVM源码
git -c core.autocrlf=false apply E:\Chinese++\patches\zh-keywords.patch
git -c core.autocrlf=false apply E:\Chinese++\patches\zh-diagnostics.patch
```

> 必须带 `-c core.autocrlf=false`：本机 `core.autocrlf=true`，否则行尾会被改成 CRLF，
> 和 LLVM 源码的 LF 不一致。
>
> 两份补丁都经过双向验证：正向套到未改动的 LLVM 源码上能**字节级复现**我们的树，
> 逐个文件比 SHA256 全部一致。
>
> 重新生成用 `powershell -File E:\Chinese++\tools\make_patch.ps1`
> （可加 `-Which keywords` / `-Which diagnostics` 只生成一份）。

### 改动清单

分三组。**核心只有 3 个文件**，其余都是它的连带后果。

**① 核心：让中文成为关键字的正式拼写**

| 文件 | 作用 |
|---|---|
| `clang/include/clang/Basic/ChineseKeywords.def` | **新增**。86 条译名表，唯一权威数据源 |
| `clang/lib/Basic/IdentifierTable.cpp` | 把中文拼写注册到**同一个** `tok::kw_*` —— 中英完全等价 |
| `clang/lib/Basic/TokenKinds.cpp` | 让中文成为对外**正式拼写**（诊断、AST 打印、补全都显示中文） |

**② 连带修复：凡是把"正式拼写"当字符串用的地方都要改**

这一组最容易漏。`getKeywordSpelling()` 的**返回值语义**变了（英文 → 中文），于是：

| 文件 | 原来错在哪 | 怎么修 |
|---|---|---|
| `clang/lib/Lex/Preprocessor.cpp` | `II->isStr(getKeywordSpelling(kw_import))` —— 用拼写比较，用户写英文 `import` 就失配 | 改成比较 `getTokenID()` |
| `clang/lib/Tooling/Syntax/Synthesis.cpp` | 合成 token 没有源位置，只能取"正式拼写"→ 重构结果里会冒出中文关键字 | 改用新增的 `getKeywordSpellingEnglish()` |
| `clang-tools-extra/clangd/SourceCode.cpp` | 统计标识符时用"正式拼写"当字典键 → 与源码里的实际写法对不上 | 改用 `Tok.text(SM)` |

**③ 构建与工具面**

| 文件 | 作用 |
|---|---|
| `clang/include/clang/Basic/TokenKinds.h` | 新增 `getKeywordSpellingEnglish()` 声明 |
| `clang/lib/Basic/CMakeLists.txt` | 注释说明 `/utf-8` 已在顶层全局设置（**故意不**在此单独设置） |
| `llvm/CMakeLists.txt` | **全局** `add_compile_options("/utf-8")` |

> `llvm/CMakeLists.txt` 那个 `/utf-8` 不是可选项：MSVC 默认按系统 ANSI（简体中文 Windows
> 上是 GBK）读源文件，而 LLVM 源码是 UTF-8 且部分文件含非 ASCII 字符——错位的字节会
> **吞掉行尾换行**，把后面几行并进上一行的注释里，表现为"某个数组凭空消失"。
> 实例：`UnicodeCharSets.h` 里 `C11AllowedIDCharRanges` 被吃掉，`Lexer.cpp` 报
> `error C2065 未声明的标识符`。而且必须**全局**设置，因为预编译头（PCH）也要一致，
> 否则会报 `error C2855`。

**④ 中文诊断（`zh-diagnostics.patch`）**

| 文件 | 作用 |
|---|---|
| `clang/include/clang/Basic/ChineseDiagnostics.def` | **新增**。`ZH_DIAG(诊断ID, "中文")` 数据表 |
| `clang/lib/Basic/Diagnostic.cpp` | 查表函数 + 3 行挂钩（唯一的取正文处） |
| `clang/include/clang/Basic/DiagnosticOptions.def` | 开关字段 `ChineseDiagnostics`（默认开） |
| `clang/include/clang/Options/Options.td` | 开关拼写 `-fchinese-diagnostics` |
| `clang/lib/Driver/ToolChains/Clang.cpp` | 驱动把 `-fno-chinese-diagnostics` 转给 cc1 |

> 这一组**没有**碰任何 `Diagnostic*.td`，也没碰诊断的分级、`-W` 分组、稳定 ID。
> 它可依赖 ③ 的全局 `/utf-8`——否则中文表会被 MSVC 当 GBK 读，**静默**变乱码。
> 详见 `docs\诊断汉化\诊断汉化清单.md`。

**⑤ 中文预处理指令（`zh-keywords.patch`）**

| 文件 | 作用 |
|---|---|
| `clang/include/clang/Basic/ChineseDirectives.def` | **新增**。22 条 `ZH_DIRECTIVE(英文名, 中文)`，以英文 `PPKEYWORD` 名为键 |
| `clang/lib/Basic/IdentifierTable.cpp` | `lookupChineseDirective()`：非 ASCII 指令名 → `tok::pp_*`。**替换掉**原先那 5 行标志位旁路 |
| `clang/lib/Lex/PPDirectives.cpp` | `chineseDirectiveEnglishSpelling()`：跳过被排除分支时把中文**就地换成英文** |
| `clang/lib/Lex/DependencyDirectivesScanner.cpp` | 依赖扫描器的自有字符串表补 13 条中文 `.Case()` |

> ⚠ 后两个文件**必须同批改**，否则会出现两种"看起来能用"的故障：
> `PPDirectives.cpp` 漏了 → `#如果 0` 为假时报「条件指令没有终结」，
> 而**单独一条** `#如果 1` 完全正常（走的是另一条路径）；
> `DependencyDirectivesScanner.cpp` 漏了 → **静默丢依赖**，改了头文件不重编。
> 详见 `docs\预处理指令汉化\预处理指令汉化.md` 第四节。

### 一句话总结这次改动的性质

**它不是"加了一张译名表"，而是改变了"关键字的正式拼写"这个概念本身**——
于是所有依赖它的地方（预处理器比较、语法树合成、clangd 统计）都必须重新审一遍。
那 3 个连带修复才是这件事真正的复杂度。
