## 修法模板（有效）

**病根**：MinGW 的 C 头把一些 C 函数定义成**函数式宏**，而 MSVC STL 用 `using ::名字;`
把它们搬进 `namespace std` —— using 声明不能命名宏，于是 `std::名字` 根本没被引入。

**处方**（`vendor/compiler-support/zh_crt_compat.h`，由 cfg 的 `-include` 强制先包含）：

```c
#include <对应的mingw头.h>   // 拿到真函数（__signbit 等）
#undef 宏名
inline 正确返回类型 名字(参数)  { 调用真函数; }   // 全局命名空间补重载
```

**已验证**：`signbit`（3 个重载 → 打通 5 个头）。

**关键约束**：**只补真正缺的那一个**。第一版把 `isnan/isinf/isfinite/fpclassify`
一起补，结果和 MSVC `<cmath>` 自己的 `constexpr` 版本冲突
（`cmath:672`：常量表达式声明跟在非常量表达式声明之后）。

## 已验证走不通的路（别再试）

### ❌ `setjmp` 用「转发到 `_setjmp3`」的写法

```c
extern "C" int __cdecl setjmp(void* _Buf) { return _setjmp3(_Buf, 0); }
```

**后果**：`_setjmp3` 在我们可导入的 DLL 里**没有导出**，导致 `libcmt.lib` 里那个
object 被拉进来时必须解析 `_setjmp3` → **所有**链接探针同时失败（3/6 → 0/6）。

**回退方式**：`git checkout -- vendor/crt/runtime-extra.cpp vendor/compiler-support/zh_crt_compat.h`
（git 备份在这里救了场，见 commit `<HEAD>` 的绿色状态）

**下一步要查的**：`_setjmp` / `_setjmpex` / `__intrinsic_setjmp` 到底哪个能从
`ucrtbase.dll` / `vcruntime140.dll` 导入，或者干脆把 `setjmp` 保留成宏、
只想办法让 `<csetjmp>` 的 `using ::setjmp;` 通过（例如在兼容头里先声明
`namespace std { using ::setjmp; }`？需实测）。

### ⚠️ 截断文件来"删代码"

第 6 轮为了删掉 `setjmp` 实现，用「按行号截断」切文件 —— **切掉了上一个函数
的收尾 `}`**，编译失败，而且旧 `libcmt.lib` 还在包里，判据一直是坏的。

**教训**：改代码用 `edit`/精确替换，**不要按行号截断**；截断后必须重编译验证。

## 剩余链接问题

`<格式化文本>` 的 2 个缺失符号是**数据**不是函数：

```
std::__POW10_SPLIT / __POW10_SPLIT_2 / __DOUBLE_POW5_INV_SPLIT
```

这是浮点→字符串（Ryu）算法的常量表，定义在 `msvcprt.lib`。
MSVC STL 以 **Apache-2.0 WITH LLVM-exception** 开源，这些表的生成脚本与值在
`microsoft/STL` 仓库里，**可以合法取用写进我们的 CRT**（供应商 note 已记录在
`vendor/crt/SOURCE.txt`）。
