## 〇、这个模式是什么

**一句话**：把标准库**整段抄一份、整段翻成中文**，做成我们自己的库；再**在中文的基础上派生一层**，把英文原名补回来。

三层结构，缺一不可：

```
微软的 std::vector                    ← 一个字节都不动，原封不动
        │
        │  ① 抄一份，整段翻成中文（成员名、内部名、注释全部中文化）
        ▼
标准::细节::向量实现                    ← 第一层：中文实现。汉字在这里是第一公民
        │
        │  ② 在【中文的基础上】派生
        ▼
标准::向量                            ← 第二层：补回英文原名 + 与 std::vector 互转
```

**为什么必须是三层** —— 两条要求各逼出一条路，而它们不能合并：

| 要求 | 只有这一条路能给你 |
|---|---|
| **实现本身是中文的**（内部变量名、注释、成员名都是中文） | 必须**抄一份** —— 继承的话实现永远是微软那份，改不了 |
| **英文原名也还能用** | 必须**派生** —— 抄来的那份没有英文名，只能自己补回来 |

"抄来的中文实现"和"英文名自动免费"**不可兼得**（理由见 §四），所以形状只能是三层。

## 一、四条铁律（都是实测逼出来的，不是设计偏好）

### 1. 必须搬进自己的 `名域`，不能留在 `std`

抄来的那份**内部件**（`_Vector_val`、`_Vector_const_iterator`、`pointer_traits<…>`）如果留在 `std`，
就和微软 `<vector>` 的同名内部件**正面相撞**。

> **实测**：抄一份、只改类名 `vector` → `向量`、**留在 `std` 里**：
> * 单独用 → ✅ 0 错误
> * 与微软 `<vector>` 并存 → ❌ **20 个「重定义」**（`_Vector_const_iterator`、`_Vector_iterator`、`pointer_traits<_Vector_const_iterator<…>>` …）

搬进 `名域 标准` 之后，内部件也跟着搬走，**反而自动避开了撞车**。
所以"用 `标准` 而不是 `std`"不是可选项，**是让方案成立的关键**。

### 2. 必须写 `使用 名域 std;`，兜住对 `std` 内部件的引用

微软那份 `vector` 之所以能不写限定就用 `_Iterator_base`、`_Container_base`、`_Compressed_pair`、
`allocator_traits`，是因为**它自己就在 `std` 里**。搬到 `标准` 之后，每一处都变成未声明。

> **实测**：搬进 `名域 标准` 但不加兜底 → ❌ **20 处错误**，第一条是
> `未知的（种类 名字） 类名 '_Iterator_base'；你是不是想写（名字） 'std::_Iterator_base'？`
> 加上 `使用 名域 std;` 之后，只剩 `pmr` 那 2 处要手工理。

**代价（如实记）**：`使用 名域 std;` 会把 `std` 的两千多个名字一并可见，
所以 `标准::` 下面会多出一批"没打算中文化的英文名"。这不是缺陷，但要知道。

### 3. 英文名在派生层补，一个成员一行

抄来的第一层里**只有中文名**。英文原名靠第二层逐个转发回来：

```cpp
模板 <类型名 元素, 类型名 分配器 = std::allocator<元素>>
类型 向量 : 公开 细节::向量实现<元素, 分配器> {
    使用 基类 = 细节::向量实现<元素, 分配器>;
    使用 基类::基类;                              // 继承全部构造函数

    模板 <类型名... 参数> 空型 push_back(参数&&... 值) { 基类::压入(static_cast<参数&&>(值)...); }
    自动 size() 常量 { 返回 基类::尺寸(); }
    // …… 其余英文名各一行
};
```

**为什么不用继承 `std::vector` 来白拿英文名** —— 那样英文名确实免费，
但实现就永远是微软那份，第一层就不存在了。这正是用户在 §〇 里要排除的。

### 4. 有一类类型**不能抄、也不能派生，只能用别名** —— 凡是「类型身份本身参与语义」的

**异常类型是这一类里最要命的。** 实测（`build\_excp.ps1`）：

| 场景 | 结果 |
|---|---|
| 第三方抛 `std::runtime_error`，用中文名 `标准::运行时错误&` 捕获 | ❌ **抓不到**，落进 `捕获 (...)` |
| 同一次抛出，用英文原名 `std::runtime_error&` 捕获 | ✅ 抓到 |
| 抛我们自己的（派生的）中文异常，用 `std::logic_error&` / `std::exception&` 捕获 | ✅ 抓到 |

根因是 C++ 的 `捕获` 语义：`捕获 (X&)` 能接住抛出的 `Y`，**当且仅当 Y 可转换为 X**。
所以 **base → derived 永远不通** —— 这跟"抄一份还是派生"无关，是**方向**问题。

**后果是静默失败**。用户写：

```cpp
尝试 { 第三方英文函数(); }
捕获 (标准::运行时错误& e) { 处理(e); }     // ← 抓不到！
```

异常会**逃出去**（落进 `捕获 (...)`，或没人接就直接 terminate），而且**不报编译错误**。

**正确做法：这类类型用别名 —— 别名是同一个类型，捕获语义一字不改。**

```cpp
名域 标准 {
    使用 运行时错误 = std::runtime_error;      // 同一个类型
    使用 逻辑错误   = std::logic_error;
    使用 异常       = std::exception;
}
```

于是 `捕获 (标准::运行时错误& e)` 与 `捕获 (std::runtime_error& e)` **完全等价**。

**这一类包含哪些**（判断标准：**类型身份本身是否参与语义**）：

| 类别 | 为什么必须同一类型 |
|---|---|
| **异常类型** | 捕获按类型匹配，见上 |
| **RTTI / `类型标识` / 动态转换** | 换了类型就换了 `type_info` |
| **跨预编译库边界的类型**（`std::string`、`std::filesystem::path` …） | DLL 导出的签名里写死的是 `std::string` |
| **按类型特化的模板**（`std::hash`、`std::tuple_size`、`std::get` …） | 特化挂在原类型上 |
| **标准规定的 traits / 概念检测** | 检测结果按类型算 |

其余类型（容器、算法、迭代器这些"用成员、用行为"的）**可以**抄一份 + 派生兼容层。

**于是整个方案是两条路并用**：

```
要中文成员名        →  抄一份 + 派生兼容层（本方案主体）
类型身份即语义      →  别名（同一类型，零风险）
```

> 📌 这一条是**在一个现已删除的老文件的提醒下查出来的** —— `examples\zhstd.h`
> （**已于 2026-09-27 删除**，长期无人使用）头部那三条警告里，第二条正是
> 「`std::string` / `std::exception` 这类跨边界类型变成"另一种类型"」。
> 本项目 2026-09-24 就写下了这条预判，本次实测把它变成了**可复现的证据**。

### 2.2 译名从哪来（**优先级，按顺序查**）

**一个新译名不是"想出来"的，是"查出来"的。** 按这个顺序查，前一张表有就照抄：

| 顺序 | 查哪 | 位置 | 条数 | 管什么 |
|---|---|---|---|---|
| 1 | **关键字表** | `LLVM-main\clang\include\clang\Basic\ChineseKeywords.def` | 88 | 语言关键字：`字符`(char)、`类型`(class)、`模板`、`名域`、`常量`、`空型` … |
| 2 | **诊断表** | `LLVM-main\clang\include\clang\Basic\ChineseDiagnostics.def` | 7344 | **技术术语的大本营**：`字符串`、`迭代器`、`容器`、`指针`、`数组`、`引用`、`常量字符` … |
| 3 | 都没有 | —— | —— | 才按最合适的中文新定，并**登记进 §2.1 / §2.2 的对照表** |

> **为什么诊断表排第 2**：它已经翻了 7344 条，把英文技术词汇的中文对应一次性定下来了。
> 标准库译名若与它不一致，就会出现**"报错里叫 X、代码里叫 Y"**的分裂。
>
> ⚠️ **注意 `string` 不在关键字表里** —— 因为 `string` 不是关键字，是标准库类型名。
> 关键字表里含"字符"的只有 5 条：`字符`(char) / `字符8位` / `字符16位` / `字符32位` / `宽字符`。
> `字符串` 是**诊断表**定下的（凡英文正文是 "string" 的都译 `字符串`）。

**已从诊断表确认、可直接用的术语**：

| 中文 | 英文 | 诊断表里的证据 |
|---|---|---|
| `字符串` | string | `err_bad_string_encoding` →「字符串字面量中的字符编码非法」 |
| `迭代器` | iterator | `err_for_range_iter_deduction_failure` →「不能把类型 X 用作迭代器」 |
| `容器` | container | `warn_unused_container_subscript_expr` →「容器访问的结果未被使用」 |
| `常量字符` | `const char` | `warn_cxx20_compat_utf8_string` →「从 常量字符 数组变为 常量字符8位 数组」 |

**⚠️ 已经另有含义的词（用之前要知道会撞）**：

| 中文 | 诊断表里**现在**的意思 | 我们想用它做 | 诊断表里的证据 |
|---|---|---|---|
| `向量` | **SIMD 向量**（GNU / NEON / SVE 向量类型） | `std::vector` → `标准::向量` | `err_attribute_bad_neon_vector_size` →「Neon 向量大小必须是 64 位或 128 位」 |
| `映射` | **OpenMP 数据映射 / 模块映射** | `std::map` → `标准::映射` | `err_omp_duplicate_map_type_modifier` →「同一个映射类型修饰符被指定了多次」 |
| `集合` | **Objective-C 集合** | `std::set` → `标准::集合` | `err_invalid_collection_element` →「集合元素的类型…不是 Objective-C 对象」 |

**判断（用户 2026-09-27 已确认）**：
* `向量` 的歧义与英文自身同构（English 里 `vector` 也同时是容器和 SIMD），**可以接受**。
* `映射` / `集合` **保留**。用户的原话：「如果原本的英文直接翻译就是那样的，我觉得映射和集合完全没问题」
  —— 即：只要是英文的**直接对译**，同词不同义不算问题。
* 备选（`字典` / `集`）**不采用**，仅留作记录。

#### 2.2.1 第四条硬约束：**同一个中文名在整个 `标准` 名域里只能有一个定义**

实测触发（2026-09-27）：`<类型特征>` 里已有 `标准::是相同类型 = std::is_same`（trait，取 `::value`），
而 `<概念>` 里想用 `标准::是相同类型` 表示 `std::same_as`（concept，本身就是 bool）。
**两个头一起 `#包含` 就重定义。**

> 所以译名表必须**全局唯一**，不能各头各定 —— 这是用户定的
> 「**先把所有库复制一份，再在复制体上统一改**」那条工序的**又一条实质理由**。

**已经采用的区分手法**（trait 与 concept 同义但不同形）：

| 类别 | 构词 | 例 |
|---|---|---|
| traits（`<类型特征>`） | `是…类型` / `是…` | `是相同类型` `是整数类型` `是引用类型` |
| concepts（`<概念>`） | `…于` / `可…` / `…型` | `相同于` `可转换到` `整数型` `浮点型` |

**做每个新头之前，先在本节与 §2.1 里查一遍新中文名是否已被用过。**

## 三、工序：四个阶段（**必须先全部复制，再统一改**）

> ⚠️ **工序是用户 2026-09-27 纠正的，理由不是形式而是实质。**

一个文件端到端地改（复制 → 改名 → 派生层）会出**跨文件漂移**：
`vector` 里的 `size` 叫 `尺寸`，`map` 里的 `size` 可能被叫成 `个数`。
**译名表必须全局建好再套用。** 实测也印证了这点：手写派生层时用了 `引用` / `大小类型`，
而当时那张 29 个名字的小表里根本没有它们 —— **自己跟自己就对不上**。

| 阶段 | 做什么 | 验收 | 脚本 |
|---|---|---|---|
| **1 复制** | 112 个公开头**全部**复制到 `zhstdlib\`，**只做结构改造**（换守卫、搬 `名域 标准 { 名域 细节 {`、写 `使用 名域 std;`），**名字一个都不改**，文件名也先沿用英文 | **112 个逐个能编过** | `tools\copy_zhstdlib.ps1` |
| **2 建译名表** | 2,128 个公开名 ＋ 112 个头文件名 ＋ 34 个内部件名，**一次性定完** | 表完整、无遗漏、**无跨文件冲突**（同一个英文名全库只能有一个中文名） | 待写（阶段 2 的产物） |
| **3 套用** | 用译名表批量改名 ＋ **让编译器当校对**（借用类型的同名成员按它报的坐标改回英文） | 全部编过 | `tools\make_zhstdlib.ps1` |
| **4 派生层** | 每个公开类追加派生层，把英文原名补回来 | 中文名 / 英文名 / 与 `std` 并存，三项通过 | 同上 |

**阶段 1 为什么能单独验收**：结构改造（换守卫、搬名域、写兜底）对**每一个**头文件都成立，
而且不依赖任何译名 —— 所以它可以先做完、先整体验一次。
逐个编译 112 个，就是在证明"结构改造不是只对 `vector` 成立"。

抄一份 `<vector>` → 改成 `<向量>`，实测可行的步骤：

|---|---|---|
| 1 | 换守卫：`_VECTOR_` → `_ZH_VECTOR_`（不抢微软的守卫） | 2 处 |
| 2 | `_STD_BEGIN` → `名域 标准 { 名域 细节 {` ＋ `使用 名域 std;`；`_STD_END` → `} }` | 各 1 处 |
| 3 | 类名 `vector` → `向量实现`（正则 `\bvector\b`） | **345 处 / 13 个名字** |
| 4 | 成员名逐个译成中文 | **390 处 / 29 个名字** |
| 5 | 手工理嵌套名域（`pmr` 那类）的引用 | **2 处** |
| 6 | 追加第二层：`名域 标准 { 类型 向量 : 公开 细节::向量实现 { …英文名 + 转换… }; }` | 新写 ~50 行/类 |

### 3.2 两个已经踩到、必须写进脚本的坑

**坑①：不能对整个文件做"全局字符串替换"。**
第 5 步曾对 `polymorphic_allocator` 做全局替换，结果把文件顶部的
`#include <xpolymorphic_allocator.h>` 改成了 `<xstd::pmr::polymorphic_allocator.h>` ——
文件名被改坏，立刻 `fatal error: 找不到文件`。
（同类教训本项目已有：`verify_chinese_keywords.py` 第一版整文件替换把注释里的 60 处文档改坏。）
**凡"整文件替换"都要先想清楚它会碰到哪些非代码文本。**

**坑②：成员名改名会撞上"借用类型的同名成员"，必须让编译器当校对。**
实测 `<vector>` 的 29 个成员名里 **3 个会撞**：`begin` / `end` 撞
`std::initializer_list` 的 `begin/end`，`swap` 撞 `std::swap`。
文本替换分不清"我们类的成员"和"借用类型的同名成员"，**编译器分得清，而且给出行列号**。
所以要：编译 → 读它报的「没有名为 X 的成员」→ 按坐标把那一个标识符改回英文 → 再编译，直到干净。
实测：第 1 轮 9 处，第 2 轮干净。

> ⚠️ **列号是【字节】偏移，不是字符偏移。** 第 3045 行报第 33 列，
> 而前 32 个字节正是 `        插入(开始(), _Ilist.`（中文一字 3 字节）——
> 按字符算会全部落空（第一版 10 轮只改中 1 处）。一律用 UTF-8 字节比对，再折回字符下标。

### 3.3 阶段 1 实测：112 个文件**不是同一类**，必须先分类

阶段 1（全量复制 + 逐个验证）的结果：**112 个文件复制成功，但逐个编译只有 33 个通过**。
79 个失败，几乎全是同一个根因，而它暴露了一件设计层的事：

`zhstdlib\cstddef` 第 100 行 `} }`（我们搬进去的名域已结束），第 103 行是

```cpp
_EXTERN_CXX_WORKAROUND
using _STD max_align_t; // intentional, for historical reasons
_END_EXTERN_CXX_WORKAROUND
```

**`using std::max_align_t;` 是一条"桥"**：原本 `cstddef` 先把全局的 `max_align_t` 引进 `std`，
再从这里引回全局。文件被搬进 `标准::细节` 后，第一步没落进 `std`，第二步就找不到 `std::max_align_t`。

**根因不是 bug，是分类错误**：`cstddef` 是 **C 包装头** —— 它自己没有实现，
只是把 C 库的名字搬进 `std`。而 `max_align_t` 这类类型**必须与 `::max_align_t` 是同一个类型**
（对齐 / ABI），这**正是铁律 4**：「类型身份本身参与语义的，只能用别名，不能抄也不能派生」。
**所以把 `cstddef` 抄一份，从设计上就错了。**

#### 3.3.1 同一根因的第二副面孔：`_STD <自己定义的东西>`

实测 `scoped_allocator`：文件里有 `_STD _Scoped_outermost` —— 用 `std::` 限定引用
**它自己**定义的东西。`_STD` 展开成 `std::`，而本文件的内容已经搬进 `标准::细节`，
于是报「namespace 'std' 中没有名为 `_Scoped_outermost` 的成员」。

> **规律**：搬名域之后，文件里一切**"对自己"的 `std::` 限定引用**都失效。
> 这和 §3.3 那条 `using _STD max_align_t` 的"桥"是同一件事的两种表现。

**修法（已做成生成器的步 4c，对所有头生效）**：改名完成后，把 `_STD <改后的名字>`
还原成**不带限定**的 `<改后的名字>`。

于是阶段 1 要加一个子步骤 —— **先分类，再决定哪些抄、哪些只做别名**：

| 类别 | 例 | 做法 | 依据 |
|---|---|---|---|
| **C 包装头**（约 30 个） | `cstddef` `cstdint` `cstdio` `cstdlib` `cstring` `cmath` `ctime` … | **别名层**（`使用` 同名事物），**不抄** | 铁律 4：类型身份参与语义（`max_align_t` / `size_t` / `FILE` …） |
| **真正的 C++ 库头** | `vector` `string` `map` `algorithm` … | **抄一份 + 派生兼容层** | §〇 三层结构 |
| **工具头**（只有模板/宏，无实体） | `type_traits` `ratio` `limits` `version` … | 待定，仍需逐个分类 | —— |

> 📌 **这正是"先全部复制、再统一改"的价值**：如果一个文件端到端地做，
> 会在 `vector` 上"通过"，然后到第 40 个文件才炸。全量复制 + 逐个验证
> 一次就把类别问题暴露出来了。

### 3.4 甲类（C 包装头）别名层：**三种机制，不是一种**

第一轮实测 8/25 通过，错因是**只用了"类型别名"一种机制**。正确做法是按种类分开：

| 种类 | 例 | 机制 | 为什么 |
|---|---|---|---|
| **类型** | `size_t` `FILE` `tm` `jmp_buf` `fenv_t` | `使用 中文名 = std::原名;` | 类型别名声明，**同一类型** ✓ |
| **普通函数** | `fopen` `strlen` `sqrt` `malloc` | `模板 <类型名... 参数> 自动 中文名(参数&&... 值) { 返回 std::原名(static_cast<参数&&>(值)...); }` | **函数没有"别名"机制** —— `使用 std::fopen;` 引入的是**原名 fopen**，不会变成「打开文件」 |
| **变参 C 函数** | `printf` `scanf` `sprintf` | **只能原名引入**，或按固定 arity 写重载 | C 变参**无法完美转发**（模板参数包接不住 `...`） |
| **值宏** | `EOF` `INT_MAX` `FLT_MAX` `NULL` | `内联 常量 类型 中文名 = 原名;` | 宏不是实体，只能造一个常量承载它的值 |
| **函数式宏** | `assert` `va_start` | `#定义 中文名 原名` | 宏替换是文本级的，`#定义` 是唯一对称手段（本项目已论证过代价对称） |

> ⚠️ **这两条约束本来写在 `examples\zhstd.h` 里**（「函数不能起别名……只能写一层
> 内联转发」「变参函数没法完美转发，只能原样引入」），而那个文件 **2026-09-27 被删除时，
> 我只写了"已删除"，没把它的设计约束搬过来** —— 于是写生成器时直接踩了回去。
> **规矩：删/改任何旧文件，必须把它携带的设计约束搬进本文档，而不只是记一句"已删除"。**

**另一条命名教训**：中文标识符**不能以数字开头**。`16位字符` 非法
（`缺少非限定标识符`）。关键字表的既有构词法是**后置**：`字符8位` / `字符16位` /
`字符32位` —— 所以是 `字符16位`、`整数8位`。这正是 §2.2「先查关键字表」的用处。

**第三条命名教训（2026-09-27 实测）**：**99 个中文关键字都不能当标识符用。**
给模板形参起名 `类型` 时直接炸：
```
模板 <类型名 类型>   →   error: 缺少（符号）identifier / 匿名 class 的声明必须是定义
```
因为 **`类型` 就是关键字 `class`**，于是 `template <typename class>` 被解析成错的形状。
同样不能用作标识符的还有 `返回`(return)、`如果`(if)、`整数`(int)、`常量`(const)、
`公开`(public)、`自动`(auto)、`空型`(void) … 全部 88 个关键字 ＋ 11 个运算符替代拼写。
所以给模板形参、变量、成员起中文名时，**必须先过一遍关键字表**；
实用做法是用不会撞的词（`某类型` `元素` `值` `对象` `参数` `甲` `乙` …）。

### 3.5 还有一个会静默毁掉全局的问题：**文件名 shadow**

阶段 1 把 112 个副本**沿用英文文件名**放进 `zhstdlib\` —— 于是 `zhstdlib\cstddef`
**把真正的 `<cstddef>` 挤掉了**。凡 `#include <cstddef>` 的都拿到我们那份，全炸。

**所以中文文件名不是"最后美化一下"，它是阶段 1 就该做的**：
副本必须以**中文文件名**存在（`zhstdlib\向量`），这样 `<vector>` 仍解析到微软真头，
`<向量>` 才是我们的。两者的关系是"并存"，不是"覆盖"。

对应的处置：甲类 26 个的副本已删除（改用中文别名头），乙/丁类的中文文件名在阶段 2
（译名表）里一并定，届时改名后需**重跑全量验证**。

### 3.6 `friend` 声明会跨头失效 —— 又一条"必须先分类"的理由

实测 `condition_variable`：`condition_variable_any` 的实现直接访问
`std::_Mutex_base::_Mymtx`，而那是微软在 **`<mutex>`** 里用 `friend` 声明授权的。
friend 声明里写的是**原来的类名**；我们把类改名成 `标准::细节::条件变量任意实现` 之后，
**那份友谊不认它了**，于是三处访问全部报「是 `std::_Mutex_base` 的私有成员」。

修法只有一条：**把 `<mutex>` 也一起抄下来，并把其中的 friend 声明一并改名**
（两边都是我们的，改得动）。所以：

> **凡是"实现伸进别的头的私有成员"的类，单独抄它自己是没用的 ——
> 必须把提供 friendship 的那个头也抄进来。** 这属于步骤 1（内部头/依赖头）的范围，
> 但它说明步骤 1 里的某些头**不是"最后再补"，而是被步骤 2 的某些头硬依赖的**。

分类时要标出这一类头（例：`condition_variable` ← 依赖 `<mutex>`），
把它们排到"需要先抄依赖"那一组。

**精确证据（2026-09-27 查到）**：friend 声明就在 `<mutex>` 里 ——
```
mutex:88    friend condition_variable;
mutex:89    friend condition_variable_any;
```
所以我们那份 `<condition_variable>` 把类改名为 `标准::细节::条件变量任意实现` 之后，
`<mutex>` 里的 `friend condition_variable_any;` 指的已经不是它了。

#### 3.6.1 由此得出：改名表最终必须是**跨头共享的一张**

修 friend 这件事要求：我们抄下来的 `<mutex>` 里那句 `friend condition_variable_any;`
也要跟着改成 `friend 标准::细节::条件变量任意实现;` —— 也就是
**`<mutex>` 的改造必须知道 `<condition_variable>` 给这个名字定的译名。**

> **结论：译名不能各头各定，最终必须是【全库共享的一张表】。**
> 这与用户定的工序（**先把所有库复制一份，再在复制体上统一改**）完全一致 ——
> 目前 `make_zhstdlib2.ps1` 的表是**按头写的**，属于过渡形态；
> 跨头名字（如 `condition_variable_any`、`_Mutex_base`）必须提到共享表里，
> 否则步骤 1 与步骤 2 之间的 friend 关系永远补不回来。

> **✅ 已解决（同一轮，见 §3.8）**：按依赖顺序抄（先 `<mutex>` 后 `<condition_variable>`），
> 成对改名的 friend 自动对上，并用一条**专门的双头测试**钉住了。
> 但"共享译名表"这件事本身**还没做** —— §3.8.2 说明它为什么还会咬人。

**所以「步骤 1」的第一批不是随便挑的**，而是：**被 friend 依赖的头**
（`<mutex>` 是第一个），先抄它们，并把跨头译名提到共享表。

### 3.7 抄 `<mutex>` 实测：两类新错误 + 两条方法论（步骤 1 第一个头）

`<mutex>` 是步骤 1 的第一个头，也是**被 `friend` 依赖的那个头**。走完一遍，
除了 §3.6 的 `friend` 问题，还逼出下面两条 —— 都已固化进 `make_zhstdlib2.ps1`。

#### 3.7.1 `_STD <本文件自己定义的名字>`：4c 原先太窄

现象（`<mutex>`，同一类错误连续冒三次）：

```
error: namespace 'std' 中没有名为 '_Unlock_locks' 的成员
error: namespace 'std' 中没有名为 '_Try_lock_from_locks' 的成员；你是不是想直接写 '_Try_lock_from_locks'？
error: namespace 'std' 中没有名为 '_Try_lock_range' 的成员
error: namespace 'std' 中没有名为 'lock' 的成员
```

- `_STD` 是宏，展开成 `::std::`。原文里 `_STD X` 用来引用**它自己**定义的 `X`。
  本文件内容已搬进 `标准::细节`，`std::X` 就不存在了 —— 这是 §3.3 那一类问题的**普遍形态**。
- **编译器的提示句就是答案**：「你是不是想直接写 `'_Try_lock_from_locks'`？」= 去限定。
- 原来 4c 只遍历 `types` + `data`，于是漏两处：
  1. 没登记进任何表的内部自由函数（`_Unlock_locks` / `_Try_lock_from_locks` / `_Try_lock_range`）；
  2. **`members` 表里的自由函数** —— 原文 467 行 `_STD lock(_Mtxes...)` 指的正是
     `<mutex>` 自己定义的自由函数 `std::lock`（已被改名成 `加锁`），
     而 `members` 里有 `lock->加锁`，却因为 §3.4 记的那个反例没被 4c 覆盖。

**修法（现在是通用规则，不再是逐个人肉登记）**：
- 4c 遍历 `types` + `data` + `members`，但**排除 `using ` 开头的 `_STD X`**
  —— 这正好精确命中 §3.4 那个反例（`using _STD swap;` 是故意拉 `std::swap` 供 ADL 的），
  比原来「干脆不做 members」的粗判据更准；
- 再**从生成文本里扫**名域作用域定义的 `_` 开头自由函数，逐个去限定。
  判据不再依赖我有没有登记，**漏登记不会再变成一个编译错误**。

> 教训与 §3.3.1 同源：**不要靠"我记得登记了"，要靠机器扫出来。**

#### 3.7.2 派生层/别名层必须照**微软这个版本实际有的接口**写，不能照标准文档写

手写派生层时我照 `cppreference` 的 `std::mutex` 接口写，结果两条都错：

| 我照标准写的 | 微软 14.44 的实际情况 | 报错 |
|---|---|---|
| `native_handle` / `native_handle_type` | **已被官方删除**（GH-3820），`<mutex>` 第 75、615 行原文写着 `native_handle_type and native_handle() have intentionally been removed` | `'_互斥量基类' 中没有名为 '原生句柄' 的成员` |
| `once_flag` 属于 `<mutex>` | **不在** `<mutex>` 里（grep 原文 0 命中） | `类型 一次标志 : 公开 细节::一次标志实现` → `缺少 类名` |

**规则：手写层的接口清单，唯一来源是 `C:\Program Files\Microsoft Visual Studio\...\include\<头>` 本身。**
标准文档只用于**命名**，不能用于**接口清单** —— 微软的 STL 是"标准的一个具体实现"，
删除项（GH-3820）、未实现项、以及被推到别的头的类型，都会让照文档写的派生层当场编不过。

### 3.8 解封 `<condition_variable>`：friend 问题解决了，但换了个方向又咬回来

`<condition_variable>` 长期挂在 `regen_zhstdlib.ps1` 的默认 `-Exclude` 里，就是等 `<mutex>`。
`<mutex>` 一过，立刻解封（同时把 `-Exclude` 默认值清空）。这一轮共 4 个错，两次"以为是 A，其实是 B"。

#### 3.8.1 步 0：`#include` 也要跟着改名 —— friend 问题的**反向形态**

第一次报：

```
error: （成员名） '_Mymtx' 是（类型名） 'std::_Mutex_base' 的（关键字） 私有 成员
```

- 原文 `_Ptr->_Mymtx()` 里 `_Ptr` 是 `shared_ptr<mutex>`，而 `mutex::_Mymtx()` 是**私有**的。
- 微软只对**真实的 `std::condition_variable_any`** 开友元。我们那个头原来第 17 行是
  `#include <mutex>` —— 拉进来的是**微软的真 `<mutex>`**，于是我们的类去碰人家的私有成员。
- 这是 §3.6 的**反向形态**：不是"我的 `friend` 指不到对方"，而是
  **"我引用了别人家的类型，人家的 `friend` 不认识我"**。
- 修法：把 `#include <mutex>` 换成 `#include <互斥量>` —— 我们那份里的 friend 已经成对改成
  `friend 条件变量任意实现;`，两边同处 `标准::细节`，友元自然对上。

**新增机制「步 0 包含改名」**：条目可选字段 `zhIncludes = @{ 'mutex' = '互斥量' }`。

> ⚠ **是按条目开，不是全局替换。** 只有**已经抄完并通过验证**的头才能作为目标，
> 否则会 `#include` 到不存在的文件。等 112 个头都抄完之后，这一步应该改成自动判定
> （"目标汉语头存在就换"），那时才是全局的。

#### 3.8.2 跨头成员名：`.unlock()` 必须写成 `.解锁()`

改完包含之后报：

```
error: '标准::细节::独占锁实现<标准::细节::互斥量实现>' 中没有名为 'unlock' 的成员
```

- `独占锁实现::unlock` 在我们那份 `<互斥量>` 里已经改名成 `解锁`，
  所以**任何别的头对它调 `.unlock()` 都会挂**。
- 本轮的处理：在 `condition_variable` 条目里把 `lock/unlock/try_lock` 也抄一遍。

**这不是长久之计**，只是把 §3.6 的"共享译名表"问题又演示了一遍：
**成员的译名同样是跨头的**。`<mutex>` 定下 `unlock->解锁` 的那一刻，
全库所有对 `unique_lock` 调 `unlock()` 的地方就都被绑定了。
所以那张共享表**不只是类型名，必须同时包含成员名**（`lock/unlock/try_lock/wait/notify_*` …）。
在共享表做出来之前，每抄一个新头都可能在同一个坑上再摔一次。

#### 3.8.3 结果与证据

- `zhstdlib\条件变量`：4/4 通过 —— 比别的头多一条**专门的双头测试**：
  ```
  与互斥量并存（friend 成对）：#包含 <互斥量> + #包含 <条件变量>
  ```
  它同时实例化了 `条件变量任意实现::等待`（会走 `_Mymtx()`），
  所以这条测试**真的在检验那份 friend 有没有对上**，不是摆设。
- 全量：**44 / 44**。

### 3.9 潜伏最久的一个 bug：派生层落在包含守卫【外面】—— 加东西时必须问"它在守卫里吗"

抄 `<shared_mutex>` 时第一次报：

```
error: 重定义（名字） '互斥量'
error: 重定义（名字） '独占锁'
error: 重定义（名字） '锁守卫'
```

而且错误全指向 `<互斥量>` —— 一个我们**以为早就验过**的头。

**根因**：MSVC 公开头的最末一行就是包含守卫的 `#endif`。生成器原先用
`AppendAllText` 把派生层**追加到文件最末**，也就是 `#endif` **之后**：

```
…  正文 …
#endif // _MUTEX_      ← 守卫到此结束
类型 互斥量 : 公开 …     ← 派生层在守卫外面
```

于是「**守卫守得住正文，守不住派生层**」：同一个头被包含两次时，正文被守卫跳过，
派生层却被编译第二遍 → 重定义。

**为什么以前 17 个条目全绿也没照出来**：每个头的测试都是"引一个中文头"，
从来没有"同一个中文头进两次"。`<shared_mutex>` 同时包含 `<mutex>` 和 `<condition_variable>`，
而我们的 `<条件变量>` 自己又包含 `<互斥量>` —— 同一个头进两次，才把这个坑炸出来。

**修法**（两处，缺一不可）：
1. 生成器改成**插在最后一个 `#endif` 之前**（只做插入，不动原文任何字节）；
2. `verify_zhstdlib.ps1` 给**每个**头加第二条探针：**同一个头连包含两遍**。
   修好之后把探针留在那里 —— 让这条规矩以后由机器守，而不是靠我记得。

> **教训（第三条同源教训）**：
> ① §3.3.1「验证产物 ≠ 验证生成器」；② §3.7.1「不要靠我记得登记了，要靠机器扫」；
> ③ 本条「不要靠我记得加对地方了，要靠机器反复包含」。
> 三条是同一个病：**对人肉记忆的依赖，就是下一个潜伏 bug 的住处。**
>
> 具体到这一条，可复述成一句自查：**凡是我们往头文件里加东西，都要问一句"它在守卫里面吗"。**

### 3.10 抄 `<shared_mutex>`：跨头译名第三例，全量 45 / 45

`<shared_mutex>` 348 行、3 个类（`shared_mutex` / `shared_timed_mutex` / `shared_lock<M>`）、无 friend。
走完一遍又添两笔跨头账（都记在 §3.8.2 那本账上）：

| `未知的类型名 'defer_lock_t'` 等 3 个 | 三个 tag 类型定义在 `<mutex>`，我们那份已改名成 `接管锁类型`/`延迟锁类型`/`尝试锁类型` | 抄进本条目的 `types` 表 |
| `.unlock()` 找不到 | 同 §3.8.2 | 抄进 `members` 表 |

- 步 0 包含改名同时挂了两个目标：`zhIncludes = @{ 'mutex'='互斥量'; 'condition_variable'='条件变量' }`。

> **跨头译名已经出现三例了**（`<mutex>`→`<condition_variable>`→`<shared_mutex>`）。

### 3.11 先做的不是"共享表"，而是**让机器保证表不漂移**

§3.10 的结论是"应该先把共享表做出来"。真正动手时选了**风险更低、收益相同**的形态：

- **没有**把译名从各条目里搬走（那是大重构，45 个绿头都在上面）；
- **而是**在 `make_zhstdlib2.ps1` 里、`$H` 表定义之后加一段**跨头译名一致性检查**：
  同一个英文名（`types` / `members` / `data` 三类各自算）出现在任意多个条目里时，
  **中文译名必须完全相同**，否则直接 `throw`，并打印"哪个名字、哪几个头、各译作什么"。

实测输出（当时）：

```
跨头译名检查: 共 85 个英文名，其中 19 个跨了多个头
```

19 个跨头名字全部一致 —— 也就说明前面三次踩坑**不是表漂移，纯粹是我漏登记**
（漏登记导致的错误由编译器和 §3.7.1 的扫描器兜住，已经不会再变成"要我记得"）。

**为什么要做成检查、而不是做成共享表**：
- 共享表解决的是"同一事实写两遍"；检查解决的是"写了两遍但不一致"。
  在生成器已经能自动校对、验证能自动发现的前提下，**检查已经足够**，
  而且不动任何现有条目 —— 45 个绿头一个字节都不用重验。
- 检查是**加**上去的规矩，共享表是**改**既有结构；先加规矩，后谈重构。

> 这是第四条同源教训（前三条见 §3.9）：**能变成机器检查的"我记得"，都要变。**
> ⚠ 诚实说明：检查**只能覆盖条目里登记过的名字**。
> 某个头忘了登记某个跨头名字时，它照不出来 —— 那种情况仍然由编译验证兜住
> （表现为"某某里没有名为某某的成员"，见 §3.8.2）。

### 3.12 抄 `<stop_token>`：`swap` 不能改名（§3.4 那个反例的第二个形态）

`<stop_token>` 399 行、4 个类（`stop_token` / `stop_source` / `stop_callback<C>` / `nostopstate_t`），
首次生成后 0/4，三条错都在同一个模式上：

```
error: 函数调用使用的实参太多；只应给出单个实参，即第 '_Other' 个，实际有 2 个实参
error: 调用非静态成员函数时没有对象实参
```

对到源码：

```cpp
void swap(stop_token& _Other) noexcept {
    _STD swap(_State, _Other._State);   // 要的是 std::swap —— 交换内部指针
}
```

- 我把 `swap` 登记进 `members`（`swap -> 交换`），于是 `_STD swap(...)` 变成 `_STD 交换(...)`，
  §3.7.1 的去限定又把它变成 `交换(...)` —— 结果解析到**同名的成员函数** `交换(停止令牌实现&)`，
  于是"实参太多"/"非静态成员函数没有对象实参"。
- **修法**：`swap` 在这一条里**不登记**（保持英文）。`_STD swap` 就还是 `std::swap` ✓。

> **这是一条通用判据，补进 §3.4 那本账**：
> **成员名出现在 `_STD X(...)` 里、而那个 `X` 本意是 `std` 的自由函数时，不能改名。**
> §3.4 记的是它的声明形态（`using _STD swap;`），本条是它的调用形态（`_STD swap(a, b)`）。
> 两种形态都会因为"改名 + 去限定"而把调用引到我们自己的同名成员上。
>
> ⚠ 也已如实写进 `make_zhstdlib2.ps1` 的该条目注释里 —— 免得下次又"顺手补上 swap"。

**结果**：`zhstdlib\停止令牌` 4/4 通过（含"停止回调 + 无停止状态"一条）。
其中 `nostopstate` 是**全局常量**、`nostopstate_t` 是**顶层 tag 类型**，
成员转发机制管不到它们，所以在 `extra` 里手写：

```cpp
使用 无停止状态类型 = 细节::无停止状态类型;
内联 常量表达式 无停止状态类型 无停止状态{};
```

### 3.13 抄 `<thread>`：嵌套名域也能改名，特化留在抄来的那层就够用

`<thread>` 446 行，比前面几个复杂在**三处结构**，都不是新机制，但都要先想清楚：

| 结构 | 处理 | 为什么行 |
|---|---|---|
| `namespace this_thread { get_id/yield/sleep_for/sleep_until }` | 当成普通标识符登记：`this_thread -> 本线程` | 名域名也是标识符。抄来的那份变成 `细节::本线程`，派生层写 `名域 本线程 { … }` 转发回中文名 |
| `class thread::id`（嵌套类） | **不改名**（`id` 太短，全局 `\bid\b` 替换不安全） | 派生类继承嵌套类型 —— `标准::线程::id` 与 `细节::线程实现::id` 是**同一个类型**，所以 §六第 8 条（嵌套类型名逐步翻）照旧适用 |
| `std::formatter<thread::id>` / `std::hash<thread::id>` 特化 | **不用额外处理** | 它们特化的是**抄来那层**的类型 `细节::线程实现::id`；而 `标准::线程::id` 就是它（继承而来），所以两种写法都能用 |

> 第 3 条值得记一句：**特化挂在抄来那层就够用，因为对外类型是派生出来的、嵌套类型是同一个。**
> 这与 `<stack>` 的 `uses_allocator` 不同 —— 那里对外类型 `标准::栈` 与抄来那层是
> **两个不同的类模板**，所以必须用 `stdExtra` 在 `std` 里**为重发一份**（见 §3.4）。
> 判据：**特化的模板参数是"对外类型本身"（要重发）还是"嵌套类型/成员类型"（不用重发）。**

又添一笔跨头账：`get_token -> 取令牌`（§3.8.2 那本账的第四例），
跨头译名检查已从 19 个跨头名涨到 **24 个**，全部一致。

**结果**：`zhstdlib\线程` 4/4 通过（含"本线程名域"与"可停线程"两条）。
全量：**47 / 47**。

### 3.14 别名轨道的跨头约束：同一个中文名只能声明一次（组合探针抓到的第一个真问题）

做 `<exception>` / `<system_error>`（都走**别名轨道**，理由见下）时发现一个从来没查过的角度：
**汉语别名全都落在同一个 `标准` 里**，于是"两个头声明同一个中文名"就是重定义。
而 C 库在标准里是**故意重叠**的。

把全部 49 个汉语头放进同一个 TU 一起引，第一条错误就出来了：

```
E:\Chinese++\zhstdlib\C数学:21:41: error: 重定义（名字）'绝对值'
```

- `std::abs` 既属于 `<cstdlib>` 也属于 `<cmath>`；`<C标准库>` 用 `std::abs`，
  `<C数学>` 用 `std::fabs`，两个头都想声明 `标准::绝对值`。
- **单头探针永远照不出来** —— 每个头自己都编译通过。这和 §3.9 的守卫 bug 是同一类盲区：
  **只看单个头，看不到头与头之间的事。**

**修法（两条，一条治标一条治本）**：

1. **宏哨兵**（治标，`make_zhc.ps1` 的 `$SENTINEL` 表）：共享名用 ASCII 宏包住，
   哪个头先引就在哪个头里生效，两个头一起引也不冲突。
   ```cpp
   #ifndef _ZH_ABS
   #define _ZH_ABS
   模板 <类型名... 参数> 自动 绝对值(参数&&... 值) { 返回 std::fabs(...); }
   #endif // _ZH_ABS
   ```
   ⚠ 哨兵名用 ASCII —— 宏名的中文写法还没验过，不冒这个险。
2. **组合探针**（治本，`verify_zhstdlib.ps1`）：把**全部**汉语头放进一个 TU 一起引。
   它不只管别名轨道的重定义，也能照出抄+派生轨道里"两个头都定义了 `标准::细节::X`"这类跨头撞名。

**顺带挖出的第二个洞**：`make_zhc.ps1`（26 个甲类 C 包装头的生成器）
**从来不在 `regen_zhstdlib.ps1` 的名单里** —— 本脚本存在的理由就是"改了生成器但没人重生成"，
结果它自己漏了一半（别名轨道有两个生成器：`make_zhc.ps1` 管 C 包装头、
`make_zhalias.ps1` 管 C++ 只能别名的头）。已补进名单（它一次生成全部，所以单独一格）。

#### 3.14.1 两个"按结构该抄、按铁律 4 必须别名"的头

`<exception>`（428 行）和 `<system_error>`（738 行）在分类里是**乙类**（自己定义类），
但**铁律 4 优先**：这两类的**类型身份参与语义**，只能别名。

| 头 | 为什么不能抄 | 处理 |
|---|---|---|
| `<exception>` | `std::exception` 是**所有异常的根**，捕获按类型匹配。抄一份 = 造出第二个异常体系，`catch (std::exception&)` 抓不到 | 全别名：`异常` / `坏异常` / `变体访问失败` / `异常指针` / `嵌套异常` / `终止处理` + 10 个自由函数转发 |
| `<system_error>` | 错误**类别**是 DLL 里的单例，错误码要和返回 `std::error_code` 的英文接口（如 `<filesystem>`）互通 | 全别名：`错误类别` / `错误码` / `错误条件` / `系统错误` / `错误码值` / `输入输出错误码` + 5 个自由函数 |

- `<异常>` 3/3 过，其中一条是**中文 `尝试/抛出/捕获` 与真实异常体系互通**的实测：
  `尝试 { 抛出 标准::异常(); } 捕获 (常量 标准::异常&) { 返回 0; }` ✅
  —— 这正是"身份必须是同一个"的正向证据。
- `<系统错误>` 3/3 过（含三种类别是三个不同单例的断言）。
- ⚠ `分配失败` / `数组长度分配失败` 已在 `<新建>` 里别名过，`<异常>` **不再重复声明** ——
  这就是上面那条跨头约束的直接后果。
- ⚠ 别名层只管**类型名 + 自由函数**，成员名（`.value()` / `.message()`）与枚举量
  （`std::errc::invalid_argument`）仍是英文 —— 记为妥协，见 §六。

**结果**：全量 **49 / 49**，组合探针通过。

### 3.15 抄 `<bitset>`：「取反」是关键词 —— 又被咬了一次，这次改成机器查

`<bitset>` 689 行、一个类模板 + 一个嵌套代理 `reference` + `hash<bitset>` 特化。四个坑：

#### 3.15.1 关键词：`取反` = `compl` = `~`（**这是最值得记的一条**）

我把 `flip` 译作「取反」，编译报的是：

```
error: '~' 之后需要给出类名来指明析构函数
```

**报的是"析构函数"，跟命名八竿子打不着。** 真相在关键词表里：

```c
ZH_OPERATOR_KEYWORD(取反, tilde)   // 取反 = compl = ~
```

于是 `取反()` 被词法成 `~()`。改名为「翻转」后立刻通过。

> **§2.2 第一步就写着"先查关键字表"，但"我记得查"不算数。**
> 这次把它做成了机器检查（见 §3.15.2）——这已经是本项目第五条同源教训了
> （§3.3.1 / §3.7.1 / §3.9 / §3.11 之后的第五条）：**凡是靠人记的规矩，迟早被咬。**

#### 3.15.2 新增机器检查：关键词表检查（`make_zhstdlib2.ps1`）

`$H` 表定义之后，逐条取出**每一个中文名**（头名 `zh`、对外类名 `pub`、
`types` / `members` / `data` 的全部值），去 `ChineseKeywords.def` 里查，
撞上就直接 `throw`，并打印"哪个条目、哪个名字、撞的是哪个关键词"。

- 关键词表解析：`ZH_KEYWORD(英文, 中文, FLAGS)` 取**第 2** 个参数；
  `ZH_OPERATOR_KEYWORD(中文, 英文)` 取**第 1** 个参数（运算符型关键词就藏在这里）。
- 实测输出：`关键词表检查: 表里 99 个关键词，查了本表 172 个中文名` ✅
- 和跨头译名检查一样，在 `regen_zhstdlib.ps1` 里显式打出来 —— 隐形规矩等于没有规矩。

#### 3.15.3 类模板必须写 `tparam`（非类型参数也一样）

`bitset` 是 `template <size_t _Bits>`（**非类型**参数）。我漏了 `tparam`，派生层就写成
`类型 位集 : 公开 细节::位集实现 {`，一次报三条互不相干的错：
「使用类模板 '细节::位集实现' 需要模板实参」「缺少类名」「未声明的标识符 '基类'」。

### 3.16 抄 `<set>`：中文名第一次需要"手写在派生层"

`<set>` 492 行、两个类（`set` / `multiset`）、无 friend。它的 API 几乎**全部继承自借用的 `_Tree`**
（在 `<xtree>` 里，我们还没翻），所以这个头自己定义的成员只有 ctor / `emplace` / `swap`。

**这逼出中文层的第二种用法**：

| 用法 | 中文名从哪来 | 例子 |
|---|---|---|
| 以前 | `members` 表改名 —— 只对【本文件自己定义】的成员有效 | `<互斥量>` 的 `lock -> 加锁` |
| **新增** | **在 `extra` 里手写中文转发，调基类的英文名** | `自动 插入(…) { 返回 基类::insert(…); }` |

也就是说：**名字不在本文件里，就改不了名，只能在派生层手写一层中文转发。**
`<set>` 手写了 `插入/擦除/查找/计数/尺寸/为空/清空/开始/结束` 九个。

- 嵌套类型名由 `types` 汉化（**中文在前**），派生层用 `deriveTypes` 把**英文补回**：`使用 iterator = 基类::迭代器;` ——
  它们继承自 `_Tree`，派生类本来就带英文名，这里只是多给一个中文名。
- ⚠ **没有**把这些名字写进 `members` 表：写进去会让改名遍去动本文件里的 `insert` 之类的
  借用路径，正是 §3.12 那类危险。**手写层是安全的位置。**

#### 3.16.1 步 2b：`pmr` 嵌套名域（`<set>` 是第一个带它的头）

MSVC 很多容器头末尾有一段：

```cpp
namespace pmr {
    using set = _STD set<_Kty, _Pr, polymorphic_allocator<_Kty>>;
}
```

搬进 `细节` 之后 `polymorphic_allocator` 就找不到了 —— 它本来就靠"在 `std::pmr` 里面"
这个**位置**找到同名的 `std::pmr::polymorphic_allocator`：

```
error: 使用了未声明的标识符 'polymorphic_allocator'；
       你是不是想写 'std::pmr::polymorphic_allocator'？
```

关键点：**`使用 名域 std;` 只把 `std` 的名字引进 `细节`，引不进 `std::pmr` 的【嵌套】名字。**
修法：生成器新增**步 2b** —— 见到 `namespace pmr {` 就在其后补一句 `使用 名域 std::pmr;`。
`pmr` 名域本身照旧暂不翻（§六第 9 条），但里面的名字必须找得到。

**结果**：`zhstdlib\集合` 4/4 通过；全量 **52 / 52**，组合探针通过。

### 3.17 抄 `<map>`：新机制 `deriveExtra`，以及"模板参数名不能和类名同名"

`<map>` 705 行、四个类型（`map` / `multimap` / `_Tmap_traits` / 嵌套的 `value_compare`），
与 `<set>` 同基类（借用的 `_Tree`）、同 `pmr` 块 —— 所以 §3.16 那一套直接复用。

#### 3.17.1 新机制 `deriveExtra`：把【中文】转发写进自动生成的派生类里

§3.16 的手写中文转发只能放在 `extra`（追加在文件末尾、类**外面**）。
但 `<map>` 的主类 `映射` 是**机制自动生成**的，中文转发必须写在它**里面**。
所以 `make_zhstdlib2.ps1` 新增条目字段 `deriveExtra`：原样插进自动生成的派生类体里
（就在英文转发之后）。`<映射>` 用它补了九个：`擦除/查找/计数/尺寸/为空/清空/包含/开始/结束`。

| 字段 | 加在哪里 | 干什么 |
|---|---|---|
| `derive` | 自动生成的派生类里 | 英文转发 → 中文成员（`at -> 取值`） |
| `deriveTypes` | 同上 | 补**英文**嵌套名 → 基类中文名（`使用 iterator = 基类::迭代器;`） |
| `deriveExtra` | 同上（**新**） | **手写**中文转发 → 基类英文名 |
| `extra` | 文件末尾、类外 | 同头里的**其余类**与自由函数 |

#### 3.17.2 模板参数名不能和类名同名（中文名同词就撞）

第一次生成的报错只有一行：

```
E:\Chinese++\zhstdlib\映射:715:50: error: 使用类模板（名字）'映射' 需要模板实参
```

对到源码：

```cpp
模板 <类型名 键, 类型名 映射, …>              // ← 参数也叫「映射」
类型 映射 : 公开 细节::映射实现<键, 映射, …>   // ← 这里的「映射」被解析成【参数】
```

模板参数 `映射` **遮蔽**了类模板 `映射`，于是 `类型 映射` 里的 `映射` 不再指类模板。
把参数改名为 `映射值` 即通过。

> **这是中文命名特有的坑**：参数名和类名共用同一个汉语词太自然了
> （`映射`/`映射`、`向量`/`向量`、`线程`/`线程`…），而英文里很少这样撞
> （`map` 的参数叫 `_Ty`，不叫 `map`）。
> **规则：模板参数名一律用"描述性的另一个词"**（`映射值`、`元素`、`容器`），
> 不要用类名本身。`<vector>` / `<set>` 当年没踩到，纯属运气 —— 它们的参数叫 `元素` / `键`。

**结果**：`zhstdlib\映射` 4/4 通过；全量 **53 / 53**，组合探针通过。

### 3.18 步 0b：`realInclude` + `dropTypes` —— 一个头里"值类型可抄、异常类型只能别名"

到 `<optional>` 时撞上一个**结构性问题**，它挡住了后面一大片头
（`<any>` / `<variant>` / `<future>` / `<memory>` / `<regex>` / `<filesystem>` …）：

> 一个头里常常**混着两类东西**：
> · 值类型（`std::optional`）—— 可以抄+派生，能有中文成员名；
> · 异常类型（`std::bad_optional_access`）—— 身份参与语义，铁律 4 要求必须是 `std` 的那个。

整个头都抄的话，`_Throw_bad_optional_access()` 抛的是**我们抄来那个类**，
用户写 `catch (std::bad_optional_access&)` **永远抓不到**。

**办法两步（新增两个条目字段）**：

| 字段 | 干什么 |
|---|---|
| `realInclude = @('optional')` | 把**微软原头**也包含进来 → 真的 `std::bad_optional_access` 存在了 |
| `dropTypes = @('bad_optional_access')` | 把抄来那份**异常类的定义删掉** → 本文件里的 `bad_optional_access` 靠 `使用 名域 std;` 解析到真的那个 |

删除用**花括号配对**实现（`Remove-ClassDef`）；`dropTypes` 里的名字**不许**再出现在 `types` 里，
否则一个删一个改名自相矛盾 —— 生成器会直接 `throw`。

**实测证据**（`<可选>` 的第 2 条测试）：

```cpp
静态断言(std::is_same<标准::坏可选访问, std::bad_optional_access>::value, "");
整数 主函数(){
    标准::可选<整数> 甲;
    尝试 { (空型)甲.取值(); }                       // 中文成员，抛异常
    捕获 (常量 std::bad_optional_access&) { ... }    // 接住的是【真】std 异常
    ...
}
```
✅ 通过 —— 中文成员抛出的异常，能被英文 `catch (std::bad_optional_access&)` 接住。

#### 3.18.1 两个顺序坑（都实测踩了）

1. **`realInclude` 必须插在【改名之后】**。
   先插的话，`#include <optional>` 里的 `optional` 会被类型改名改成 `#include <可选实现>`：
   `fatal error: 找不到文件 '可选实现'`。
2. **`dropTypes` 必须在【改名之前】**（要匹配英文类名 `bad_optional_access`）。
   两个字段一个在前一个在后，注释里写清楚了，免得下次调换。

#### 3.18.2 跨头译名检查第一次用到"豁免"：`reset` 同名不同义

- `bitset::reset` = 把某一位清零 → **复位**
- `optional::reset` = 销毁所存的值 → **重置**

检查拦下之后，登记进 `$ZH_NAME_EXCEPTIONS` 并**写明理由**（豁免必须写理由，默认是必须一致）。

#### 3.18.3 关键词检查又拦下一次：`否则` = `else`

`or_else` 我本想译「否则」—— 那是关键词。改成与 `and_then -> 且则` 对称的 **`或则`**。

#### 3.18.4 又一次"照文档写错"（与 §3.7.2 同源）

`std::nullopt` 我照 cppreference 写成 `无值{42}`，报"没有匹配的构造函数"。真相在 MSVC 原头里：

```cpp

```

**取的是嵌套的 `_Tag`，不是 int。** 又一次印证 §3.7.2 那条：手写层的接口清单，

**结果**：`zhstdlib\可选` 4/4 通过；全量 **54 / 54**，组合探针通过。

### 3.19 抄 `<any>`：抄来的**自由函数**怎么在 `标准` 里可用

`<any>` 464 行，`any` + `bad_any_cast`（步 0b 处理，同 §3.18），机制基本复用。两个新知识点：

#### 3.19.1 `使用 细节::中文名;` —— 把抄来的自由函数引进 `标准`

抄来的文件整体搬进 `细节`，所以它里面**命名空间作用域的自由函数**（`any_cast` / `make_any`）
也落在 `细节::`。派生层只管类成员，管不到自由函数。

两种做法：

| 做法 | 保真度 |
|---|---|
| 在 `标准` 里重写泛型转发 `模板 <类型名...> 自动 名(...)` | ❌ **会把 `T&` 退化成 `T`**：`自动`（`auto`）的返回值推导会去掉引用，`any_cast<T&>` 直接坏掉 |
| `使用 细节::任意转换;`（**using 声明**） | ✅ 重载全带上、返回引用也不丢 —— 就是把同一个函数引进另一个名域 |

**结论：抄来的自由函数一律用 `使用 细节::X;` 引进 `标准`，不要重写转发。**
（这条也解释了为什么别名轨道的转发只能是"值返回"的：那边没有 `细节` 可借，只能自己写。）

#### 3.19.2 派生类要能"从基类回来"：接管构造函数

`make_any<T>(...)` 返回的是**抄来那层**的 `细节::任意实现`，而对外类型是派生出来的 `标准::任意`。
派生类没有"基类 → 派生类"的隐式转换，所以 `deriveExtra` 里手写一个接管构造：

```cpp
任意(细节::任意实现&& 内) noexcept : 基类(static_cast<细节::任意实现&&>(内)) {}
```

> 这类"抄来那层的自由函数返回抄来那层的类型"的头还有 `<memory>`（`make_unique`）、
> `<utility>`（`make_pair`）等 —— **接管构造是它们的通用解**。

#### 3.19.3 关键词检查第三次拦下：`取类型` = `typeof`

`any::type()` 我想译「取类型」—— 那是 `typeof` 关键词。改成 **`所属类型`**。
（顺带：`类型` 本身是 `class` 关键词，所以「类型」这条路早就堵死了。）

**结果**：`zhstdlib\任意` 4/4 通过；全量 **55 / 55**，组合探针通过。

### 3.21 `<array>` 走别名：结构化绑定是决定性证据；顺带修掉生成器"对读者说谎"

`<array>` 913 行，按结构是乙类（自己定义了 `array` / `array<_Ty,0>` 特化 / 迭代器），
但**铁律 4 优先 —— 只能别名**，理由两条，都实测过：

| 理由 | 证据 |
|---|---|
| `std::array` 是**聚合**，花括号初始化靠它 | `标准::数组<整数, 3> 甲{1, 2, 3};` ✅ |
| **结构化绑定走 `std::tuple_size` / `tuple_element` 的特化** | `自动 [甲0, 甲1] = 甲;` ✅ |

抄一份再派生会**同时丢掉这两样**（派生类不是聚合；特化认的是 `std::array` 那个类型）。
所以 `<数组>` 没有中文成员名 —— 这是别名轨道的固有代价（§六第 18 条），
但换来了"两种名字是同一个类型"。

- `取<下标>(数组)` 与 `<元组>` 里的 `取<下标>(元组)` 是**重载**（参数类型不同），
  可以同名共存 —— 组合探针会验这一点。
- `转数组` 对应 `std::to_array`（两版：左值数组 / 右值数组）。
- ⚠ 别名模板必须写成 `模板 <类型名 元素, size_t 尺寸> 使用 数组 = std::array<元素, 尺寸>;`
  —— 写成 `使用 数组 = std::array;` 会报"使用类模板 'std::array' 需要模板实参"。

#### 3.21.1 生成器不许对读者说谎（修掉一段写死的注释）

`make_zhalias.ps1` 以前给**每一个**别名头都印同一句理由：

```cpp
//   本头里是【常量】而不是类 —— 常量换不了类型，只能承载它的值。
```

这对 `<数字>` 是对的，对 `<数组>` / `<元组>` / `<类型信息>` 全是**假话**。
已改成：条目可选 `reason = '…'` 给准确理由，没给则用一句**不会说错**的默认话
（"类型身份参与语义"）。`<数组>` 的 reason 已按上表写明。

> 这是"文档诚实性"层面的同一条规矩：**机器生成的话也必须是真的**，
> 否则后来的人会拿它当依据（本项目已经因为"删文件没搬约束"栽过一次，见 §3.0 的教训）。

**结果**：`zhstdlib\数组` 3/3 通过；全量 **59 / 59**，组合探针通过。

### 3.22 抄 `<forward_list>`：第一次生成即通过；一个"标准故意不提供的成员"

`<forward_list>` 1653 行，与 `<list>` 同族（迭代器类都在本文件里），机制完全复用：
100 处类型改名 / 124 处成员改名 / 校对第 1 轮即"无同名冲突" / 4 条测试 4/4。

两点值得记：

1. **`forward_list` 没有 `size()`**（标准如此：单链表求长度是 O(n)，所以不提供）。
   所以 `members` 表里**刻意不登记 `size`** —— 登记了也不报错（本文件里没有这个名字，
   改名是空操作），但一旦哪天文件里出现别处的 `size` 调用，空操作就会变成误伤。
   **规矩：只登记本文件真正定义了的成员；"顺手登记"是 §3.12 那类事故的温床。**
2. 新译名（都进了跨头表）：`before_begin -> 首前`、`cbefore_begin -> 常量首前`、
   `insert_after -> 后插`、`emplace_after -> 后就地构造`、`erase_after -> 后擦除`、
   `splice_after -> 后接合`、`insert_range_after -> 范围后插`。

### 3.25 抄 `<span>`：步 2b 从"只管 pmr"泛化为"所有 std 嵌套名域"

`<span>` 516 行，机制本无新意，但踩到**两个新坑**，都已固化成规则：

#### 3.25.1 步 2b 泛化：`pmr` 之外还有 `ranges` / `chrono` / `filesystem` / `execution`

`<span>` 末尾有一段：

```cpp
namespace ranges {
    template <class _Ty, size_t _Extent>
    constexpr bool enable_view<跨度实现<_Ty, _Extent>> = true;
    ...
}
```

报的是 `没有变量模板匹配部分特化` —— 根因与 §3.16.1 的 `pmr` **完全一样**：
原头靠"在 `std::ranges` 里面"这个**位置**找到主模板，搬进 `细节` 后就找不到了。
所以步 2b 从"只找 `namespace pmr {`"泛化为一张表：

```powershell
$nested = @('pmr', 'ranges', 'chrono', 'filesystem', 'execution')
```

> ⚠ **`this_thread` 绝不能进这张表**（实测：全量重生成时 `<线程>` 立刻 0/4）。
> 因为 `<thread>` 里的 `this_thread` 是**我们自己翻译**的（`本线程`），
> 注入的 `使用 名域 std::this_thread;` 会被改名成 `std::本线程` →
> `namespace 'std' 中没有名为 '本线程' 的名域`。
> **判据：只有"我们不翻、原样保留"的嵌套名域才补 using。**

#### 3.25.2 命名空间作用域的**变量**也要登记：`dynamic_extent`

`dynamic_extent` 是 `<span>` 里的 `inline constexpr size_t`，**不是类型也不是成员**。
原文有 `_STD dynamic_extent`，而步 4c 只去限定 `types` / `members` / `data` + `_` 开头函数
—— 于是它留在 `std::dynamic_extent`：

```
error: namespace 'std' 中没有名为 'dynamic_extent' 的成员；
       你是不是想写 '细节::dynamic_extent'？
```

**修法：把它登记进 `data` 表**（4c 也遍历 `data`）。这条同时说明了一件事：
`data` 表不只是"数据成员"，它是"**命名空间作用域的变量**"的登记处 —— 两类都该进。
（另：我自己的 `tparam` 里也写了 `std::dynamic_extent`，应写 `细节::动态范围` ——
**手写层引用抄来那层的东西，一律写 `细节::`，不能写 `std::`。**）

**结果**：`zhstdlib\跨度` 4/4 通过；全量 **64 / 64**，组合探针通过。

### 3.26 `<variant>` 试做未成：三条约束先记在这里（**未完成，不是妥协**）

本轮试做 `<variant>`，**没有做通，已撤下条目并把产物移出 `zhstdlib\`**（规矩：`zhstdlib\` 只放验证过的）。
撤下前抓到的三条约束是真实的，记在这里，免得下次从零再撞：

1. **`std::monostate` 不在 `<variant>` 里。**
   `grep monostate <variant>` 的第一处命中是第 1650 行的 `operator==(monostate, monostate)` ——
   **只有它的运算符，没有它的定义**（定义在别的头）。所以：
   · 不能把 `monostate` 登记进 `types` 改名（本文件里没有类定义，改名必然落空，
     于是 `单态类型` 成了未声明的名字）；
   · 只能在 `extra` 里**别名** `std::monostate`（真头已由 `realInclude` 带进来）。
   > 教训：**登记改名前先确认"这个类真的定义在本文件里"**（同 §3.22 的 `size`）。

2. **`stdExtra` 里引用抄来那层，要写 `标准::细节::X`，不能写 `细节::X`。**
   `stdExtra` 被包在 `名域 std { }` 里，而 `细节` 是 `标准` 的嵌套名域 ——
   从 `std` 里看不见 `细节`：`error: 使用了未声明的标识符 '细节'`。
   （§3.13 那条同类经验只说了"对外类型要重发"，没说清限定名怎么写。）

3. **`realInclude` 打开后，抄来的 `std::` 特化会和真头里的同一特化撞车。**
   `<variant>` 里有 `hash<monostate>` 特化；`monostate` 解析到 `std::monostate` 之后，
   我们抄来那份就成了"在 `细节` 里特化 `std::hash<std::monostate>`"，
   而 `realInclude` 带进来的真 `<variant>` 里**已经有一份**：
   `error: 重定义（名字）'hash<std::monostate>'`。
   > **这说明 `realInclude` 与"抄来的 std 特化"天生冲突**：
   > 凡是抄来的文件里含 `std::` 模板特化的，要么用 `dropTypes` 一并丢掉，
   > 要么别开 `realInclude`。**这是一条新的机制级约束，`<variant>` 之后类似头都要先查。**

### 3.27 **【重要缺陷】`dropTypes` 一直静默失效**：`-fsyntax-only` 验不了运行期语义

§3.26 第 3 条让我去复查 `<optional>` / `<any>`，结果**查出真缺陷**：

#### 3.27.1 `dropTypes` 从来没删掉过东西

`Remove-ClassDef` 的正则写的是 `class\s+NAME`，而 MSVC 原文是：

```cpp
_EXPORT_STD class _NODISCARD bad_optional_access : public exception {
```

**类名和 `class` 之间夹着 `_NODISCARD`**，于是正则**匹配不到**，`dropTypes` 什么都没删 ——
而 `_Throw_bad_optional_access()` 抛的正是**我们抄来那个类**（`细节::bad_optional_access`）。
证据：修好之前 `zhstdlib\可选` 第 40 行仍是那段类定义、第 55 行仍是 `_THROW(bad_optional_access{})`。

而且它**只是打印一行警告就过去了**（`⚠ dropTypes 没找到类定义`），
在几十行的生成日志里根本没人会看见 —— **这是"软失败"，比报错更坏。**

**修法**：正则允许类名前的说明符：`class\s+(?:[A-Za-z_]\w*\s+)*NAME`。
修好后日志变成 `步0b 丢掉抄来的类定义 'bad_optional_access'`，文件里定义确实消失，4/4 仍通过。

> **教训：`dropTypes` 这类"删掉点什么"的步骤，必须自己校验"真的删掉了"。**
> 打印警告不算校验 —— 要么让"没找到"直接失败，要么在生成后断言目标已消失。

#### 3.27.2 我 §3.18 那句"能被英文 `catch` 接住"**当时并没有被真正验证**

`verify_zhstdlib.ps1` 全程 `-fsyntax-only`：**它只验能不能编过，验不了运行期语义。**
`静态断言(std::is_same<标准::坏可选访问, std::bad_optional_access>::value, "")` 只能证明
**别名**指向真类型（那部分是对的），**证明不了"抛出来的也是真类型"** ——
而后者才是铁律 4 真正要求的东西。

用**真正编译 + 运行**的探针去验时，还暴露出 `-fsyntax-only` **完全没报**的错：

```
E:\Chinese++\zhstdlib\可选:1014:26: error: （类型名）'标准::细节::可选实现<int>' 中没有名为（名字）'类' 的类型
 1014 |     使用 值 = 基类::类;
```

**这是下一个要查的缺陷**（派生层的 `deriveTypes` 行在完整实例化时才被检查，
`-fsyntax-only` 的用例没触发它）。它说明两件事：

1. **验证方式本身有盲区**：`-fsyntax-only` 既不验运行期语义，也不验"只有完整实例化才检查"的代码。
2. 已有的 64 个绿头里，**凡是含 `deriveTypes` / 模板体内依赖基类名字的行，都还没被真正验证过。**

> **下一步（明确记下，不留悬念）**：
> ① 查 `使用 值 = 基类::类;` 这一行的来源（`deriveTypes` 的发射文本被谁改了）；
> ② 给验证脚本加**至少一条"链接并运行"的探针**，专验异常身份（抛/接同一类型）；
> ③ 把"`-fsyntax-only` 通过"在文档里的说法统一降级为"语法通过"，
>    不再用它支撑任何"运行期语义正确"的结论。

**结论**：`<variant>` 需要一个"抄来的特化怎么与真头共存"的机制，
不是靠再加一个字段能糊过去的。**在机制想清楚之前不做它**（`<expected>`、`<optional>` 的
`stdExtra` 情形也要按第 3 条复查一遍）。

## 十、「把没翻译的全部翻译」：一次全库扫描的实测结果与正确做法

用户 2026-09-27 明确要求：**把没翻译的全部翻译。** 本轮按此做了一次**全库自动扫描**
（把嵌套类型名提成全库共享表，对所有头一次性生效，并自动在派生层补回英文）。

### 10.1 结果：64 → 55（**已回退**，仓库现为 64/64 全绿）

9 个头失败，错误**分成三类，每一类都是真知识**：

| 失败头 | 错误签名 | 根因 |
|---|---|---|
| 双端队列 / 链表 / 跨度 | `namespace 'std' 中没有名为（名字）'反向迭代器' 的模板` | `reverse_iterator` **在借用上下文里**出现（`std::reverse_iterator`），改了名就找不到 std 的模板 |
| 条件变量 / 任意 | `'标准::细节::条件变量任意实现' 中没有名为（名字）'引用' 的类型` | 自动生成的 `使用 reference = 基类::引用;` 挂错了：`reference` 是**同文件里另一个类**（嵌套迭代器）的成员，不是主类的 |
| 单向链表 | `未知的类型名 'reference'` | 同上 |
| 线程 | `'标准::细节::线程实现' 中没有名为（名字）'迭代器' 的类型` | 同上（`iterator` 属于嵌套迭代器类，不属于 `thread` 本身） |

### 10.2 三条结论（**下次不再重犯**）

1. **不能全库一把梭。** 同一个英文名在**同一个文件里**可能属于**不同的类**
   （主类 vs 嵌套迭代器类），自动生成的"派生层补回英文"必然挂错。
   → **必须一头一头做**，而且每个头都要看"这个名字到底属于哪个类"。
2. **借用途徑必须先排除。** `std::reverse_iterator` / `allocator_traits<...>::value_type`
   这类是**借来的**，不能改。→ 改名清单要**先减掉这些**，不能等编译器报错再回退。
3. **校对的回退模式还不够**：本轮新发现 `没有名为（名字）'X' 的模板`
   这一种（原来只认"成员名/名字的类型"两种）——补进去之后回退才会更全。

### 10.3 正确的做法（下一轮按此执行）

**一头一个头地翻，每个头四步**：
1. 先把该头里**借用上下文**的嵌套名挑出来（`std::` 前缀、`<借来的模板>::`、`allocator_traits` 等），**从清单里剔除**；
2. 再确认剩下那些名字**属于哪个类**（主类才写进条目的 `types`，嵌套类的写进该类的改名清单）；
3. 条目 `types` 加中文名，`deriveTypes` 翻成 `@('英文名','中文名')`（派生层补回英文）；
4. 单头 4/4 → 全量 64/64 → 组合探针。

**并把校对的错误模式补上 `没有名为（名字）'X' 的模板`。**

> 这一轮的价值在于：**用一次失败换来三类别名"不能怎么做"的实证**，
> 并且**没有把 55/64 留在仓库里**（已 `git checkout` 回到全绿）。
> 教训与 §8 一致：**全库级改动必须能一次验证完；验不完的，就不要一次性上。**

## 十一、常设规则（用户 2026-09-27 定）：**不许半汉半英；全部汉语，再补英文**

> 用户原话：「**不要出现半汉语半英文，全部汉语，再补英文**」
> 「中文库是先有中文的格式，再有的英文的格式」

### 11.1 规则本身

1. **抄来那层（`标准::细节`）必须是纯汉语。** 里面出现英文标识符就是**欠账**，不是设计。
2. **英文只在派生层（`标准`）出现**，而且**只为"英文还能用"而存在**：
   删掉派生层，中文库应当**仍然完整可用**（只是英文名字不能用）。
3. **半汉半英的中间态不得进仓库。** 一次只做一个头，做完就是纯汉语 + 派生补英文；
   做不成就回退，不留中间态（本规则的直接后果）。

### 11.2 这条规则改写了工作顺序（**自底向上**）

实测证据：给 `<向量>` 加嵌套类型名汉化后报

```
error: 使用类模板（名字）'reverse_iterator' 需要模板实参
```

因为 `using 反向迭代器 = std::reverse_iterator<迭代器>;` 里的
**`std::reverse_iterator` 是借来的，变不成汉语** —— 除非我们**先把它抄成自己的**。

> **结论：一个头只有在"它借用的一切都汉化之后"才可能全是汉语。**
> 所以顺序必须是**自底向上**：
> ① 内部件与基础设施（`<iterator>` 的 `reverse_iterator`、`xutility`、`xmemory`、`xstring`… 即**步骤 1**）
> ② 再上层容器/算法/流
> ③ 每上一层"翻完即纯汉语"，派生层只补英文。
>
> 这也**正式解释了为什么步骤 1 是前提**：不是"为了更完整"，而是
> **内部件借用一天，上层就一天做不到"全是汉语"**。

### 11.3 判据（可机器检查，下一步实现）

- **检查 A**：条目里登记了中文译名的名字，在抄来那层的生成物里**不得再作为标识符出现**（借用的除外，借用要显式登记成"借"）。
- **检查B**：派生层里**新声明**的名字必须是 ASCII（英文）；出现中文声明即方向反了。
- 两条都要**失配就 `throw`**，让"半汉半英"在生成阶段就进不来，而不是等人来看。

### 11.4 本轮的动作

| 类别 | 例子 | 怎么消灭 |
|---|---|---|

> （我两次想用"借用名排除表"绕过，两次都是同一个妥协，都该删。）

### 13.2 顺序

1. 先区分上面两类（对每个名字查：它在抄来那层的正文里有没有定义）；

3. **真正借来的**：按依赖顺序抄成汉语件（步骤 1），并把所有引用点改名指向我们的汉语件；
4. 验收标准不变：**`examples\汉语库示例.cpp` 整体编过** + 每个头 4/4 + 全量 64/64 + 组合探针。

### 13.3 第①类已用"一键替换"做完（用户提醒：这类本来就是正则一把替换的事）

用户问「这个东西不应该是正则直接一键替换就能完成的吗」——**对，第①类就是**。
生成器里新增全库共享表 `$INTERNAL_NAMES`（步 3/4b），在改名遍里对所有头生效：

> **为什么这类能一把替、而 `reverse_iterator` 那次不能** —— 判据是**二义性**：
> `_Mybase` 在抄来那层的正文里**有定义**（`using _Mybase = ...`），全篇都是我们自己的，
> 替换没有歧义；而 `reverse_iterator` 同时还指 `std::reverse_iterator`（借来的模板），
> 盲替会把借用点也改掉。**所以"能不能一键替换"取决于映射是否唯一，不取决于名字长什么样。**

### 13.4 第②类的正确做法：替换 + **同时把定义抄过来**

第②类（`_Alty_traits` = `allocator_traits`、`_Alnode_traits`、`_Pocma_values`、`_Outer_traits`…）

所以第②类 = **抄（步骤 1）+ 一键替换**，两件事必须一起做。

### 15.5 `optional` 的根因找到了：成员改名伤到**借来类型的成员** `::value`

`<可选>` 2/4 的两个错（`甲 = 5` 无可行 `=`；`标准::可选<整数> 甲(9)` 无匹配构造）根因在**抄来那层**，不在派生层：

```cpp
template <class _Ty2 = remove_cv_t<_Ty>,
          enable_if_t<_AllowDirectConversion<_Ty2>::取值, int> = 0>   // ← 原为 ::value
constexpr explicit(!is_convertible_v<_Ty2, _Ty>) 可选实现(_Ty2&& _Right) ...
```

`_AllowDirectConversion<_Ty2>` 是 **`bool_constant<...>`（借来的 std 类型）**，它的成员是 `value`；
而我把 `value`（`optional::value()` 的成员名）登记进 `members` 表 → 全局改名把
`::value` 也改成了 `::取值` → **约束恒假** → SFINAE 把整个转换构造删掉
→ `可选<int>` 无法从 `int` 构造。

**这与 §13 的 `_Alty_traits::最大尺寸` 是同一类错**：
**"成员改名"会误伤"访问借来类型成员"的写法（`X::名字`）。**

#### 15.5.1 试过的护栏与结果（如实记录）

试过一条精确护栏：成员改名跳过 `::名字` 形式（正则 `(?<!::)\b名字\b`）。
**结果：不行** —— 错误的形状变了（`标准::可选<int>` 反而找不到 `有值`/`取值`），
仍不通，且这是**机制级改动**。按目标规矩**已回退**（`git checkout`），仓库回到 64/64。

**下一轮的正确做法**：不要用"一刀切的前缀规则"，而要**按限定名是否属于借来类型**判定
（例如：`::value` 只在限定名是 `bool_constant`/`allocator_traits` 这类 `std` 里有的模板时跳过），
或者干脆**逐个名字判**：先只对 `optional` 把 `value` 从 `members` 表移除、
改在派生层补中文（代价是基类里 `value()` 保持英文——记作欠账，附消除路径）。

### 15.6 `optional` 已修好（4/4）：两处修法都记在这里

按 §15.5 的结论分两步，`<可选>` 由 2/4 → **4/4**：

1. **把 `value` 从 `members` 表移出**（中文名改在派生层手写）——
   这样 `bool_constant<...>::value` 这种**访问借来类型成员**的写法不再被改坏，
   optional 的转换构造恢复 → `标准::可选<整数> 甲(9)` 通过。
   > **代价记作欠账**：抄来那层里 `optional::value()` 暂时仍是英文；
   > **消除路径**：按 §11.2 自底向上抄 `xutility`/`xmemory`（`bool_constant` 等），
   > 它们成为我们自己的汉语件之后，`::value` 就是我们的成员，才能一起改名。

2. **不要写 `使用 基类::operator=;`** —— 它会把基类的**拷贝/移动赋值**也拉进派生类，
   而 `int` 能经转换构造变成 `可选`，于是 `甲 = 5` 出现**两个候选 → 歧义**（实测）。
   改为手写一个模板赋值：
   ```cpp
   模板 <类型名 实参> 可选& operator=(实参&& 右) {
       基类::operator=(static_cast<实参&&>(右));
       返回 *this;
   }
   ```
   对 `可选 = 可选`，隐式拷贝赋值（非模板）优先，不冲突 ✓。

**这条经验对后面同类头（`<任意>` 的 `operator=`、`<变体>` 的赋值）直接适用。**

### 15.7 `<set>` 1/4 的根因：它比 `deriveExtra` 机制更早，主类一直没有中文转发

错误：`标准::集合<int>` 中没有名为 `插入`/`计数`/`尺寸` 的成员。

根因：`<set>` 是 §3.16 做的，当时**还没有 `deriveExtra` 机制**（那是 §3.17 给 `<map>` 才加的），
所以 `集合` 这个**主类**里一直没有中文转发（只有陪跑类 `多重集合` 在 `extra` 里手写过）。
空测掩盖至今 —— 这正是"手写层不受约束"那一类（第 5 个实例）。

**修法**：给 `<set>` 补 `deriveExtra`（与 `<map>` 同样的九个：插入/擦除/查找/计数/尺寸/为空/清空/包含/开始/结束）。

⚠ 本轮尝试补的时候**踩了自己的坑**：用 `String.Replace` 落盘，而它是**替换全部匹配**，
`    derive  = @( @('emplace','就地构造') )` 这一行不止一个条目有 → 块被插了多次 →
生成器语法坏（ParserError）。**已 `git checkout` 回退，仓库保持 64/64。**
教训：**脚本化改生成器时，锚点必须唯一，或改用"只替换第一处"的 API**（`[regex]::Replace` 带计数，
或先 `IndexOf` 再 `Substring` 拼接）。这条与 §13.5 的"映射唯一性"是同一类判断。

### 15.8 Triage 结论：**五个 0/4 是同一个根因**（`max_size` 误伤借用的 allocator_traits）

对 `deque` 的 0/4 做 triage，四条测试**全部**报同一处：

```
zhstdlib\双端队列:980: error:
  'std::allocator_traits<std::allocator<int>>' 中没有名为（成员名）'最大尺寸' 的成员
  ... _Alty_traits::最大尺寸(_Getal()));
```

即：`max_size → 最大尺寸` 的成员改名**误伤了借来的 `std::allocator_traits::max_size`**
（`_Alty_traits` 是我们给 `allocator_traits` 起的别名）。
这与 §13（`_Alty_traits::最大尺寸`）、§15.5（`bool_constant<...>::value`）是**同一类**。

**所以 `deque`/`list`/`vector`/`map`/`queue`/`unordered_map`/`semaphore` 这几个 0/4
大概率共用这一个根因** —— 先修它，可能一次通一片。

**修法（与 `<可选>` 的 `value` 完全同构，已实测过两次有效）**：
把 `max_size` 从该条目的 `members` 表**移出**（保护借用点），
中文名 `最大尺寸` 改在派生层用 `deriveExtra` 手写：
```cpp
模板 <类型名... 参数> 自动 最大尺寸(参数&&... 值) 常量 {
    返回 基类::max_size(static_cast<参数&&>(值)...);
}
```

⚠ **本轮两次落盘都踩了"作用域"的坑，都已回退**（仓库保持 64/64）：
1. 用 `String.Replace` → 替换全部匹配 → 块插多次；
2. 用"段内 Replace" → 我选的段（从 deque 到 `'scoped_allocator'`）**包含多个条目**，

### 16.10 `xpolymorphic_allocator.h`(368) 勘察：**混合型头**——一段可翻、一段必须原样

```
 25: template <class _Ty, class _Outer_alloc, class _Inner_alloc, class... _Types>   ← 我方助手模板（翻）
114: using _Pair_ref_t = _Normally_bound_ref<…>;                                      ← 同上
128: namespace pmr {
129: _EXPORT_STD class __declspec(novtable) memory_resource {                          ← ABI 身份（不翻）
171: _EXPORT_STD _NODISCARD inline memory_resource* get_default_resource() noexcept { ← ABI（不翻）
201: class polymorphic_allocator {                                                     ← 我方模板类（翻）
```

按 §16.7 判据逐个过一遍：

| 内容 | 判据 | 处理 |
|---|---|---|
| 助手模板（`_Normally_bound_ref`、`_Deallocate_bytes_guard`、……） | 改名不破坏身份 | **翻** |
| `polymorphic_allocator<Ty>`（模板类） | 同上 | **翻** |
| `std::pmr::memory_resource`（`_EXPORT_STD` + `novtable`，带虚表） | **改名破坏 ABI/虚表身份**（用户会跨边界传 `memory_resource*`） | **保留原名** |
| `get_default_resource` / `set_default_resource` / `new_delete_resource` … | 同上（导出函数，名字即链接身份） | **保留原名** |

> **好消息：这里不需要新机制。** 机制的默认行为就是"**没登记的就不改名**" ——
> 所以混合型头只要**只登记该翻的那些**，其余自然原样保留。
> （这一点值得记下来：混合型头在 `<可选>`（值类型 + 异常）已经用过一次，这是第二次，
> 说明"混合"是常态而不是特例，而现有机制本来就支持它。）

**这也顺带解释了步 2b 的存在意义**：`pmr` 名域里的名字（`polymorphic_allocator`）如果翻了，
`细节::pmr::多态分配器` 就是我们自己的；而 `std::pmr::memory_resource` 仍走
`使用 名域 std::pmr;` 借真头 —— 一个名域里"自有件 + 借件"并存，正是这套设计允许的形态。

**不登记** `memory_resource` 家族；生成 → 真测试 → 完整总判据。
