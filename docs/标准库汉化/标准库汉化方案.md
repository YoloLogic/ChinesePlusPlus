## 〇、这个模式是什么

**一句话**：把标准库**整段抄一份、整段翻成中文**，做成我们自己的库；再**在中文的基础上派生一层**，把英文原名补回来。

三层结构，缺一不可：

```
微软的 std::vector                    ← 一个字节都不动，原封不动
        │
        │  ① 抄一份，整段翻成中文（成员名、内部名、注释全部中文化）
        ▼
标准::细节::向量实现                    ← 第一层：中文实现。汉字在这里是第一公民
        │
        │  ② 在【中文的基础上】派生
        ▼
标准::向量                            ← 第二层：补回英文原名 + 与 std::vector 互转
```

**为什么必须是三层** —— 两条要求各逼出一条路，而它们不能合并：

| 要求 | 只有这一条路能给你 |
|---|---|
| **实现本身是中文的**（内部变量名、注释、成员名都是中文） | 必须**抄一份** —— 继承的话实现永远是微软那份，改不了 |
| **英文原名也还能用** | 必须**派生** —— 抄来的那份没有英文名，只能自己补回来 |

"抄来的中文实现"和"英文名自动免费"**不可兼得**（理由见 §四），所以形状只能是三层。

## 一、四条铁律（都是实测逼出来的，不是设计偏好）

### 1. 必须搬进自己的 `名域`，不能留在 `std`

抄来的那份**内部件**（`_Vector_val`、`_Vector_const_iterator`、`pointer_traits<…>`）如果留在 `std`，
就和微软 `<vector>` 的同名内部件**正面相撞**。

> **实测**：抄一份、只改类名 `vector` → `向量`、**留在 `std` 里**：
> * 单独用 → ✅ 0 错误
> * 与微软 `<vector>` 并存 → ❌ **20 个「重定义」**（`_Vector_const_iterator`、`_Vector_iterator`、`pointer_traits<_Vector_const_iterator<…>>` …）

搬进 `名域 标准` 之后，内部件也跟着搬走，**反而自动避开了撞车**。
所以"用 `标准` 而不是 `std`"不是可选项，**是让方案成立的关键**。

### 2. 必须写 `使用 名域 std;`，兜住对 `std` 内部件的引用

微软那份 `vector` 之所以能不写限定就用 `_Iterator_base`、`_Container_base`、`_Compressed_pair`、
`allocator_traits`，是因为**它自己就在 `std` 里**。搬到 `标准` 之后，每一处都变成未声明。

> **实测**：搬进 `名域 标准` 但不加兜底 → ❌ **20 处错误**，第一条是
> `未知的（种类 名字） 类名 '_Iterator_base'；你是不是想写（名字） 'std::_Iterator_base'？`
> 加上 `使用 名域 std;` 之后，只剩 `pmr` 那 2 处要手工理。

**代价（如实记）**：`使用 名域 std;` 会把 `std` 的两千多个名字一并可见，
所以 `标准::` 下面会多出一批"没打算中文化的英文名"。这不是缺陷，但要知道。

### 3. 英文名在派生层补，一个成员一行

抄来的第一层里**只有中文名**。英文原名靠第二层逐个转发回来：

```cpp
模板 <类型名 元素, 类型名 分配器 = std::allocator<元素>>
类型 向量 : 公开 细节::向量实现<元素, 分配器> {
    使用 基类 = 细节::向量实现<元素, 分配器>;
    使用 基类::基类;                              // 继承全部构造函数

    模板 <类型名... 参数> 空型 push_back(参数&&... 值) { 基类::压入(static_cast<参数&&>(值)...); }
    自动 size() 常量 { 返回 基类::尺寸(); }
    // …… 其余英文名各一行
};
```

**为什么不用继承 `std::vector` 来白拿英文名** —— 那样英文名确实免费，
但实现就永远是微软那份，第一层就不存在了。这正是用户在 §〇 里要排除的。

### 4. 有一类类型**不能抄、也不能派生，只能用别名** —— 凡是「类型身份本身参与语义」的

**异常类型是这一类里最要命的。** 实测（`build\_excp.ps1`）：

| 场景 | 结果 |
|---|---|
| 第三方抛 `std::runtime_error`，用中文名 `标准::运行时错误&` 捕获 | ❌ **抓不到**，落进 `捕获 (...)` |
| 同一次抛出，用英文原名 `std::runtime_error&` 捕获 | ✅ 抓到 |
| 抛我们自己的（派生的）中文异常，用 `std::logic_error&` / `std::exception&` 捕获 | ✅ 抓到 |

根因是 C++ 的 `捕获` 语义：`捕获 (X&)` 能接住抛出的 `Y`，**当且仅当 Y 可转换为 X**。
所以 **base → derived 永远不通** —— 这跟"抄一份还是派生"无关，是**方向**问题。

**后果是静默失败**。用户写：

```cpp
尝试 { 第三方英文函数(); }
捕获 (标准::运行时错误& e) { 处理(e); }     // ← 抓不到！
```

异常会**逃出去**（落进 `捕获 (...)`，或没人接就直接 terminate），而且**不报编译错误**。

**正确做法：这类类型用别名 —— 别名是同一个类型，捕获语义一字不改。**

```cpp
名域 标准 {
    使用 运行时错误 = std::runtime_error;      // 同一个类型
    使用 逻辑错误   = std::logic_error;
    使用 异常       = std::exception;
}
```

于是 `捕获 (标准::运行时错误& e)` 与 `捕获 (std::runtime_error& e)` **完全等价**。

**这一类包含哪些**（判断标准：**类型身份本身是否参与语义**）：

| 类别 | 为什么必须同一类型 |
|---|---|
| **异常类型** | 捕获按类型匹配，见上 |
| **RTTI / `类型标识` / 动态转换** | 换了类型就换了 `type_info` |
| **跨预编译库边界的类型**（`std::string`、`std::filesystem::path` …） | DLL 导出的签名里写死的是 `std::string` |
| **按类型特化的模板**（`std::hash`、`std::tuple_size`、`std::get` …） | 特化挂在原类型上 |
| **标准规定的 traits / 概念检测** | 检测结果按类型算 |

其余类型（容器、算法、迭代器这些"用成员、用行为"的）**可以**抄一份 + 派生兼容层。

**于是整个方案是两条路并用**：

```
要中文成员名        →  抄一份 + 派生兼容层（本方案主体）
类型身份即语义      →  别名（同一类型，零风险）
```

> 📌 这一条是**在一个现已删除的老文件的提醒下查出来的** —— `examples\zhstd.h`
> （**已于 2026-09-27 删除**，长期无人使用）头部那三条警告里，第二条正是
> 「`std::string` / `std::exception` 这类跨边界类型变成"另一种类型"」。
> 本项目 2026-09-24 就写下了这条预判，本次实测把它变成了**可复现的证据**。

### 2.2 译名从哪来（**优先级，按顺序查**）

**一个新译名不是"想出来"的，是"查出来"的。** 按这个顺序查，前一张表有就照抄：

| 顺序 | 查哪 | 位置 | 条数 | 管什么 |
|---|---|---|---|---|
| 1 | **关键字表** | `LLVM-main\clang\include\clang\Basic\ChineseKeywords.def` | 88 | 语言关键字：`字符`(char)、`类型`(class)、`模板`、`名域`、`常量`、`空型` … |
| 2 | **诊断表** | `LLVM-main\clang\include\clang\Basic\ChineseDiagnostics.def` | 7344 | **技术术语的大本营**：`字符串`、`迭代器`、`容器`、`指针`、`数组`、`引用`、`常量字符` … |
| 3 | 都没有 | —— | —— | 才按最合适的中文新定，并**登记进 §2.1 / §2.2 的对照表** |

> **为什么诊断表排第 2**：它已经翻了 7344 条，把英文技术词汇的中文对应一次性定下来了。
> 标准库译名若与它不一致，就会出现**"报错里叫 X、代码里叫 Y"**的分裂。
>
> ⚠️ **注意 `string` 不在关键字表里** —— 因为 `string` 不是关键字，是标准库类型名。
> 关键字表里含"字符"的只有 5 条：`字符`(char) / `字符8位` / `字符16位` / `字符32位` / `宽字符`。
> `字符串` 是**诊断表**定下的（凡英文正文是 "string" 的都译 `字符串`）。

**已从诊断表确认、可直接用的术语**：

| 中文 | 英文 | 诊断表里的证据 |
|---|---|---|
| `字符串` | string | `err_bad_string_encoding` →「字符串字面量中的字符编码非法」 |
| `迭代器` | iterator | `err_for_range_iter_deduction_failure` →「不能把类型 X 用作迭代器」 |
| `容器` | container | `warn_unused_container_subscript_expr` →「容器访问的结果未被使用」 |
| `常量字符` | `const char` | `warn_cxx20_compat_utf8_string` →「从 常量字符 数组变为 常量字符8位 数组」 |

**⚠️ 已经另有含义的词（用之前要知道会撞）**：

| 中文 | 诊断表里**现在**的意思 | 我们想用它做 | 诊断表里的证据 |
|---|---|---|---|
| `向量` | **SIMD 向量**（GNU / NEON / SVE 向量类型） | `std::vector` → `标准::向量` | `err_attribute_bad_neon_vector_size` →「Neon 向量大小必须是 64 位或 128 位」 |
| `映射` | **OpenMP 数据映射 / 模块映射** | `std::map` → `标准::映射` | `err_omp_duplicate_map_type_modifier` →「同一个映射类型修饰符被指定了多次」 |
| `集合` | **Objective-C 集合** | `std::set` → `标准::集合` | `err_invalid_collection_element` →「集合元素的类型…不是 Objective-C 对象」 |

**判断（用户 2026-09-27 已确认）**：
* `向量` 的歧义与英文自身同构（English 里 `vector` 也同时是容器和 SIMD），**可以接受**。
* `映射` / `集合` **保留**。用户的原话：「如果原本的英文直接翻译就是那样的，我觉得映射和集合完全没问题」
  —— 即：只要是英文的**直接对译**，同词不同义不算问题。
* 备选（`字典` / `集`）**不采用**，仅留作记录。

## 三、工序：四个阶段（**必须先全部复制，再统一改**）

> ⚠️ **工序是用户 2026-09-27 纠正的，理由不是形式而是实质。**

一个文件端到端地改（复制 → 改名 → 派生层）会出**跨文件漂移**：
`vector` 里的 `size` 叫 `尺寸`，`map` 里的 `size` 可能被叫成 `个数`。
**译名表必须全局建好再套用。** 实测也印证了这点：手写派生层时用了 `引用` / `大小类型`，
而当时那张 29 个名字的小表里根本没有它们 —— **自己跟自己就对不上**。

| 阶段 | 做什么 | 验收 | 脚本 |
|---|---|---|---|
| **1 复制** | 112 个公开头**全部**复制到 `zhstdlib\`，**只做结构改造**（换守卫、搬 `名域 标准 { 名域 细节 {`、写 `使用 名域 std;`），**名字一个都不改**，文件名也先沿用英文 | **112 个逐个能编过** | `tools\copy_zhstdlib.ps1` |
| **2 建译名表** | 2,128 个公开名 ＋ 112 个头文件名 ＋ 34 个内部件名，**一次性定完** | 表完整、无遗漏、**无跨文件冲突**（同一个英文名全库只能有一个中文名） | 待写（阶段 2 的产物） |
| **3 套用** | 用译名表批量改名 ＋ **让编译器当校对**（借用类型的同名成员按它报的坐标改回英文） | 全部编过 | `tools\make_zhstdlib.ps1` |
| **4 派生层** | 每个公开类追加派生层，把英文原名补回来 | 中文名 / 英文名 / 与 `std` 并存，三项通过 | 同上 |

**阶段 1 为什么能单独验收**：结构改造（换守卫、搬名域、写兜底）对**每一个**头文件都成立，
而且不依赖任何译名 —— 所以它可以先做完、先整体验一次。
逐个编译 112 个，就是在证明"结构改造不是只对 `vector` 成立"。

### 3.1 单个文件的改造细节（阶段 3/4 用的配方）

抄一份 `<vector>` → 改成 `<向量>`，实测可行的步骤：

| 步 | 做什么 | 实测数量（`<vector>`） |
|---|---|---|
| 1 | 换守卫：`_VECTOR_` → `_ZH_VECTOR_`（不抢微软的守卫） | 2 处 |
| 2 | `_STD_BEGIN` → `名域 标准 { 名域 细节 {` ＋ `使用 名域 std;`；`_STD_END` → `} }` | 各 1 处 |
| 3 | 类名 `vector` → `向量实现`（正则 `\bvector\b`） | **345 处 / 13 个名字** |
| 4 | 成员名逐个译成中文 | **390 处 / 29 个名字** |
| 5 | 手工理嵌套名域（`pmr` 那类）的引用 | **2 处** |
| 6 | 追加第二层：`名域 标准 { 类型 向量 : 公开 细节::向量实现 { …英文名 + 转换… }; }` | 新写 ~50 行/类 |

**内部名不会被误伤**：MSVC 的内部名用 `_Vector_val`（大写 V），
正则 `\bvector\b` 只匹配小写的公开类名。

**译名表是真正的工作量**：`std` 里共 **2,128 个公开名**（含内部名 7,575 个）。

### 3.2 两个已经踩到、必须写进脚本的坑

**坑①：不能对整个文件做"全局字符串替换"。**
第 5 步曾对 `polymorphic_allocator` 做全局替换，结果把文件顶部的
`#include <xpolymorphic_allocator.h>` 改成了 `<xstd::pmr::polymorphic_allocator.h>` ——
文件名被改坏，立刻 `fatal error: 找不到文件`。
（同类教训本项目已有：`verify_chinese_keywords.py` 第一版整文件替换把注释里的 60 处文档改坏。）
**凡"整文件替换"都要先想清楚它会碰到哪些非代码文本。**

**坑②：成员名改名会撞上"借用类型的同名成员"，必须让编译器当校对。**
实测 `<vector>` 的 29 个成员名里 **3 个会撞**：`begin` / `end` 撞
`std::initializer_list` 的 `begin/end`，`swap` 撞 `std::swap`。
文本替换分不清"我们类的成员"和"借用类型的同名成员"，**编译器分得清，而且给出行列号**。
所以要：编译 → 读它报的「没有名为 X 的成员」→ 按坐标把那一个标识符改回英文 → 再编译，直到干净。
实测：第 1 轮 9 处，第 2 轮干净。

> ⚠️ **列号是【字节】偏移，不是字符偏移。** 第 3045 行报第 33 列，
> 而前 32 个字节正是 `        插入(开始(), _Ilist.`（中文一字 3 字节）——
> 按字符算会全部落空（第一版 10 轮只改中 1 处）。一律用 UTF-8 字节比对，再折回字符下标。

### 3.3 阶段 1 实测：112 个文件**不是同一类**，必须先分类

阶段 1（全量复制 + 逐个验证）的结果：**112 个文件复制成功，但逐个编译只有 33 个通过**。
79 个失败，几乎全是同一个根因，而它暴露了一件设计层的事：

`zhstdlib\cstddef` 第 100 行 `} }`（我们搬进去的名域已结束），第 103 行是

```cpp
_EXTERN_CXX_WORKAROUND
using _STD max_align_t; // intentional, for historical reasons
_END_EXTERN_CXX_WORKAROUND
```

**`using std::max_align_t;` 是一条"桥"**：原本 `cstddef` 先把全局的 `max_align_t` 引进 `std`，
再从这里引回全局。文件被搬进 `标准::细节` 后，第一步没落进 `std`，第二步就找不到 `std::max_align_t`。

**根因不是 bug，是分类错误**：`cstddef` 是 **C 包装头** —— 它自己没有实现，
只是把 C 库的名字搬进 `std`。而 `max_align_t` 这类类型**必须与 `::max_align_t` 是同一个类型**
（对齐 / ABI），这**正是铁律 4**：「类型身份本身参与语义的，只能用别名，不能抄也不能派生」。
**所以把 `cstddef` 抄一份，从设计上就错了。**

于是阶段 1 要加一个子步骤 —— **先分类，再决定哪些抄、哪些只做别名**：

| 类别 | 例 | 做法 | 依据 |
|---|---|---|---|
| **C 包装头**（约 30 个） | `cstddef` `cstdint` `cstdio` `cstdlib` `cstring` `cmath` `ctime` … | **别名层**（`使用` 同名事物），**不抄** | 铁律 4：类型身份参与语义（`max_align_t` / `size_t` / `FILE` …） |
| **真正的 C++ 库头** | `vector` `string` `map` `algorithm` … | **抄一份 + 派生兼容层** | §〇 三层结构 |
| **工具头**（只有模板/宏，无实体） | `type_traits` `ratio` `limits` `version` … | 待定，仍需逐个分类 | —— |

> 📌 **这正是"先全部复制、再统一改"的价值**：如果一个文件端到端地做，
> 会在 `vector` 上"通过"，然后到第 40 个文件才炸。全量复制 + 逐个验证
> 一次就把类别问题暴露出来了。

### 3.4 甲类（C 包装头）别名层：**三种机制，不是一种**

第一轮实测 8/25 通过，错因是**只用了"类型别名"一种机制**。正确做法是按种类分开：

| 种类 | 例 | 机制 | 为什么 |
|---|---|---|---|
| **类型** | `size_t` `FILE` `tm` `jmp_buf` `fenv_t` | `使用 中文名 = std::原名;` | 类型别名声明，**同一类型** ✓ |
| **普通函数** | `fopen` `strlen` `sqrt` `malloc` | `模板 <类型名... 参数> 自动 中文名(参数&&... 值) { 返回 std::原名(static_cast<参数&&>(值)...); }` | **函数没有"别名"机制** —— `使用 std::fopen;` 引入的是**原名 fopen**，不会变成「打开文件」 |
| **变参 C 函数** | `printf` `scanf` `sprintf` | **只能原名引入**，或按固定 arity 写重载 | C 变参**无法完美转发**（模板参数包接不住 `...`） |
| **值宏** | `EOF` `INT_MAX` `FLT_MAX` `NULL` | `内联 常量 类型 中文名 = 原名;` | 宏不是实体，只能造一个常量承载它的值 |
| **函数式宏** | `assert` `va_start` | `#定义 中文名 原名` | 宏替换是文本级的，`#定义` 是唯一对称手段（本项目已论证过代价对称） |

> ⚠️ **这两条约束本来写在 `examples\zhstd.h` 里**（「函数不能起别名……只能写一层
> 内联转发」「变参函数没法完美转发，只能原样引入」），而那个文件 **2026-09-27 被删除时，
> 我只写了"已删除"，没把它的设计约束搬过来** —— 于是写生成器时直接踩了回去。
> **规矩：删/改任何旧文件，必须把它携带的设计约束搬进本文档，而不只是记一句"已删除"。**

**另一条命名教训**：中文标识符**不能以数字开头**。`16位字符` 非法
（`缺少非限定标识符`）。关键字表的既有构词法是**后置**：`字符8位` / `字符16位` /
`字符32位` —— 所以是 `字符16位`、`整数8位`。这正是 §2.2「先查关键字表」的用处。

### 3.5 还有一个会静默毁掉全局的问题：**文件名 shadow**

阶段 1 把 112 个副本**沿用英文文件名**放进 `zhstdlib\` —— 于是 `zhstdlib\cstddef`
**把真正的 `<cstddef>` 挤掉了**。凡 `#include <cstddef>` 的都拿到我们那份，全炸。

**所以中文文件名不是"最后美化一下"，它是阶段 1 就该做的**：
副本必须以**中文文件名**存在（`zhstdlib\向量`），这样 `<vector>` 仍解析到微软真头，
`<向量>` 才是我们的。两者的关系是"并存"，不是"覆盖"。

对应的处置：甲类 26 个的副本已删除（改用中文别名头），乙/丁类的中文文件名在阶段 2
（译名表）里一并定，届时改名后需**重跑全量验证**。

### 3.6 `friend` 声明会跨头失效 —— 又一条"必须先分类"的理由

实测 `condition_variable`：`condition_variable_any` 的实现直接访问
`std::_Mutex_base::_Mymtx`，而那是微软在 **`<mutex>`** 里用 `friend` 声明授权的。
friend 声明里写的是**原来的类名**；我们把类改名成 `标准::细节::条件变量任意实现` 之后，
**那份友谊不认它了**，于是三处访问全部报「是 `std::_Mutex_base` 的私有成员」。

修法只有一条：**把 `<mutex>` 也一起抄下来，并把其中的 friend 声明一并改名**
（两边都是我们的，改得动）。所以：

> **凡是"实现伸进别的头的私有成员"的类，单独抄它自己是没用的 ——
> 必须把提供 friendship 的那个头也抄进来。** 这属于步骤 1（内部头/依赖头）的范围，
> 但它说明步骤 1 里的某些头**不是"最后再补"，而是被步骤 2 的某些头硬依赖的**。

分类时要标出这一类头（例：`condition_variable` ← 依赖 `<mutex>`），
把它们排到"需要先抄依赖"那一组。
