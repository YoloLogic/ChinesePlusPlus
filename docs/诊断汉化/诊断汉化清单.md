## 一、一句话

**报错的"正文"变中文，其余一切不动；表里查不到就原样回退英文。**

```
error: 未使用的变量（变量名） '甲' [-Wunused-variable]
^^^^^^                                                   ^^^^^^^^^^^^^^^^^^^^
前缀没动                                                 选项名没动
       ^^^^^^^^^^^^^^^^^^^^^^^^^^^
       只有正文换了
```

因为"查不到就回退"，这张表可以**分批做、永远不完整**，
不需要追平上游，LLVM 升级也不会漏、不会崩——新诊断自动是英文。

## 三、为什么挂钩点只有一个

全 clang 只有**一处**取诊断正文文本：

```cpp
// clang/lib/Basic/Diagnostic.cpp
void Diagnostic::FormatDiagnostic(SmallVectorImpl<char> &OutStr) const {
  ...
  StringRef Diag = Diags->getDiagnosticIDs()->getDescription(getID());
  if (Diags->getDiagnosticOptions().ChineseDiagnostics) {   // ← 加的三行
    StringRef ZH = getChineseDiagnosticText(getID());
    if (!ZH.empty())
      Diag = ZH;                                            // 查不到就保持英文
  }
  FormatDiagnostic(Diag.begin(), Diag.end(), OutStr);
}
```

（`grep -rn "getDescription(" clang/lib` 里，取"诊断描述"的调用只有这一处；
其余同名函数都是"类型/检查器描述"，与诊断文本无关。）

因此纯文本输出、`-fdiagnostics-format=json`、SARIF、fix-it
全都自动一致，而且**只影响最终文本**：

- 不动诊断分类、等级、`-W` 分组 → `-Werror`、`#pragma clang diagnostic` 照旧
- 不动 `DiagID` / 稳定 ID → PCH、模块、`-fdiagnostics-serialize` 照旧
- 占位符（`%0` / `%select`）照旧由同一个格式化器替换 → 参数显示不变

## 四、三条硬约束

1. **只换正文** ✓
   `error:` / `warning:` / `note:` 前缀、`[-Wxxx]` 选项名、行列号、
   源码片段、fix-it 一律不动。否则 CI 和编辑器里按 `error:` 抓取的脚本会全断。

2. **查不到 → 原样返回英文** ✓✓
   这是"部分翻译安全"的保证，也是不需要追平上游的原因。

3. **术语与关键字表逐字一致** ✓
   诊断里的类型名、限定词必须和 `ChineseKeywords.def` 的译名相同，
   否则用户看到的报错和他写的代码对不上。例如：
   类型(class) / 名域(namespace) / 结构(struct) / 常量(const) /
   重载(overload) / 重写(override) / 显式(explicit)。

### 附：`error:` / `warning:` 前缀**故意不翻**（已定，勿再议）

2026-09-22 决定：**前缀保持英文**。理由是这几个词太简单，而且这个位置是
**给机器读的**，不只是给人读的：

| 谁在读 | 翻了会怎样 |
|---|---|
| **VS Code 的 C++ 问题匹配器** | 它的正则写死了 `(warning\|error\|note):` → 前缀一变中文，**Problems 面板直接空掉**（没有红点列表、点不过去） |
| CI / 日志脚本 | `grep -i "error:"`、`scan-build` / `clang-tidy` 包装脚本都按英文抓 |
| LLVM 自己的 `-verify` | ✅ 不受影响（按诊断**等级**比，不按打印出来的前缀） |

所以 `error:` 与 `[-Wunused-variable]` 属于同一类：**机器依赖的标记**，与"正文"性质不同。
**只换正文**这条约束覆盖它们。

> 万一以后改主意，位置在
> `clang/lib/Frontend/TextDiagnostic.cpp:775-783`（就一个 `switch`），
> 第二处调用点是 `TextDiagnosticPrinter.cpp:137`，
> 结尾汇总句在 `CompilerInstance.cpp:1082/1086`。
> 可以复用现有的 `ChineseDiagnostics` 开关，**不必新增选项字段**
> —— 因此不需要再来一次全量重编，只编 `clangFrontend` + 重链。
> 同时要改 `.vscode\tasks.json` 加一个中文 problem matcher，否则 VS Code 面板会空。

## 六、怎么再加一批（4 步）

### 第 1 步：抄英文原文——**抄生成的 `.inc`，不要抄 `.td`**

```
E:\Chinese++\build\tools\clang\include\clang\Basic\Diagnostic*Kinds.inc
```

搜英文句子，找到那一行：

```
DIAG(note_ovl_candidate_bad_conv, CLASS_NOTE, ..., "candidate %select{function|...}0 not viable: no known conversion from %3 to %4 for %select{%ordinal6 argument|object argument}5", ...)
```

ID 是第 1 个参数，消息是第 4 个，**直接复制第 4 个字符串**。

> ⚠️ **为什么必须抄 `.inc`**：源表 `.td` 里的 `%sub{...}` 和
> `%enum_select<...>{...}` 在生成时就被**展开**了。例如
> `.td` 写的是 `%sub{select_ovl_candidate_kind}0,1,2`，
> 生成出来是 `%select{function|constructor|...}0`。
> 拿 `.td` 翻译会漏掉整段分支。（实测：7248 条 `.td` 定义 →
> 7374 条生成条目，其中 **146 条**名字只在 `.inc` 里、
> **128 条**文字与 `.td` 不同。）

### 第 2 步：在 `ChineseDiagnostics.def` 里加一行

```c
ZH_DIAG(err_unknown_typename, "未知的类型名（类型名） %0")
```

- 占位符 **一个都不能动**（位置可以按中文语序调整，序号不能变）
- ID 写错会**编译报错**（`switch` 里没有这个 `case`），这是好事
- 术语查第一节那张对照表

### 第 3 步：机器校核

```powershell
python E:\Chinese++\tools\diag_id_lookup.py --check-table
```

它逐条检查：

| 检查项 | 说明 |
|---|---|
| ID 在生成表里存在吗 | 拼错直接报出来 |
| 引用了哪些参数 | **多重集**比较 —— 允许中文语序与英文不同（`no B in A` → `A 中没有 B`） |
| 每个分支占位符的种类 / 挂的序号 / 分支数 | `%select` `%plural` `%diff` 都要对 |
| **分支顺序** | 按文档顺序比各分支的"原子画像"（分支就是下标，顺序不能换） |
| 中文正文里混着的英文词 | **只报告不判失败** —— `';'` 与 `'typename'` 这种该保留，由人确认 |

**任何一条对不上就退出码 1。**

校核器自己也有测试（`--self-test`：故意写坏 6 种占位符 + 分支顺序颠倒
+ 英文残留检测，确认它真的会报错）—— 一个永远返回"通过"的检查等于没有检查。

> ### 校核器**抓不到**的两件事（别以为它全包）
>
> 1. **纯 `%0`/`%1` 对调**：两者结构完全等价，多重集比较看不出来。
>    暴露面其实很小：32 条里只有 5 条引用了两个以上不同实参，其中 4 条
>    **在运行时断言里有强串**（如 `04_no_member.cpp` 断言
>    `（类型名） '点' 中没有名为（成员名） 'y' 的成员`，对调后必然变红）。
> 2. **某个 `%select` 的所有分支彼此原子画像相同时**（如 `%select{非|}`），
>    颠倒分支顺序在结构上也看不出来。
>
> 这两点由**运行时逐条断言**兜底：`tests\12-diagnostics\` 对实际会被触发的
> 条目断言"输出必须出现这一句、英文那句必须消失"。所以规矩是：
> **没写断言的条目 = 没被验证的条目。**
>
> （这两条局限是独立复核者 2026-09-22 指出的 —— 本文档原先把校核器的
> 能力说大了，已按实际情况改写。）
>
> **曾经还有一个更危险的盲区，现已堵上**：校核器原本**不查条目条数** ——
> 表被截断/被误删时，剩下的条目依然条条合法，于是它报 0 问题、退出码 0。
> 复核者实测把 32 条砍到 7 条仍然"通过"。现在有两条独立机制兜它：
> `MIN_ENTRIES = 7344` 下限（每加一批就同步抬高），加表尾 `#undef ZH_DIAG` 收尾检查。
> **减少条目是允许的，但要同时改 `MIN_ENTRIES` 并写明原因** ——
> 这是故意留的手续，防止"表悄悄变小"。

## 七、占位符语法与两处"允许的改动"

| 写法 | 含义 | 中文里怎么办 |
|---|---|---|
| `%0` `%1` | 普通参数 | 原样保留 |
| `%select{a\|b}0` | 按参数 0 选分支 | 原样保留，**分支顺序不能换**（参数就是下标） |
| `%plural{1:x\|:y}0` | 复数形式 | 原样保留（中文可只留一个分支，但分支数要一致） |
| `%diff{a$\|b}1,2` | 两个类型的差异 | 原样保留 |
| `%s0` | 英文复数的 `s`（参数为 1 时输出空） | **可以直接删掉** —— 中文没有单复数 |
| `%ordinal0` | 英文序数（`1st`/`2nd`） | **可以改成 `%0`** —— 中文写"第 `%0` 个" |
| `%q0` `%quoted0` `%human0` | 限定名 / 加引号 / 人类可读 | 原样保留（换了就变语义） |

前两种"允许的改动"校核器认识；其余任何改动都会被抓出来。

### 中文正文的排版约定：空格只出现在「词块交界处」

**不是每个汉字之间都空格。** 词块内部连写，词块之间空格。

```
未使用的变量（变量名） '甲'           ← 词组内部不空格；（角色词）紧贴前词块
使用了未声明的标识符（名字） '甲'      ← 同上
声明末尾缺少 ';'                      ← 词组内部不空格；汉字↔拉丁，空格
不能给常量限定类型（类型） 'const int' 的变量（变量名） '甲' 赋值  ← 汉字词组连写，交界处空格
缺少 非限定标识符                    ← 「缺少」与「非限定标识符」是两个词块 → 空格
不能给 变量（变量名） 'x' 赋值，它带有 嵌套 常量限定数据成员（成员名） 'y'  ← 同上
```

三条可操作的判断：

| 情况 | 空格？ | 例 |
|---|---|---|
| 一个词/词组内部（含并列复合词） | ❌ 不空格 | `未使用的变量`、`非静态数据成员`、`常量限定类型` |
| 两个词块交界（动宾、主谓、修饰） | ✅ 空格 | `缺少 非限定标识符`、`不能给 变量（变量名） …`、`它带有 嵌套 …` |
| 汉字 ↔ 拉丁/数字/占位符 | ✅ 空格 | `未使用的变量（变量名） '甲'`、`（类型名） %1 中没有名为（成员名） %0 的成员` |
| 角色表 ↔ 它前面那个词块 | ❌ 不空格 | `缺少（符号） %0`、`未使用的变量（变量名） '甲'` |

**空格不参与语法、不影响渲染，纯粹为了可读性。** 连成一长串（`缺少非限定标识符`）
读起来费劲，中间隔开一眼能断句。

唯一的技巧是 `%select` 分支：如果空格只该在某个分支出现，就把空格写在
**分支内部**，例如

```
它带有 %select{|嵌套 }3常量限定数据成员 %4
        ^^^^^^  空分支   → "它带有 常量限定数据成员"
                 "嵌套 " → "它带有 嵌套 常量限定数据成员"
```

（分支内的空格有且仅有这一个作用，改动它不影响任何东西。）

## 九、实测发现（都是踩出来的，别再踩）

### 1. 生成表才是准的，源表不是

`.td` 里的 `%sub{...}` / `%enum_select<...>{...}` 在生成 `.inc` 时被展开。
**翻译必须抄 `.inc`。** 另外 7374 条里有 146 条在 `.td` 里根本搜不到名字
（`compat_c*` 那批由 `multiclass` 实例化而来）。

### 2. 一条英文可能对应多个诊断 ID

```
DIAG(warn_unused_variable,       ..., "unused variable %0", ...)
DIAG(warn_unused_const_variable, ..., "unused variable %0", ...)
```

正文一模一样，ID 不同。**所以表必须按 ID 查，不能按英文原文查**
（按英文原文查会塌成一条，将来想区分时无从下手）。

### 3. 总条数是 **7374**，不是 6722

路线图里写的 6722 是旧数字。按文件分布：

| 文件 | 条数 |
|---|---|
| `DiagnosticSemaKinds.inc` | 5033 |
| `DiagnosticParseKinds.inc` | 729 |
| `DiagnosticLexKinds.inc` | 429 |
| `DiagnosticDriverKinds.inc` | 369 |
| `DiagnosticASTKinds.inc` | 281 |
| `DiagnosticFrontendKinds.inc` | 201 |
| `DiagnosticCommonKinds.inc` | 168 |
| 其余 6 个文件 | 164 |
| **合计** | **7374** |

### 4. `%sN` 与 `%ordinalN` 是"英文专用"的

- `%sN`：参数为 1 时输出空，否则输出 `s` —— 中文直接删
- `%ordinalN`：**硬编码英文序数**（`1st`/`2nd`）
  —— 中文写 `第%0个`，用普通 `%0` 取整数

### 5. 开关：默认开，`-fno-chinese-diagnostics` 关

默认开，因为"汉字第一公民"。留开关是为了：
跑上游 `clang/test`（成千上万个 `-verify` 断言写的是英文原文）、
或者想要英文输出的场合。

开关走的是 clang 标准的选项编组（`BoolFOption` + `MarshallingInfo`），
所以 `-###` 往返、`-cc1` 命令行、PCH/模块的选项序列化都自动一致。

### 6. MSVC 的 `/utf-8` 是全局的，漏了会**静默**失败

中文表里的字符串是 UTF-8 字节。MSVC 默认按当前代码页（简中是 GBK）
读源文件，于是中文变成乱码 —— **不报错，只是显示不对或匹配不上**。
`/utf-8` 在顶层 `llvm/CMakeLists.txt` 里全局设置，关键字表与诊断表共用。

> 顺带发现：原来的 `patches\zh-keywords.patch` **只扫 `clang\`**，
> 而 `/utf-8` 那一行在 `llvm\CMakeLists.txt` 里 —— 也就是说那份补丁
> 在 MSVC 上应用后，中文会静默失效。已修 `tools\make_patch.ps1`：现在扫
> `clang\` + `llvm\`，并在开头断言两棵树顶层目录一致。

### 🆕 排版约定：角色表（第三批起）

正文里的「成分」前面写一张角色表，用全角括号，**按顺序一一对应**：

```
调用了未声明的函数（函数名） 'foo'；ISO C99 及以后的版本不支持隐式函数声明
未使用的（种类 类型名） 类型别名 '丙'
（关键字） 常量表达式 变量（变量名） 'P' 必须用编译期常量初始化
```

- **封闭词表（12 个）**：关键字 种类 变量名 类型名 函数名 属性名 成员名 名字 表达式 类型 符号 选项
  —— 加词是一次**明确动作**（要同时改 `ChineseDiagnostics.def` 与 `tools\diag_id_lookup.py` 的 `ROLE_WORDS`）
- **并列成分用连词分开**：角色表**按位置一一对应**，连词照写（要用空格与角色词分开），
  例如 `二元表达式的运算对象无效（表达式 和 表达式）（%0 和 %1）`
  —— 连词表同样是封闭的（`ROLE_CONNECTORS`），而且**光有连词不算角色表**（校核器会硬失败）
- **能确定的写具体角色，不能确定的写（名字）**
- **角色表写在哪取决于成分在哪**：成分在分支之外就写在分支之外；分支只是续接片段
  （如 `%select{非|}`）就不写；成分**只**出现在分支里、或分支本身是完整从句时，
  角色表写在该分支内紧贴成分（整句就是一个 `%select` 的条目只能这样标）
- **含占位符的括号组不算角色表** —— 既有条目有用括号做补注的（如 `（%0 和 %1）`），硬套词表会误判
- **角色表的排版**：`（角色词）` 紧贴它**前面那个词块**（不空格），角色表与成分之间按
  「汉字 ↔ 占位符」规则空格 —— 写作 `缺少（符号） %0`，不写 `缺少 （符号）%0`。
  句子已经点明角色时**照样标**（如 `未知的类型名（类型名） %0`）——
  这是刻意选择的统一，代价是冗余，换来的是「每条都有角色表」这个可机器校核的性质。

> 这个约定的意义：英文把关键字（`typedef`）和术语（`type alias`）混在句里从不标注；
> 我们给每个成分都标了角色，而且词表是封闭、可机器校核的。
> **中文报错在这个维度上比英文更规整** —— 代价是句子更长。

性质不覆盖它。改成断言**正文**逐字节相同，并单独断言摘要行跟着开关走。

**两个工具对账**：`diag_frequency.py` 现在把三个数分开列（参与排名 / 驱动·前端自身 /
未能反查），三块相加 = 4980，与 `diag_coverage.py` 的总数一致。**对不上就说明有实例又丢了**
（这正是它原来的毛病：识别到但属于驱动前缀的实例两个分支都不走，凭空消失）。

⚠️ **撤回记录**：本清单早期写的 **0.43%（32 条）**、对外说过的 **85.2% / 80.7% / 61.3%**，

看不见 1090 条；而且**英文被丢 32.2%、中文只丢 17.5%**，丢得不均匀，把比例抬高了。
**当前数字一律以 [`docs\README.md`](../README.md) 的「当前实测」为准。**

### 未覆盖部分的结构：翻了主句、漏了兄弟 ID（同一次实测）

1495 条未覆盖实例里：**1014 条（67.8%）能唯一贴上 ID**、266 条（17.8%）是多个 ID 共用

## 十九、P 档批量汉化：2654 条（2026-09-24）

### 这一批是怎么选的

先把 7374 条按英文正文的**形态**分档（`build\_diag_tiers.py` 实测）：

| 档 | 条数 | 特征 | 本批 |
|---|---|---|---|
| **P 纯句子** | 2683 | 无占位符、无分支，一句话换一句话 | **做了 2654 条** |
| V 有值占位符 | 3867 | 翻 + 每条挂角色表 | 未做 |
| S 只有 `%select` | 791 | 翻 + 保住分支数与顺序 | 未做 |
| F 纯片段 | 3 | 拼进别的句子 | 未做 |
| E 空或纯占位符 | 30 | `"%0"` 这种，没有英语可翻 | 不适用 |

**可翻总量 = 7341 / 7374 = 99.6%**。P 档之所以先做：它不需要角色表，
结构风险为零 —— 门禁能**静态证明**它的正确性，不必逐条构造触发用例。

### 为什么之前只有 90 条

不是 90 有多大，是**频次曲线是幂律**。clang/test 400 个文件实测：

```
前   1 个 ID   →  27.1% 的实例
前   5 个 ID   →  60.2%
前  10 个 ID   →  72.0%
前  70 个 ID   →  88.8%      剩下 231 个 ID 共 435 条，平均每个 1.9 次
```

400 个文件（编译器自己的酷刑测试集）只碰到 **301 个不同的 ID** = 全表的 4%。
按频次挑 90 条能拿到真实项目 99.3%，但表面覆盖率只有 1.2%。这一批补的是**长尾**。

### 机器强制的不变量（`tools\diag_id_lookup.py`）

这批没法逐条写触发用例，所以把"能静态证明的部分"全部交给门禁，每条都带自检：

| 检查 | 拦什么 |
|---|---|
| `check_protected_tokens` | 引号里的**代码记号**必须还在；**关键字**必须写 `（关键字） 中文关键字`（不能留英文原拼写） |
| `check_percent_escapes` | `%%` 数量必须一致（`%%` 渲染成一个字面 `%`） |
| `check_keyword_markers` | `（关键字） ` **只能标在英文加了引号的关键字上** —— 裸提及（`for loop`、`class member`）是普通散文 |
| `KW_IS_DSL_TOKEN` | 6 处显式例外：OpenMP/OpenACC 的**子句名/枚举值**拼写碰巧和关键字一样，必须保留英文 |
| `check_role_table` | 角色表词表；2026-09-24 收窄为「含角色词的全角括号组才算角色表」，补注（`（plain old data）`）不再误判 |

`MIN_ENTRIES` 从 90 抬到 **2744**。

### 这一批撞出来的 4 个真 bug（都已修 + 补断言）

1. **每次编译成功都多打一行「生成了 」**。`CompilerInstance.cpp` 里中文前缀写在了
   「有警告或有错误」的守卫**外面**，英文分支什么都不打。78 个渲染用例 + acceptance
   18 项全没抓到 —— 因为它们**每一条都是有诊断的用例**。已补 4 条断言（干净编译两个
   模式都不得出现摘要；连接词后必须有空格）。
2. **`生成了 2 个警告和1 个错误。`** 连接词后缺空格。实测既有表里「汉字紧贴数字」0 处，
   约定必须留空格。同一批断言覆盖。
3. **`scan_specs` / `has_value_placeholder` 把 `%%` 当成占位符**，于是任何保留 `%%`
   的条目都被判"畸形转义"+"缺角色表"。而 `%%` 恰恰是必须原样保留的。
4. **`_p_merge.py` 写 `.def` 时只转义 `"` 没转义 `\`**。中文正文里的 `'\u'` / `'\0'`
   写进 C++ 字符串字面量后被当成 Unicode/NUL 转义，5 条译文的字面反斜杠全丢。
   是 `check_protected_tokens` 报"丢了代码记号"才暴露的。

另外还有两处**门禁自己的**误报（都已修）：`'[^']*'` 在相邻引号 `''{...}'` 上会跨散文
配对出 `' are expressions with scalar type, and '` 这种假记号；英语所有格 `function's`
会被当成引号开头。

### 关键字口径（用户 2026-09-24 裁定）

**诊断里提到的关键字一律写中文关键字拼写**，写成 `（关键字） 类型名` / `（关键字） 静态转换` / `（关键字） 自身`。

裁定的直接起因：表里**自己就是矛盾的** —— `note_reinterpret_updowncast_use_static`
（"use **static_cast** to adjust the pointer"）写 `（关键字） 静态转换`，
而 `warn_reinterpret_different_from_static`（"behaves differently from **static_cast**"）
写 `'static_cast'`。**同一句话两种写法。**

理由不是"多数票"，是原则：**这是汉语编译器，用户源代码里敲的就是 `类型名` / `自身`，
诊断不该让他去认一个他不需要敲的英文词。** 裁定前先实测过中文关键字可用：

```cpp
struct S { int a; S* g() { return 自身; } };
void h(void* p) { int* q = 静态转换<int*>(p); }
struct T { int a; void f() { auto l = [自身]{ return 自身->a; }; } };
void k() { 常量表达式 int n = 3; 静态断言(n == 3); }
```
`clang++ -fsyntax-only -std=c++20` → **exit=0**。

这条推翻了 `docs\诊断汉化\第三批-待译与术语包.md` 第二版规则 8 的后半句
（"指你要敲进去的词 → 保留英文"），该文档已就地更正并附推翻记录。

**反过来的一条同样重要**：没加引号的关键字词是普通散文，**不许**标 `（关键字） `。
先例是 gold 里的 `class member cannot be redeclared` → `类中成员不能被重新声明` ——
裸的 `class` 当普通名词译成「类」，不是关键字「类型」。这条由 `check_keyword_markers` 强制。

### 两个语料（必须并排引用）

| 语料 | 改前 | 改后 |
|---|---|---|
| 真实项目（7 个开源项目，1398 条实例） | 99.3% | **99.4%**（1390/1398） |
| clang/test（400 个文件，4980 条实例） | 78.4% | **84.7%**（4217/4980） |

真实语料只涨 0.1 个点 —— 因为 P 档是**按表格长尾**选的，不是按频次选的；
它买到的是**表面覆盖率 1.2% → 37.2%**，不是实例覆盖率。两个数说的是不同的事。

## 二十、V/S/F 档全量汉化：4600 条（2026-09-24）

P 档（纯句子）之后，把剩下的 **V 档 3813 + S 档 784 + F 档 3 = 4600 条**也做完了。
中文表 **2744 -> 7344 条**，占全部内置诊断的 **99.6%**。

### 结果

| | P 档做完时 | 现在 |
|---|---|---|
| 中文表 | 2744 / 7374（37.2%） | **7344 / 7374（99.6%）** |
| 真实项目语料 | 99.4%（1390/1398） | **100.0%（1398/1398）** |
| clang/test 语料 | 84.7%（4217/4980） | **99.9%（4974/4980）** |

剩下的 30 条是 `"%0"` 直通条目：正文由后端（LLVM）给，本来就没有英语可翻。

### 「回退英文」这条路已经无处可观测

从第一批起，`tests\12-diagnostics\10_fallback_english.cpp` 一直靠「挑一条还没翻的诊断」
来证明「查不到就回退英文」。每加一批就要换一条，前后换过三次；到这一批**无条可换**了。

处理办法是把它换成一条更强的**表级断言**（写在 `tools\diag_id_lookup.py --check-table` 里）：
**凡是有英文正文的诊断，都必须在中文表里**。白名单只有 `"%0"` 这类直通条目。
这条断言不会随着覆盖率上升而失效，而那一个渲染用例会。

### 这一批的门禁边界（必须说清）

门禁能证明的：占位符集合、`%select`/`%plural`/`%diff` 的分支数与**分支顺序**、
角色表词表合法且成对、代码记号保留、`%%` 数量、关键字用中文拼写。
门禁**证明不了的**：**角色词选得对不对** —— 把 `（属性名）` 写成 `（变量名）` 照样通过。

这一批的实际做法：
1. 4600 条由 39 个批次翻译，每批自报「不确定的 ID」；
2. 门禁跑出 451 处问题，其中 321 条是「有占位符却没挂角色表」；
3. 派 8 个**定向修复**代理只修这些（把问题原文连同英文、现译文一起给它们），
   再跑一轮收尾修掉最后 23 条；
4. 最终 **4600 条 0 问题**。

角色词的正确性仍然只有**抽样人看**这一层保障。已在金标准里写明：门禁查不出标错。

### 这一批顺带修掉的门禁自身缺陷

- `scan_specs` / `has_value_placeholder` 把 `%%` 当占位符（保留 `%%` 反而被判畸形转义）。
- 引号里的 `%select{...}` 被当成「必须逐字保留的代码记号」，逼着把最该翻的分支留成英文。
- `'[^']*'` 在相邻引号 `''{...}'` 上跨散文配对，产出 `' are expressions with scalar type, and '` 这种假记号；
  英语所有格 `function's` 被当成引号开头。
- `check_role_table` 把**任何**全角括号组当角色表，正常补注 `（plain old data）` 被判非法。
- `check_zh` 只查中文的畸形 `%`、不比对英文，于是英文模板自带 `'%|'` 的条目**无论怎么翻都必红**。
- `（关键字） ` 的字符类没排除 `}`，写成 `%select{…|（关键字） 新建}0` 时会把 `}0` 一起当成关键字。
- `check_keyword_markers` 写好了却**没接进 `check_table`**，也没自检 —— 是批量翻译的子代理
  反过来发现的（"工具里定义了但没人调用"）。这个项目已经栽过两次同类。

### 另一处「重复门禁漂移」——第四次

用例 10 改掉之后，`tests\12-diagnostics\check.ps1` 过了而 `tools\acceptance.ps1` 还是 17/1 ——
因为它有**同一断言的第 4 份副本**。两份现在互相写明「对方也有一份，改就一起改」。
