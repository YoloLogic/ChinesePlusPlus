# 诊断汉化：独立复核指南

> ## 只要一条命令
>
> ```powershell
> powershell -File E:\Chinese++\tools\acceptance.ps1
> ```
>
> 它把下面 9 条主张里**能自动化的全部**做成带证据的断言，逐条打印 PASS/FAIL，
> 最后给总数并以退出码表态。约 8 分钟。
> 本文档剩下的部分是给"想自己动手、不信任那个脚本"的复核者看的。
>
> **给复核 AI 的一句话**：
> 先跑上面那条命令，再读 `tools\acceptance.ps1` 的源码确认它没有作弊；
> 然后按本文档第 3 节的格式，给出你自己跑出来的结论与任何反例。

> **用途**：让**另一个 AI 对话**（或另一个人）在**完全没有上下文**的情况下，
> 独立验证"报错汉化"这件事到底做完没有、做对没有。
>
> ## 铁律
>
> **不要相信本仓库任何文档里的结论 —— 包括本文档。**
> 文档只提供"该验证什么"和"怎么验证"。**结论必须来自你自己跑出来的输出。**
> 凡是写着"已通过"的地方，你都要自己复现一遍；发现对不上，直接判失败。

## 1. 要验证的 9 条主张

每条都给了命令和**失败判据**。请逐条给结论。

### 主张 1：报错正文是中文

```powershell
$cxx = 'E:\Chinese++\build\Release\bin\chinese++.exe'
& cmd /c "`"$cxx`" -std=c++20 -fsyntax-only `"E:\Chinese++\报错示例\01_undeclared.cpp`" 2>&1"
& cmd /c "`"$cxx`" -std=c++20 -fsyntax-only `"E:\Chinese++\报错示例\05_const_assign.cpp`" 2>&1"
```

**应看到**：`error: 使用了未声明的标识符（名字） '甲'`、
`error: 不能给常量限定类型（类型） 'const int' 的变量（变量名） '甲' 赋值`
+ 一条中文 note `变量（变量名） '甲' 在此被声明为常量`。
**失败判据**：正文是英文；或同一行里中英混排（例如 `使用了 undeclared identifier`）。

### 主张 2：前缀与选项名**没有**被翻译

同上面命令的输出。

**应看到**：仍然是 `error:` / `warning:` / `fatal error:`；警告尾部仍带 `[-Wunused-variable]` 这类英文选项名。
**失败判据**：出现 `错误:` / `警告:`；或 `[-W...]` 不见了。

### 主张 3：只换正文 —— `.td` 零改动（**这条最关键，请重点查**）

```powershell
Get-ChildItem 'E:\Chinese++\LLVM-main\clang\include\clang\Basic' -Filter 'Diagnostic*.td' | ForEach-Object {
  $b = Join-Path 'E:\LLVM-main\clang\include\clang\Basic' $_.Name
  $same = (Get-FileHash $_.FullName -Algorithm SHA256).Hash -eq (Get-FileHash $b -Algorithm SHA256).Hash
  Write-Host ("{0,-40} identical={1}" -f $_.Name, $same)
}
```

**应看到**：**全部 `identical=True`**（包括 `DiagnosticSemaKinds.td`、`DiagnosticParseKinds.td` 等）。
**失败判据**：任何一个 `False` —— 那说明英文诊断定义被动过了。

顺带请自己判断：**只加一张表、不改上游定义** 这个设计是否真的成立
（可对照 `clang/include/clang/Basic/ChineseDiagnostics.def` 与
`clang/lib/Basic/Diagnostic.cpp` 里那 3 行挂钩）。

### 主张 4：查不到就回退英文（**最强的证据是"逐字节相同"**）

`tests\12-diagnostics\10_fallback_english.cpp` 用的诊断**不在**中文表里，所以：

```powershell
$cxx = 'E:\Chinese++\build\Release\bin\chinese++.exe'
$f = 'E:\Chinese++\tests\12-diagnostics\10_fallback_english.cpp'
& cmd /c "`"$cxx`" -std=c++20 -fsyntax-only `"$f`" > $env:TEMP\a.txt 2>&1"
& cmd /c "`"$cxx`" -std=c++20 -fsyntax-only -fno-chinese-diagnostics `"$f`" > $env:TEMP\b.txt 2>&1"
$a = [IO.File]::ReadAllBytes("$env:TEMP\a.txt"); $b = [IO.File]::ReadAllBytes("$env:TEMP\b.txt")
Write-Host ("length {0} vs {1}   identical={2}" -f $a.Length, $b.Length, ([Linq.Enumerable]::SequenceEqual([byte[]]$a,[byte[]]$b)))
```

**应看到**：`identical=True` —— 一条没有中文条目的诊断，加不加开关**输出完全一样**。
**失败判据**：两份输出不同。

### 主张 5：开关真的能切回英文

```powershell
$cxx = 'E:\Chinese++\build\Release\bin\chinese++.exe'
$f = 'E:\Chinese++\tests\12-diagnostics\09_unused_var.cpp'
& cmd /c "`"$cxx`" -std=c++20 -fsyntax-only -Wall `"$f`" 2>&1"
& cmd /c "`"$cxx`" -std=c++20 -fsyntax-only -Wall -fno-chinese-diagnostics `"$f`" 2>&1"
```

**应看到**：第一份是 `warning: 未使用的变量（变量名） '甲'`，第二份是 `warning: unused variable '甲'`。
**失败判据**：开关无效、或报 `unknown argument`。

### 主张 6：占位符没有写坏（这事的最大风险）

```powershell
python E:\Chinese++\tests\checks\verify_zh_diagnostics.py
```

**应看到**：`chinese table entries: N`、`validator self-test: OK`、
`all Chinese diagnostics entries are valid`，退出码 0。
**失败判据**：退出码非 0；或问题列表非空。

**并且请自己判断这个校核器是不是"永远返回通过"的空壳**：
读 `tools\diag_id_lookup.py` 里的 `self_test()`，看它是否真的构造了"写坏的占位符"
并断言校核器会报错。你也可以自己复制一份 `.def` 到临时文件、故意删一个 `%0`，
看把路径指过去会不会报错（**不要改仓库里的原文件**）。

### 主张 7：中文正文里没有漏掉的占位符（端到端，不依赖校核器）

把某个用例编译出来的中文输出里，**不应该出现 `%0`、`%select{`、`%1` 这种原始占位符**：

```powershell
$cxx = 'E:\Chinese++\build\Release\bin\chinese++.exe'
Get-ChildItem 'E:\Chinese++\报错示例\*.cpp' | ForEach-Object {
  $out = & cmd /c "`"$cxx`" -std=c++20 -ferror-limit=0 -fsyntax-only `"$($_.FullName)`" 2>&1" | Out-String
  if ($out -match '%[0-9]|%select|%plural|%diff') { Write-Host ("!! 占位符漏了: " + $_.Name) }
}
Write-Host 'no output above = ok'
```

**失败判据**：任何 `!!` 行。

### 主张 8：补丁可信（干净树 + 补丁 == 我们的树）

补丁在 `E:\Chinese++\patches\`。**请自己重新验证一遍**，不要相信文档里的说法：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File E:\Chinese++\tools\make_patch.ps1
```

**应看到**：每个补丁末尾出现
`OK: clean tree + patch == our tree, all N files byte-identical`，
以及 `all patches verified`，退出码 0。
**失败判据**：任何 `content differs` / `missing` / 退出码非 0。

> **这一条请特别用力查：补丁"完整性"曾经错过两次。**
> 只扫 `clang\` 时漏了 `llvm\CMakeLists.txt`（全局 `/utf-8`，
> 漏了会导致中文在 MSVC 下**静默**变乱码）；
> 只扫 `clang\` + `llvm\` 时又漏了
> `clang-tools-extra\clangd\SourceCode.cpp`（clangd 的中文关键词修复，
> 漏了会让用补丁重建的人**静默**失去 clangd 的中文支持）。
> 两次都是复核者发现的，不是脚本自己发现的。
>
> 所以请**独立地**做一遍全树比对：把两个树的**每一个顶层目录**都过一遍
> （文件数 + 总字节数，快；怀疑的再逐个 SHA256），确认
> **有差异的文件全都在补丁里**。脚本现在有 0b 步做这件事，但别信它 ——
> 自己写几行跑一遍。
>
> 残余局限（脚本注释里也写了）：若某个未被扫描的目录里，
> 改动恰好让**文件数与总字节数都不变**，这一步看不出来。

### 主张 10：终端 UTF-8 的修复**真的生效**且**真的可逆**

背景：`chinese++.exe` 固定输出 UTF-8 字节，而中文 Windows 控制台默认代码页是
GBK(936)，于是中文变乱码。修复方式是往用户的 PowerShell `$PROFILE` 里加一段
带标记的块（`chcp 65001` 等三行）——**不是**改 VS Code 的终端配置。

这一条**必须自己验**，因为"改了配置文件"和"真的生效了"是两件事。

**10a. 真的生效了吗** —— 关键在于**先把父控制台强制成 936**，
否则你可能看到的是上一次实验残留的 65001（这是个真实的假验证陷阱）：

```powershell
cmd /c "chcp 936 >nul && powershell -NoLogo -Command chcp"
```

**应看到**：`Active code page: 65001`。
**失败判据**：显示 936（说明 profile 没起作用），或报错。

**10b. 真的可逆吗** —— 请**自己**保存安装前的字节数与 SHA256，然后：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File E:\Chinese++\tools\setup_utf8_terminal.ps1        # 装
powershell -NoProfile -ExecutionPolicy Bypass -File E:\Chinese++\tools\setup_utf8_terminal.ps1 -Undo  # 撤
```

**应看到**：撤销后**字节数与 SHA256 都与安装前完全相同**。
（块首行写着 `prev-chars=<原字符数>`，撤销按它截断回原长度。）
**失败判据**：长度或哈希变了；或撤销后块还在。
别忘了验完**再装回去**（否则你把用户的终端修复撤掉了）。

**10c. 失败时会装死吗** —— 门禁必须能失败。把脚本复制到临时文件、
故意把一个不存在的路径塞进 `$targets`，或者在一个无写权限的位置测试：

**应看到**：`FAILED: N file(s) could not be written` + **退出码 1**。
**失败判据**：写不进去却打印 "updated ... file(s)" 并 exit 0
—— 这个脚本的第一版就是这样（"失败报成功"），已被复核者抓过一次。

**10d. 顺带证伪一个说法**：文档声称"把终端设成 UTF-8 **不会**让 MSVC 的报错变乱码，
因为 `cl.exe` 会跟着代码页走"。请自己试：

```powershell
$cl = 'C:\Program Files\Microsoft Visual Studio\2022\Community\VC\Tools\MSVC\*\bin\Hostx64\x64\cl.exe'
cmd /c "chcp 936   >nul && cl.exe /不存在"    # 看它的中文
cmd /c "chcp 65001 >nul && cl.exe /不存在"    # 再看
```

**应看到**：两次都能显示出可读的中文（第二次是它自己改成 UTF-8 输出的）。
**失败判据**：某一次乱码 —— 那说明文档这句话是错的，请指出来。

## 2. 已知陷阱（**先确认这些，再下结论**）

这些现象是**设计如此**，不是 bug。但请你**独立确认**，而不是照抄：

| 现象 | 为什么不是 bug |
|---|---|
| 有些报错仍是英文（如 `candidate function not viable: ...`、`too few template arguments ...`、`'x' is a private member of 'y'`） | 中文表做了 48 条（按真实频次覆盖约七成诊断实例），查不到就**故意**回退英文。这正是主张 4。同一次编译里中英并排出现是预期效果，见 `报错示例\11_overload.cpp` |
| `error:` / `warning:` 前缀是英文 | **故意定的**：VS Code 的 C++ 问题匹配器正则写死了 `(warning\|error\|note):`，翻了前缀 Problems 面板会空。理由与"以后想改怎么改"记在同目录《诊断汉化清单.md》 |
| `chinese++.exe` 和 `clang++.exe` **大小/时间戳可能不一致** | 它是硬链接，链接器"先删后建"会**断链**，让 `chinese++.exe` 停在旧版本 —— 这时你测的就是旧编译器。**先查这个**：<br>`(Get-Item ...\chinese++.exe).Length` 与 `clang++.exe` 比，不一致就是断了；用 `New-Item -ItemType HardLink -Force` 重建 |
| `报错示例\` 里的代码全都编不过 | 那是给人看的"错误示范"目录，**故意**不纳入 `run_all.ps1` |
| `.vscode\settings.json` 里**没有**终端 profile 配置 | 这是**故意的**：曾经两次把 `chcp` 塞进 `args`，都因为命令行里出现**第二个 `-Command`** 而启动即报错（`参数格式不正确 - -Command`）。所以终端设置走用户 `$PROFILE`，见主张 10。**不要**把它加回 `.vscode` |
