## 3. 第 4 步：我主动尝试推翻它的结果

### 反例 A（成立，但可被流程兜住）：校核器会**静默放过被截断的中文表**

校核器只检查"读到的条目是否合法"，**从不检查读到了多少条**。

```powershell
# 把真表复制到临时文件，只保留到 err_no_member 那一行为止（不要动仓库原文件）
cd E:\Chinese++
python -X utf8 -c "
import sys,hashlib
sys.path.insert(0,r'E:\Chinese++\tools')
import diag_id_lookup as d
SRC=r'E:\Chinese++\LLVM-main\clang\include\clang\Basic\ChineseDiagnostics.def'
orig=open(SRC,encoding='utf-8').read()
before=hashlib.sha256(open(SRC,'rb').read()).hexdigest()
cut=orig.index('ZH_DIAG(err_no_member,'); cut=orig.index(chr(10),cut)+1
tmp=r'E:\Chinese++\build\_adv\trunc.def'
open(tmp,'w',encoding='utf-8',newline=chr(10)).write(orig[:cut])
d.ZH_DEF=tmp
inc=d.parse_inc(); lines,probs,zh=d.check_table(inc)
print('entries the validator actually read: %d  (real table: 32)' % len(zh))
print('problems reported                 : %d' % len(probs))
print('validator exit code would be      : %d' % (1 if probs else 0))
after=hashlib.sha256(open(SRC,'rb').read()).hexdigest()
print('repo file unchanged               : %s' % (before==after))
"
```

原始输出：

```
entries the validator actually read: 7  (real table: 32)
problems reported                 : 0
validator exit code would be      : 0
repo file unchanged               : True
```

同一现象在"物理砍掉一半"和"砍在一个多行条目中间"时同样成立：

```
A) truncated right after the err_no_member line
   entries parsed : 7  (real table has 32)   problems: 0
   -> validator verdict: MISSED (silently passes)
B) truncated in the middle of a multi-line entry
   entries parsed : 8   problems: 0
   -> validator verdict: MISSED
```

**影响与缓解**：`verify_zh_diagnostics.py`（主张 6）与 `diag_id_lookup.py --check-table` 会在表被截断时**返回通过**；`acceptance.ps1` 的第 6 步只看这个退出码，因此**这一步抓不到截断**。兜底在下游：`tests\12-diagnostics` 的 26 个用例共 **63 个 `expect:`/`forbid:` 运行时断言**（我数出来的），删掉任何一个有用例的诊断都会让主张 9 变红。所以实际风险是"证据环节出现虚假绿色"，而不是"用户拿到坏编译器"。
**建议**：在校核器里加一句最低条数断言（例如 `assert len(zh) >= 32`），并把"截断不被本步发现"写进同目录《诊断汉化清单.md》的局限清单。

## 5. 总体结论

**可发布。** 指南第 1 节的 9 条主张，我独立复现后**全部成立**；第 2 节"已知陷阱"的 4 条（部分英文回退、前缀英文、硬链接断链、`报错示例` 故意编不过）我也逐条独立确认属实，没有把它们误判成 bug。

**必须修的（1 项，非阻塞）**：
- `verify_zh_diagnostics.py` / `diag_id_lookup.py --check-table` **不校验条目条数**，被截断的表会以退出码 0 静默通过（反例 A）。建议加最低条数断言；下游 63 个运行时断言目前兜住了它。

**建议如实补充文档的（1 项）**：
- `%0`/`%1` 对调确实抓不到（反例 B，文档已自认）；补充说明"表被截断同样抓不到"，这份诚实清单才算完整。

**不构成缺陷的**：
- `类` 不是关键字而 `类型` 是（反例 C）——是我的测试写错，不是汉化问题。

### 6.3 唯一残留：把守卫行**注释掉**时按子串判断，不报错（影响可忽略）

先说明：我第一次写的 E4 用例是**我的测试错误**，不是实现缺陷。我用
`orig.replace('#ifndef ZH_DIAG', '// #ifndef ZH_DIAG')` 造"删掉表头守卫"，

判定为"存在"——它没坏，是我没真的删掉那一行。

改用真正删除整行后重测（`build\_adv\guard.def` 路线）：

```
  [CAUGHT] G1 header #ifndef line actually REMOVED    entries=32 problems=1
        - 表头缺少 `#ifndef ZH_DIAG` 守卫 —— 文件可能被改坏了
  [CAUGHT] G2 tail #undef line actually REMOVED       entries=32 problems=1
        - 表尾缺少 `#undef ZH_DIAG` —— 文件很可能被截断了

        - 表里只有 29 条，少于下限 32 —— 被截断或被误删？
  [MISSED] G4 real table (must be clean)              entries=32 problems=0
```

**两条守卫都按预期生效，且不误伤真表。** 仅存的边角是：两条守卫用的是**子串**判断，
把守卫行改成注释（`// #ifndef ZH_DIAG`）在文本上仍含该子串，因而不会报错。
**影响可忽略**：这种做法不减少任何条目、也不改变表的内容（`#ifndef` 被注释掉后
头文件仍能编译），所以不构成"表被改小"的风险。真正有威胁的两类——**截断**与
**删条目**——已分别被 G2 与 G3 覆盖。
